00项目定义与边界

一句话
把"原文 + 音视频"变成"双语字幕文件"的本地流水线
输入台词文本和音轨，输出带正确时间轴的 ASS/SRT。全程离线。
核心未知量
只有"时间"
内容已知（台本/日文字幕），要解的是每个字符落在音频的哪一秒——这是一个对齐问题，不是识别问题。
成功标准
4 个数字
对齐中位误差 ≤80ms、术语命中 100%、24 分钟单集 ≤90s（GPU）、断网可跑通。

明确不做的事（Non-goals）

  • 不接任何在线服务：不调 OpenAI / DeepL / 百度 / 有道，不发一个字节出去。断网必须是正常状态，不是降级状态。
  • 不走 Whisper 系：不用 whisper、faster-whisper、whisperX、stable-ts、whisper.cpp。也不做"先 ASR 再翻译"这个结构。
  • 不做配音（TTS）：只做文本与时间轴。语音合成是另一个项目，混进来会让范围失控。
  • 不做视频压制：输出字幕文件，封装交给 ffmpeg 一行命令，工具本身不碰编码参数。
  • 不追求"一键全自动无人值守"：目标是把人工从 100% 降到 20%，而不是 0%。全自动的字幕一定需要人看一遍。

01为什么"不用 Whisper"反而是更优解

大多数人听到"不用 Whisper"的第一反应是"那质量不就差了"。恰恰相反——在你的场景里，Whisper 是那个多余的环节。

1.1 ASR-first 的四个结构性缺陷

主流方案是 音频 → Whisper 识别 → 得到文本和轴 → 翻译 → 输出。这条路在你关心的场景（日语动画、Galgame、广播剧、舞台影像）里有四个绕不过去的问题：

问题一：错误会级联，一次错三处

识别把角色名听错 → 翻译跟着错 → 时间轴也切在错的位置。改一个字要重跑整条链。而文本优先的方案里，内容从一开始就是对的，出错只可能出在"边界偏了几十毫秒"，改起来是拖一下鼠标。

问题二：Whisper 的静音幻觉是结构性的，不是调参能解决的

在纯 BGM 段、音效段、长静音段，Whisper 会凭空生成文本——最常见的产物是"ご視聴ありがとうございました"、"字幕由 XX 提供"这类训练数据里的高频尾巴。这是自回归解码在低信息量输入上的必然行为。你只能事后过滤，但过滤规则永远漏。

问题三：专有名词恰恰是 ASR 最弱、翻译最需要的地方

人名、招式名、拟声词、方言、造语，这些在通用 ASR 的发音词典里几乎不存在。而术语一致性正是字幕质量的第一道门槛（报告 01 的踩坑清单里，"术语不统一"是出现频率最高的一条）。用最不可靠的环节去决定最需要可靠的部分，这个结构本身就不对。

问题四：重叠语音无法分条

多人同时说话时，ASR 只能给出一条混合文本流。但字幕必须按说话人切成多条、分别定位。ASR 的输出形态和字幕的需求形态天生不匹配。

1.2 换个问法，问题规模小一个数量级

维度ASR-first（含 Whisper）Text-first（本项目）
要解的未知量内容 + 时间（两个都未知）只有时间
错误性质语义级，只能重跑数值级，可局部微调
专有名词听错就一路错到底原文里就是对的
术语一致性受识别结果波动影响术语表直接约束
失败模式整段崩坏单句偏 200ms，标记后手调
可复现性换模型/换版本结果就变确定性算法，同输入同输出
CPU 耗时（24min）十几分钟起VAD + 对齐约 2–4 分钟

架构结论

音频只承担一件事：告诉你"这句话从第几秒说到第几秒"。它不参与"说了什么"的判断。

于是整条链变成：原文 → 分句 → 对齐到音频 → 翻译 → 排版 → 输出。翻译和对齐是两条独立的、可分别测试的支路，任何一条坏了不会污染另一条。

1.3 四种输入形态，四种处置

真实素材不是只有一种。工具必须先判断"手上有什么"，再决定走哪条路——这是整个系统的第一个分叉点。

档手上有什么缺什么走哪条路典型场景质量
L0带轴的原文（日字 .ass/.srt）译文直通：继承轴 → 只翻译 → 重新断行BD 自带日文字幕、已扒的软字幕最高
L1无轴原文（台本 / 游戏文本 / 小说）轴强制对齐：VAD 切段 → 文本-音频 CTC 对齐Galgame 文本、DRAMA CD 台本、舞台剧脚本高

关键设计：L2 是兜底档，不是主路径。它的产出被明确标注为"草稿"，UI 上默认高亮待审。系统不允许 L2 的结果被误认为成品——这是防止质量悄悄下滑的机制。

3.2 打轴：三档引擎，各管一段

档算法依赖精度许可备注
L1-aCTC 强制对齐（已知文本在音频上跑 Viterbi）torchaudio MMS_FA（wav2vec2，1100+ 语言）中位 40–80msMIT首选，GPU 上很快
L1-bHMM-GMM 强制对齐Montreal Forced Aligner + japanese_mfa 模型中位 50–100msMITCPU 稳、慢，作为对照

为什么 L1 要加 VAD 硬约束

纯 CTC 对齐有一个典型故障：某一句的结尾被拉到很远的地方，导致后面整段错位（"雪崩"）。原因是模型在长静音上给出了弥散的发射概率。

解法是把 VAD 结果当成不可跨越的边界：每句话只能落在它所属的那个语音段内部。这一步把"全局崩坏"降级为"单句偏移"，是整个打轴模块最重要的工程细节。

L2 的比例分配，具体怎么算

日语是モーラ等时性语言，一个モーラ的时长相对稳定。所以段内按モーラ数加权，天然比按字符数准得多——这是它能在"只有音频"时还勉强可用的原因。

import pyopenjtalk

def mora_count(text: str) -> int:
    # 去掉标点与空白，只数假名/モーラ
    phones = pyopenjtalk.g2p(text, kana=True)
    return sum(1 for c in phones if c not in "、。！？!? 　")

def allocate(lines, seg_start, seg_end):
    total = sum(mora_count(l.src) for l in lines) or 1
    span, t = seg_end - seg_start, seg_start
    for l in lines:
        d = span * mora_count(l.src) / total
        l.start, l.end = t, t + d
        t += d

然后做边界吸附：真实的换句点通常落在能量低谷，而不是数学计算出来的位置。

def snap(t, rms, sr=100, win=0.15):
    lo, hi = int((t - win) * sr), int((t + win) * sr)
    lo, hi = max(lo, 0), min(hi, len(rms) - 1)
    return min(range(lo, hi), key=lambda k: rms[k]) / sr

两个函数加起来不到 20 行，但它们决定了 L2 档是"能用"还是"不能用"。这类算法不需要模型，需要的是对语言节奏的理解。

3.3 翻译：模型不是关键，术语表才是

先摆一个反直觉的事实：在 Galgame / 动画字幕这个领域，把 14B 换成 7B 的质量损失，远小于"没有术语表"带来的损失。角色名前后不一致、同一招式三种译法，读者会立刻出戏；而模型小一点只是文风稍平。

方案显存日语→中文速度许可定位
Sakura 14B GGUF (iq4_xs)~9 GB同尺寸最优，专为日译中微调20–40 tok/s见模型卡主力
Sakura 7B GGUF~5 GB良好更快见模型卡低配机 / 批处理
Opus-MT / Argos（CPU）0一般，短句尚可很快MIT / CC-BY无独显兜底
TM + 术语表 + 规则0完全可控极快自有UI 文本 / 重复台词

四层兜底，保证"没有模型也能出活"

  1. TM 命中：完全相同的原文（Galgame 里 UI 文本、系统提示、口头禅重复率极高）直接复用旧译，零推理。
  2. 术语表替换：专有名词先占位成 {T1} 之类的 token 再送模型，译完还原。彻底杜绝"模型自己发挥"。
  3. 本地模型：剩下的句子走 Sakura。
  4. 原文回填：模型超时、输出异常（长度比例 <0.2 或 >3.0、含未翻译假名）时保留原文并打 untranslated 标记，绝不静默输出垃圾。

3.4 许可证：一条容易被忽略的分发边界

组件许可能否直接 import处理方式

04数据模型与产物契约

4.1 唯一的中间表示

整个系统只有一种核心数据结构。所有解析器都产出它，所有渲染器都消费它，任何模块都不允许绕过它直接读写字幕文件。

@dataclass
class Line:
    id: str              # 稳定 ID：ep03-0042，重跑不变，人工修改靠它对位
    speaker: str | None  # 说话人，可为空
    src: str             # 原文（日语）
    dst: str             # 译文（中文），未翻译时等于 src
    start: float         # 秒
    end: float           # 秒
    mora: int            # モーラ数，L2 分配用
    conf: float          # 对齐置信度 0–1
    flags: list[str]     # overlong / untranslated / term_conflict / overlap / low_conf

id 为什么必须稳定

人工校对会产生修改（改了译文、拖了边界）。如果重跑一次 ID 就变，所有人工修改都会丢。

规则：id = 集号-行号，行号在解析阶段确定，之后永不重排。人工修改存在独立的 edits.jsonl 里，按 id 覆盖流水线输出。这样"重跑"和"人工修改"可以共存，而不是互相覆盖。

4.2 目录即契约

work/<project>/
  source/            原始输入，只读，永不修改
  audio/16k.wav      统一采样率单声道
  vad/segments.json  语音段列表
  script/lines.jsonl 核心中间表示
  align/words.json   字/音素级时间戳
  tm/cache.sqlite    翻译缓存
  edits.jsonl        人工修改（append-only）
  out/
    ep01.zh.ass      纯中文字幕
    ep01.bi.ass      中日双语
    ep01.srt         兼容格式
  report.json        每集统计

这个结构的设计意图是：任何一步都可以单独重跑，且不污染上下游。改翻译只删 out/；改对齐只删 align/ 和 out/；source/ 永远不动，所以任何灾难都能回到原点。

4.3 幂等：重跑必须给出同一个结果

cache_key = sha256(
    src + "" +
    prev_src + "" + next_src + "" +   # 前后文，保证语境一致
    glossary_version + "" +                # 术语表改了就失效
    model_id + "" + temperature
)

把前后文和术语版本纳入 key，是一个容易被省略但很重要的细节：只按原文做缓存，会导致"改了术语表但旧译还在"的诡异 bug，而且极难排查。

08Day 0 启动清单

第一天的目标不是写代码，是把"不确定性"清零。

环境（半天）

  • Python 3.11 + uv（不要用 3.13，torch 生态还没跟上）
  • ffmpeg 静态包，加进 PATH，ffmpeg -version 能跑
  • llama.cpp 或 Ollama，先跑通一个 7B 的 GGUF，确认推理链路
  • pip install torch torchaudio pyopenjtalk numpy soundfile，跑通一次 MMS_FA 对齐

读代码（一天，只读不写）

项目读什么为什么
GalTransl ★2353术语表实现、GPT 字典、缓存文件格式、断句逻辑这四块是翻译质量的全部，自己从零设计会走一样的弯路
ffsubsync ★7.9kVAD 抽取 + FFT 互相关的具体参数重同步的工业级实现，直接抄参数比自己调快十倍
MFA ★1.9k日语模型的音素集与词典格式决定 L1 的输入怎么准备
HDEG（报告 03 提到）台本锚定 ASR 纠错的思路它的核心洞察和本项目一致：用已知文本约束对齐

素材（半天，必须真的准备）

  • L0 组：一段带日文字幕的 5 分钟片段（验证直通）
  • L1 组：一段有台本、无字幕的 5 分钟音频（验证强制对齐）
  • L2 组：一段只有音频的 3 分钟片段（验证比例分配）
  • L3 组：把 L0 的字幕人为偏移 +4.7s（验证重同步）
  • 金标集：20 个术语（人名/地名/招式）+ 50 句手工标轴的真值

没有金标集就没有验收标准，没有验收标准就会在"感觉差不多了"里无限打磨。这半天的投入回报率最高。

两个必须先写下来的决定（一小时）

ADR-001：文本优先，不做 ASR

记录第 1 节的推理。将来任何人（包括三个月后的你）想"顺手加个 Whisper 兜底"时，先读这一页。约束一旦松动，架构就会退回 ASR-first。

ADR-002：GPL 组件进程隔离

记录 3.4 的结论。决定"这个工具是自用还是要发出去"，并据此定依赖策略。这个决定越晚做越贵。

最后一句

这个项目的技术难点不在模型，在对"什么该由机器决定、什么该由人决定"的划分。把时间轴交给算法、把内容交给原文、把判断留给校对界面——分工清楚，六周就能出东西；分工不清楚，六个月还在调参。
