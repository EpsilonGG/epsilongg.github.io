01三个仓库各自是什么

先建立坐标系：一个是"流程契约"，一个是"桌面产品"，一个是"脚本碎片"。三者的可复用粒度完全不同。

1.1 GalgameCriticism-skills —— 把编辑流程写成 Agent 能执行的契约

Agent Skills Python / Node / C# ★2 最近推送 2026-10-21

仓库本体只有 76 个文件，但结构极其克制：skills/<name>/ 下每个技能自带 SKILL.md（给 agent 看，讲怎么执行）、README.md（给人看，讲这是什么）、scripts/、references/、agents/、tests/。仓库根只允许存在 README.md、AGENTS.md、.gitignore——这条规则写在 AGENTS.md 里，并且要求提交前自检目录一致性、扫描凭证与个人路径。

它真正值钱的不是代码量，而是把一份周报从 docx 到四个平台的全过程拆成了可验证的契约：

Skill输入输出关键依赖人工介入点
bilibili-weekly-article期目录（去注音 docx + 图包 + 封面）B 站图文草稿 / 已发布 OpusPython requests、lark-cli（飞书）、扫码登录第 3 步强制人工审核，第 4 步手动点发布
weekly-cross-platform-sync来源平台 + 目标平台 + 期号不可变 manifest + SHA-256 + 各端回执无（纯编排）账号/社区确认、预览核对

编排关系是一条单向前缀链，中间被人为切开一道口子：

期目录（docx 去注音 + 图包 + 封面） │ ▼ parse_materials.py → render_preview.py → fetch_staff.py（飞书署名） ┌──────────────────────────────────────────────┐ │ bilibili-weekly-article 产出草稿（不代发） │ └──────────────────────────────────────────────┘ │ 草稿箱回执 article_id ▼ ✋ 人工审核版式/配图/署名 → 在 B 站编辑器手动点「发布」 已发布的 B 站图文（cv 号 / 公开链接） │ ▼ weekly-cross-platform-sync：按期号定位、采集一次不可变 manifest ├──▶ xiaoheihe-weekly-sync ──▶ 小黑盒 ├──▶ zhihu-weekly-sync ──▶ 知乎 └──▶ weibo-weekly-sync ──▶ 微博

这条链上有三份契约，是全仓库最有复用价值的部分：

  • 素材契约 _preview/article.json：sections[].items[] 里带 n / heading / body[] / candidates[] / selected[]，把"哪条新闻配哪两张图"变成可索引的数据；title_status 区分 proposed（机器拟的）与 manual（人定稿的）；warnings[] 未清零不得上线。
  • manifest 契约：一次采集产出 manifest.json + preview.md + 图片目录，字段含 source / source_id / canonical_url / title / blocks / images / author / published_at，并记 SHA-256。所有目标平台从这一份派生，不允许二次抓取来源。
  • 回执契约：去重键是 source + source_id + target_account + target_scope + content_type；最终回复必须给公开链接，草稿/编辑器/本地路径不得填在"成功"位置，没回读通过只能标 submitted / pending_review / unknown / failed。

2.3 踩坑清单（可用性最硬的证据）

这批文档里最有价值的内容不是"怎么用"，而是"哪里会炸"。整理如下——如果你要复用这套东西，这张表能省掉几天调试：

#坑表现正确做法
1docx 选错版本正文里混进 【注音】 括号必须用标题带「去注音」的稿；脚本对回退原始稿告警，未清不得上线
2署名不在 docx 里发布后缺"文案/审核"fetch_staff.py 从飞书「周报工作表」按期号拉取
3大图上传超时aiohttp 库版必超时统一走 upload_bfs.py requests 直传，120s 超时 + 重试
4B 站扫码失效旧 login.py 拿不到 cookie新版把 cookie 移到 Set-Cookie 头，用 login_qr.py，并用 nav 接口验证 isLogin 后才落盘
5草稿被覆盖重跑冲掉人工改过的草稿已有回执默认停止，--replace 才删旧建新
6小黑盒 Cookie 短命编辑器能打开，发布最后一步失败有效期实测 1–2 天；判断依据是返回的用户名，不是"编辑器可编辑"
7标题长度差异各平台截断规则不同B 站 ≤80 字；小黑盒 30 字（超了只截标题，原标题留正文首）；微博标题 32 字、导语 44 字
8微博图片插错位置图片跑到文末、WBIMGPH_ 残留必须"真实鼠标选区 + Shift+ArrowRight + Backspace + 合成 paste"；只派发 paste 无效
9微博"假成功"发布后跳 #/history/<id>那不是公开链接；要从 m.weibo.cn 时间线接口取 page_info.page_url
10知乎图片重复图片数翻倍判定完成用托管 URL 的 /v2-[0-9a-f]{32}，不能用 zhimg.com 域名；重试会重复插入，attempt<=1 是刻意的
11知乎 DOCX 导入"确认选择文件"永不进入可点击态被直答知识库配额拦截，不要在这条路上耗时间，走直排
12跨进程 CDP脚本被 SIGTERM（退出码 137）且无输出编排/校验/发布串在同一个 async 里，窗口只开一次
13端口冲突两个平台互相干扰微博 9333、知乎 9444，各自独立 profile
14误清登录态删 profile / Singleton*绝对不要——会直接清掉已登录 Cookie，必须让用户重新扫码

这 14 条说明一件事

这套 skill 的可用性不是"写得好"，而是"失败模式被穷举过"。每个坑都写了现象、判定依据和正确做法，而且明确区分"提交待审核"和"已公开发布"。这种文档质量在个人项目里极少见。

2.4 xueayi 与 TianSalt 的可用性

XiaoXue-Video-Tools 开箱可用

内置 FFmpeg/ffprobe，Windows x64 与 macOS arm64 双包，Release 附 SHA256。启动后台探测编码器能力，硬件编码器不可用自动置灰——这个设计避免了"选了 NVENC 结果报错"的常见体验崩点。

限制：macOS 包未做 Developer ID 公证；AviSynth 兼容模式仅 Windows；兼容模式要求非中文路径。

TaskNya 开箱可用

Docker 一行起，Web UI 管配置，支持 60 / 5m / 1h30m 时间格式，目录监控带"二次确认"避免文件没写完就通知。多条件是"或"关系。

限制：GPU 监控仅 NVIDIA；配置改完要点"应用当前配置"才生效。

Daily-Web-Login 需改造

三个工程细节值得抄：外置卷等待挂载（plist 不直接跑 main.py，先跑本机磁盘上的包装脚本轮询 900 秒）、日志分两处（启动日志放本机磁盘，卷没挂也能写）、flock 单实例（launchd 与手动启动不会双开）。

限制：macOS 专用菜单栏 App，不能直接跑在 Linux/CI；yngal 部分强绑定特定站点。

TianSalt 的零件 即取即用

lrc-converter 一行命令处理整个目录；accentjiten_anki 是数据管道；Kemono-Downloader 用 window.open 绕开跨域图片限制——这个技巧很实用。

限制：blog-scraper 自述是面试作业，MongoDB + Redis 依赖重，且明确写"仿人类行为效果未知"，不建议生产使用。

03边界内的组合用途

边界定义为：一份 Galgame 内容，从素材到多平台分发。不涉及视频平台投稿（不在 skill 范围）、不涉及商业变现。

场景 A · 周报视频版：把一次生产变成两种形态

现有链路只产出图文。但周报的素材（docx 正文 + 图包）本身就是视频分镜的原料。

期目录（去注音 docx + 图包） │ parse_materials.py → 抽出 sections[].items[]（标题 / 正文 / 配图） ▼ Subtitle-text-splitting-script（xueayi）→ 按字数断句成字幕行 ▼ lrc-converter（TianSalt）→ 若已有 SRT/VTT，统一转 LRC 做时间轴底稿 ▼ XiaoXue-Video-Tools（xueayi） · 图包序列 + 配音轨 → 压制（HEVC 高压缩，CRF 20） · 字幕策略选「内嵌（烧录）」→ 与图文版严格一致的视觉 ▼ TaskNya（xueayi）监控输出目录 → 飞书通知「成片已就绪」 ▼ 人工审片 → B 站视频投稿（不在 skill 范围）

价值：一份素材两种分发形态，边际成本只有压制时间。风险：docx 断句节奏和配音对不齐；烧录字幕要先做字体准备（macOS 用"字体兼容增强"，Windows 用 AviSynth 兼容模式），否则会出现字重/字形错误。

场景 B · 可观测性：把五个 skill 的回执汇成一张卡片

这是最容易被忽略、收益最直接的一环。当前链路的痛点不是"发不出去"，而是发出去之后没人知道哪一端失败了——尤其小黑盒 Cookie 每 1–2 天就过期一次。

用 TaskNya 做通知总线

  • 监控 _preview/publish_receipt.json、draft_receipt.json 生成 → 触发"草稿就绪"
  • 监控 data/delivery/*.jsonl 里 failed 记录 → 触发"某端待补发"
  • 日志关键字检测：CDP connection closed / newlogin / isLogin → 判定登录态失效
  • 统一推飞书群，用 ${var} 内联变量带期号与平台名

用 Daily-Web-Login 的范式做保活

  • 它的本质是"定时 + 打开页面 + 结果推飞书"，正好对应 Cookie 保活
  • 三个可移植设计：等待依赖就绪（卷挂载 → 等价于等 profile 解锁）、日志分离（启动日志与业务日志分开）、单实例锁
  • 不能直接跑：它是 macOS 菜单栏 App，CI 上要重写成 headless 定时任务

注意：Cookie 保活不能替代扫码。小黑盒的判定依据是接口返回的用户名，保活只能降低频率，不能绕过平台策略。

场景 C · 素材采集：补上流水线最前面那个空洞

GalgameCriticism 的 parse_materials.py 只认本地期目录——素材从哪来，是这条链完全没有覆盖的一段。TianSalt 的两个采集工具正好填进来：

  • Kemono-Downloader → 一键抓作品页全部图片；用 window.open 弹窗绕过浏览器跨域下载限制，落盘后直接进图包目录
  • XiaoXue-Video-Tools 的图片转换 + 批量重命名 → 把采集到的混杂格式（PNG/JPG/WEBP/GIF/TIFF）统一，并按 candidates[] 期望的顺序编号
  • blog-scraper 的工程范式（代理轮换 + Redis 队列 + 失败重试 + Actions 测试）→ 可作为 VisualNovel-Interview-RSS 那 11 个解析器的反爬兜底参考

关键约束：采集层必须产出可复现的清单（文件名 + 源 URL + SHA-256），否则 manifest 契约的"不可变素材"就失效了。

场景 D · 术语与注音一致性：消灭"去注音"这个人工环节

整条链路里有一个奇怪的细节值得注意：docx 必须用「去注音」版本，因为原始稿的 【注音】 括号会漏进正文。这说明团队内部有一个"给专有名词标读音"的工序，而它现在是纯手工的。

TianSalt 的 accentjiten_anki 提供了一条现成的数据管道：日语重音词典 → 结构化条目 → Anki 卡组。把中间那层抽出来，就是一张「Galgame 作品名 / 声优名 / 厂商名 → 读音」的术语表。接在 parse_materials.py 之后做一道校验：

parse_materials.py 产出 article.json ▼ 术语校验（新增） · 抽取 heading / body 中的专有名词 · 查术语表 → 命中则校验读音标注一致性 · 未命中 → 进 warnings[]，人工补录后回写术语表 ▼ warnings 清零后才允许 render_preview.py

诚实评估：accentjiten 是通用日语重音词典，不是 Galgame 专有名词库。它解决不了"这个作品名该怎么读"，只能提供读音标注的格式与工具链。真正的价值是把人工知识沉淀成可复用数据，而不是自动注音。

场景 E · 数据底座：给"新作资讯"章节供结构化候选

galgame-sedai 里有一段很实用的代码经验：它用 Bangumi 官方 API（POST /v0/search/subjects，sort=heat、tag=Galgame、按年过滤）在构建期生成年度榜单，而不是运行时抓网页。README 里还留了一条教训：

"原项目用 cheerio 抓 bgm.tv 网页，该方式现在会被 Cloudflare 拦截（403），因此改为走官方 API。请求必须携带可识别的 User-Agent。"

这条经验对场景 C 同样成立——VisualNovel-Interview-RSS 的 11 个解析器全是抓 HTML，长期一定会遇到同样的拦截。优先级应该是：有官方 API 就走 API，没有才写解析器。

三种不建议的组合

① 不要把发布 skill 塞进无人值守的 CI

五个 skill 里有四个依赖真实浏览器会话与扫码登录，weekly-cross-platform-sync 自己也写了"无人值守验收"要区分"代理临时改脚本跑通"和"固定脚本完整跑通"。把它当 cron 用，必然在 Cookie 过期那天静默失败。

② 不要用 bstream 做图片/视频压缩

它是按位读写文件的 C++ 头文件，不是编解码器。看着"底层"就想拿来做压缩是典型的能力错配——真正该做压缩的是 XiaoXue-Video-Tools 里的 FFmpeg。

③ 不要直接复用 blog-scraper

作者自己在 README 里标了"仿人类行为效果未知"，且强依赖 MongoDB + Redis。它适合当范式参考（代理池、队列、失败重试、Actions 测试），不适合当依赖。

04结论：这条链缺的是哪一块

把三个仓库摊开看，Galgame 内容流水线其实已经覆盖了 70%：生产契约、四平台分发、视频压制、通知监控、格式转换都有现成的。真正缺的是两块：

  • 采集层——素材从哪来完全空白，靠人工下载。TianSalt 的 Kemono-Downloader 只能覆盖一部分。
  • 翻译/多语言层——中文团队做日本内容，但整条链里没有任何一处处理日文。这是最反常的缺口。

第二块缺口正好是 EpsilonGG 那批仓库的主题。第三篇报告会接着讲：把那边的采集与翻译能力接进来之后，这条链会变成什么样。
