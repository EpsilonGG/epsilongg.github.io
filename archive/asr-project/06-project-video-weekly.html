00项目定义与边界

一句话
一份结构化内容 → 一条视频 → 六个平台
内容只写一次，形态由渲染器决定，平台差异由配置决定，人不参与重复劳动。
真正的约束
人工 ≤ 90 分钟/周
不是"能不能做出来"，而是"做了三个月还想不想做"。超过 90 分钟，周更必然断。
成功标准
4 个数字
端到端 ≤15 分钟机器时间、渲染成功率 ≥95%、连续 8 周不断更、镜像 ≤1.5GB。

明确不做的事（Non-goals）

  • 不做"AI 自动生成整条视频"：让 LLM 直接产出可播放成片，是稳定性的天敌。内容由 LLM 协助，画面由模板决定。
  • 不把两个上游项目当常驻服务跑：它们是构建期工具，不是 runtime 依赖。跑完就退，不占端口、不占内存。
  • 不做自动上传：除 YouTube 外，多数平台没有稳定开放的上传接口。自动上传的维护成本高于手动点六次。
  • 不做实时 / 日更：周更的节奏才能让"批量渲染 + 人工审一次"的模式成立。
  • 不做个性化推荐 / 数据分析：先把"稳定产出"做出来，数据看平台后台。

关键判断一：这两个项目都不能"养"

ManimCat 的作者在 README 里写得很直白——他没时间长期维护，建议你 fork 自己做。这句话翻译过来就是：不要把它当成一个会持续变好的依赖。你现在接进来的东西，大概率就是它最终的样子。

juya-news-card 更极端：★15、最后推送半年前、README 第一行写着"100% AI 项目，0 人工编写"。它不是一个会修 bug 的项目，它是一个"思路 + 模板库"的交付物。

关键判断二：所以只取"资产"，不取"应用"

把两个仓库各拆成两半：能带走的部分（模板、排版方案、渲染契约、失败修补思路）和带不走的部分（Next 应用、Studio 前端、Redis 队列、Supabase、Agent 会话）。

带走前者，丢弃后者。前者是静态的、可复制的、不会腐烂的；后者是运行时的、要升级的、会腐烂的。低维护的本质，就是只依赖不会腐烂的东西。

1.1 "低维护"的三个真正敌人

敌人表现为什么致命本方案的解法
上游漂移某天 npm install 突然失败，或渲染结果全变周更产线停摆，而你根本不知道是哪个依赖动了pin 到 commit SHA / 镜像 digest，锁定一切版本，升级走独立分支
LLM 不确定性同一份内容，今天渲染成功，明天代码跑不通产线不可重放，出问题无法复现LLM 只在内容层用一次，产物落盘成 JSON；渲染层完全不碰 LLM
渲染环境字体缺失、TeX 装不上、ffmpeg 编码器不一样换台机器就跑不了，"我这能跑"变成口头禅单镜像交付、字体内嵌、Typst 替代 TeX、固定 ffmpeg 版本

三个敌人里，LLM 不确定性是最容易被低估的。绝大多数"AI 视频工具"的失败不是因为效果不好，而是因为不可重放：这次成功了你很高兴，下次失败了你不知道为什么，第三次你就不想用了。

3.2 从 juya-news-card 拿走什么

资产拿走怎么用为什么值得
174 个主题模板是挑 6–8 个风格稳定的，剥成独立 HTML + CSS + 占位符这是它唯一的护城河。174 个里挑 8 个，够用一年不重样
audit-themes:strict 的契约思想是定义"一个模板必须接受哪些字段"，批量渲染才不会崩没有契约的模板库，加第 9 个模板时就会炸
内嵌字体 htmlFont.ttf是@font-face 本地引用，不走 CDN服务器没中文字体 → 截图全是方框，这是最高频的坑
Playwright 截图路径是无头 Chromium，deviceScaleFactor=2CSS 全部生效，比 satori/resvg 兼容性好得多
Next.js 应用 + /api/*否—为一个截图功能跑一个 Web 服务，是纯粹的负担
服务端 LLM 调用否改成离线一次性生成渲染时不该有网络请求，更不该有不确定性

一个具体的成本对比

跑它的方式：npm install + 起 Next 服务 + 装 Playwright 浏览器 + 配 .env 里的 LLM 三件套。约 800MB 依赖，常驻一个 Node 进程，每周还要担心依赖更新。

抽它的方式：8 个 HTML 文件 + 1 个 CSS + 1 个 TTF + 一段 30 行的 Playwright 脚本。约 15MB，无服务，无依赖更新。

产出完全一样。这就是"取资产不取应用"的实际差价。

3.3 从 ManimCat 拿走什么

ManimCat 的价值不在它的 Studio，在它解决的两个具体问题。这两个问题是所有想用 manim 做内容的人都会撞上的墙。

① Typst 替代 TeX

manim 默认走 LaTeX 渲公式，意味着镜像里要装 TeX Live——4GB 起步，中文字体还要额外配 ctex，经常配不对。ManimCat 用 Typst 做排版，镜像降到几百 MB，中文开箱可用。

这一条独立于 ManimCat 存在，可以直接搬到任何 manim 项目里。

② 渲染失败自动修补

manim 场景代码第一次跑通率很低（API 记错、坐标越界、字体缺失）。它的做法是渲染失败 → 抓 stderr → 回喂模型 → 重试，直到成功或超次数。

本方案不生成代码，但保留这个降级链：动效失败 → 换静帧 → 换纯色卡 → 记录并继续。

但动效这一层，我建议改一个根本性的做法

不要用 LLM 生成 Manim 代码

ManimCat 的 Agent 模式是"自然语言 → 生成 Python 场景代码 → 渲染"。这条路在演示里很惊艳，在周更产线里是灾难：同样的需求，今天生成的代码能跑，明天生成的多了个参数就崩。你无法保证第 12 期还能出片。

改成"固定模板 + 参数填充"

周报的动效其实是高度重复的：数字滚动、折线生长、柱状对比、地图高亮、时间轴推进。这五种覆盖 90% 的需求。

把它们写成 5 个参数化的 manim 场景（CounterScene(value, label, duration)），LLM 只负责输出参数 JSON。稳定性从"看运气"变成"看 schema 校验"，而且渲染时间可预测、可缓存。

# scenes/counter.py —— 参数化场景，不是生成出来的代码
class CounterScene(Scene):
    def __init__(self, value: float, label: str, fmt: str = "{:,.0f}", **kw):
        super().__init__(**kw)
        self.value, self.label, self.fmt = value, label, fmt

    def construct(self):
        num = DecimalNumber(0, num_decimal_places=0)
        num.add_updater(lambda m, dt: m.set_value(
            min(m.get_value() + self.value * dt / 1.2, self.value)))
        caption = Text(self.label, font="Noto Sans CJK SC").next_to(num, DOWN)
        self.play(FadeIn(caption), run_time=0.4)
        self.add(num); self.wait(1.2)

这 8 行代码替代了"让模型写 manim 代码"的整个环节。它不是更聪明，它是更可靠——而周更产线要的是可靠，不是聪明。

3.4 合成层：一条 ffmpeg 命令搞定 80%

卡片是静帧，动效是片段，两者要接成一条片子。不需要任何剪辑软件，filter_complex 就够：

ffmpeg -y   -loop 1 -t 6 -i cards/01.png   -i clips/counter.mp4   -loop 1 -t 5 -i cards/02.png   -i bgm.mp3 -i voice.wav   -filter_complex "    [0:v]scale=2112:-1,crop=1920:1080,         zoompan=z='min(zoom+0.0008,1.08)':d=150:s=1920x1080,         setsar=1[v0];    [1:v]scale=1920:1080,setsar=1[v1];    [2:v]zoompan=z='if(lte(zoom,1.0),1.08,max(1.001,zoom-0.0008))':d=125:s=1920x1080,         setsar=1[v2];    [v0][v1][v2]concat=n=3:v=1:a=0[vcat];    [3:a]volume=0.12[bg];    [4:a]volume=1.0[vo];    [bg][vo]amix=inputs=2:duration=first:dropout_transition=0[aout]"   -map "[vcat]" -map "[aout]"   -c:v libx264 -crf 18 -preset medium -pix_fmt yuv420p   -c:a aac -b:a 192k -movflags +faststart   master.mp4

三个细节决定成败：zoompan 的推拉幅度必须小（1.08 封顶，大了会晕）；setsar=1 漏了会导致某些播放器画面拉伸；-pix_fmt yuv420p 不加则 B站/微信可能黑屏。

3.5 分发层：平台差异必须变成配置，不能变成手工

平台画幅常用规格真正要注意的派生方式
B站16:91920×1080；封面 1146×717封面决定点击率；分区选错就没流量直接用 master + 封面模板
YouTube16:91920×1080；缩略图 1280×720章节时间戳（描述区）能显著提升完播master + 自动生成章节文本
小红书3:41080×1440；≤5 分钟首图即全部；文字要大到手机能看清卡片纵向重排，非裁切
抖音 / 视频号9:161080×1920；≤3 分钟前 3 秒定生死；需要单独剪一个"钩子"开头竖版重排 + 前 3 秒重组
知乎16:9 + 图文—文字稿本身是主体，视频是附属口播稿直接复用
公众号图文—需要长文 + 配图，不能只贴视频episode.json → 文章模板

9:16 不能靠裁切

把 16:9 中间裁一块变竖版，结果是字被切掉一半、卡片只剩中间一条。正确做法是换一套排版：卡片改成纵向堆叠，字幕上移到安全区（下 1/4 会被平台 UI 遮挡），标题字放大 1.5 倍。

所以渲染器要支持两种布局模式，而不是渲染完再处理。这也是为什么 episode.json 必须和布局解耦——同一份内容，两种排法。

04数据契约与幂等

4.1 episode.json：唯一事实源

{
  "id": "2026-W43",
  "title": "本周 AI 圈发生了什么",
  "duration_target": 420,
  "chapters": [
    {
      "id": "c1",
      "heading": "模型发布",
      "layout": "card",              // card | motion | quote
      "card": { "template": "minimal-dark", "title": "...", "body": "..." },
      "motion": null,
      "narration": "这周最值得说的是……",
      "assets": ["img/xxx.png"],
      "duration": 42
    },
    {
      "id": "c2",
      "heading": "成本对比",
      "layout": "motion",
      "card": null,
      "motion": { "scene": "bar", "params": { "values": [12, 5, 3], "labels": ["A","B","C"] } },
      "narration": "从成本上看……",
      "duration": 28
    }
  ]
}

layout 字段是这套设计的核心：它让"这一章用什么形式呈现"变成内容决策而不是渲染决策。渲染器只负责按 layout 找对应的渲染器，找不到就降级到 card。

4.2 三层缓存，让重跑几乎免费

层缓存 key失效条件省下什么
卡片 PNGhash(章节内容 + 模板名 + 尺寸)内容或模板变了每次重跑省 2–3 秒/张 × 20 张
动效片段hash(scene + params + 镜像 digest)参数或镜像变了省 10–60 秒/段，这是最贵的一环
平台派生hash(master 的 sha256 + profile)master 或 profile 变了省 3–5 分钟转码

三层缓存的共同点是key 里都包含"环境指纹"（模板版本、镜像 digest）。少了这一项，就会出现"我明明改了模板，出来的图还是旧的"——这种 bug 找一天都不一定找到。

4.3 lock.json：让三个月后的你能复现

{
  "image": "ghcr.io/you/weekly-render@sha256:3f2a...",
  "ffmpeg": "6.1.1",
  "fonts": { "cjk": "Noto Sans CJK SC 2.004" },
  "templates": { "juya": "a1b2c3d", "count": 8 },
  "llm": { "model": "gpt-4o-mini", "prompt_version": "v7" },
  "locked_at": "2026-10-21"
}

这个文件看起来是形式主义，但它是唯一能回答"为什么上个月能跑这个月不能跑"的东西。每次成功产出后自动写入，出问题先 diff 它。

可重放性100%同 episode.json + 同 lock.json，两次产出 md5 一致
镜像体积≤ 1.5 GBdocker images，验证 Typst 方案确实省了 TeX
冷启动可用新机器 30 分钟跑通拿一台干净机器，只按 README 操作
断更韧性连续 8 周真正的验收指标——前六条都是手段，这条才是目的

为什么把"连续 8 周"写进验收

技术指标全绿但第 5 周放弃的项目，比指标不达标但做了两年的项目价值低得多。周更产线的真实成本在第 6 周到第 12 周才显现——新鲜感过去了，工作量还在。

所以这一条要单独列出来，逼自己在第 4 周就问：我现在还想做第 9 期吗？如果不想，问题不在技术，在流程设计。

07风险与对策

风险触发条件影响对策
AGPL 传染把 ManimCat 代码并入自有服务并对公网提供必须开源整个服务只在本机/内网跑；产出视频不是衍生作品；如需对外，独立进程调用
上游停更ManimCat 作者已明说无长期维护bug 无人修只取已理解的思路，不取代码依赖；lock.json 锁死；每季度评估"还需要它吗"
LLM 生成不稳定依赖代码生成做动效某期出不了片固定模板 + 参数填充；schema 校验不通过直接降级静帧
字体缺失换机器/换镜像截图全是方框字体打进镜像 + @font-face 本地引用；启动时自检并报错
渲染占满机器并发跑多期机器卡死串行队列 + 夜间调度 + 单任务 CPU/内存上限
平台规则变动尺寸/时长限制调整派生产物不合规profile 是 JSON，改配置不改代码；每季度核对一次
内容同质化模板只用 2 个观众疲劳8 个模板轮换 + 每季度加 1 个；用 episode.id 做哈希轮换
素材版权引用他人图片/视频下架/索赔只用截图 + 自绘图表 + 官方新闻稿图；建立来源记录字段

08Day 0 启动清单

先做三个决定（一小时，但影响全局）

决定一
动效要不要
不要 → 只做卡片 + 推拉，2 周能上线。要 → 加 2 周。建议第一季先不要。
决定二
口播怎么来
真人录音（质量高、依赖你）／TTS（稳定、机械感）。建议先 TTS 跑通流程。
决定三
首发哪几个平台
建议只做 2 个（B站 + 小红书）。6 个平台是稳定之后的事，不是启动条件。

环境（半天）

  • Node 20+ / Playwright Chromium（只装 chromium-headless-shell，省 200MB）
  • ffmpeg 6.x 静态包，确认有 libx264 与 aac
  • Docker（动效阶段才需要）
  • 中文字体：Noto Sans CJK SC + 一个衬线体，装进系统字体目录

读代码（半天，只读不写）

看哪里看什么为什么
juya-news-card/src/templates/模板的数据结构约定、CSS 变量命名决定你的 8 个模板怎么抽、怎么共用一套变量
scripts/ 里的 batch 与 audit批量截图的并发控制、契约校验批量渲染的坑（内存、超时）他们已经踩过
ManimCat DockerfilePython 依赖、字体、Typst 怎么装这是最值钱的一页，直接决定镜像能不能压到 1.5GB
ManimCat 的 retry / patch 逻辑失败分类、重试上限、错误回喂你的降级链要照着这个设计

样片（一天，必须真做）

不要从"搭框架"开始，从做一条 60 秒的样片开始。选 3 条真实新闻，走完整条链：内容 → 卡片 → 合成 → 导出。这一天会暴露 80% 的设计问题，而且是在你还愿意改的时候。

最后一句

这两个 fork 最大的价值不是它们的功能，而是它们用真实代价换来的两个教训：juya 告诉你"模板是资产，应用是负债"；ManimCat 告诉你"渲染环境才是真门槛，不是模型"。

把这两条吃透，你甚至可以不用它们任何一个——但你做出来的东西会比直接用它们更耐用。
