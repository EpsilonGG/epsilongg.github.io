诊断：fork 动作是"收藏"，不是"开发"

13 个 fork、0 次提交、11 个与上游同 pushed_at——这不是在改代码，是在用 fork 当书签。问题在于 fork 会持续落后：GalTransl 已经落后一个月，context-infrastructure 落后两个月。真要用的那天，第一件事不是写代码，而是先 git pull upstream 解决冲突。

更实际的代价是信号污染：13 个 fork 让"最近更新"看起来每天都在动，但没有任何一行是自己的。用 pushed_at 判断活跃度的人会被误导。

02关键发现：X-Reader 和 X-rss 是同一套架构的两个半成品

2.1 分层几乎一一对应

层X-ReaderX-rss差异
编排app/runner.py（36 KB）app/pipeline.py + runner.py + bootstrap.pyX-rss 把"装配"和"流程"拆得更细
配置config/{loader,schema}.py（Pydantic）config/{loader,models,validator,defaults}.pyX-rss 有独立 validator
领域模型domain/models/{item,account,media,tweet,rss_item,youtube_item}.pydomain/models/{tweet,author,media,attachment,account,feed}.pyX-Reader 有跨源 NormalizedItem；X-rss 只有 tweet + feed
抓取providers/（nitter / rss / youtube / factory）providers/（多实例切换）X-Reader 源更多
解析parsers/（nitter_rss / nitter_html / rss / youtube / timeutil）parsers/X-Reader 多了 HTML 形态与时间工具
出口无 exporter 目录；RSS 输出标 ⛔ 未实现exporters/，产出 rss.xml这就是缺口
账本data/items/ + data/delivery/*.jsonl无投递账本这也是缺口

2.2 一句话概括

X-Reader
有账本，没 RSS 出口
把"见过/发过"两件事分得极清楚（items/ vs delivery/），支持失败补发、按输出独立记账。但 README 明确写着「生成 RSS 输出文件 ⛔ 未实现」。
X-rss
有 RSS 出口，没账本
能稳定产出可订阅的 rss.xml 并发布到 Pages，但没有增量与投递状态，重复运行靠的是"重新生成整份 RSS"。

所以 P0 不需要写新功能，只需要把两边各缺的一半接起来。这是整个方案里性价比最高的一步。

还有一条更关键的线索

X-Reader 的能力矩阵里两个 ⛔ 是：「生成 RSS 输出文件」和「AI 摘要 / 翻译」。而 EpsilonGG 整个账号的母题恰恰是"日文内容中文化"。也就是说，这个项目缺的两块，一块已经由隔壁的 X-rss 实现了，另一块正是账号主人最擅长的事。

03目标架构

在现有分层上加三个新层，不动已被冻结的契约。
┌─────────────── 采集（已有） ───────────────┐ │ providers/ X-Reader 三源 + VN-Interview 11 站 │ └────────────────────┬─────────────────────────┘ ▼ ┌─────────────── 归一化（已有，冻结） ─────────┐ │ NormalizedItem source_id + item_id 为身份 │ └────────────────────┬─────────────────────────┘ ▼ ┌─────────────── 存储与账本（已有） ───────────┐ │ data/items/*.jsonl 「见过吗」 │ │ data/delivery/*.jsonl 「发过吗」（按输出） │ └────────────────────┬─────────────────────────┘ ▼ ┌── 新增 ① exporters/（P0，从 X-rss 迁入） ────┐ │ rss.py → rss.xml ＋ data/delivery/rss.jsonl │ └────────────────────┬─────────────────────────┘ ▼ ┌── 新增 ② translations/（P1） ────────────────┐ │ 按 (source_id,item_id) 关联，不改主字段 │ │ 引擎：GalTransl / HDEG 术语表：glossary │ └────────────────────┬─────────────────────────┘ ▼ ┌── 新增 ③ publishers/（P2） ──────────────────┐ │ 聚合 manifest（GC 契约）→ 交给发布 skill │ │ 回执 + 回读 + 去重键 │ └──────────────────────────────────────────────┘

为什么是"加"而不是"改"

X-Reader 有一份 docs/ARCHITECTURE_FREEZE_V3.md（44 KB）——文件名里的 FREEZE 说明作者已经做过一次架构冻结。NormalizedItem 的 12 个字段和"推送格式不进模型"的原则就是冻结内容。新加的三层全部是旁挂：exporter 读 items/，translations 用外键关联，publishers 消费聚合结果。任何一层挂掉都不影响已有链路。

05P1：加翻译态（约 2 周）

5.1 设计原则：不污染主模型

X-Reader 自己定了两条规矩：「时间不猜」和「推送格式不进模型」。翻译同属"派生信息"，所以不能往 NormalizedItem 里塞 title_zh、content_zh——那会让原文和译文在同一个结构里纠缠，也无法记录引擎版本。

data/
├── items/                    ← 原文（不动）
│   └── x.jsonl
├── delivery/                 ← 投递账本（不动）
│   ├── telegram.jsonl
│   ├── qq.jsonl
│   └── rss.jsonl             ← P0 新增
└── translations/             ← P1 新增
    └── zh/
        └── x__12345.json     ← 文件名 = source_id + "__" + item_id
{
  "source_id": "x",
  "item_id": "12345",
  "target_lang": "zh",
  "title": "……",
  "content": "……",
  "engine": "galtransl+deepseek",
  "glossary_version": "2026-10-21",
  "status": "ok",              // ok | partial | failed | skipped
  "translated_at": "2026-10-21T22:00:00Z",
  "terms_hit": ["柚木かなめ", "ゆずソフト"]
}

这样做的三个好处：① 原文永远可回溯；② 换引擎可以整批重跑而不动原文；③ terms_hit 让术语表命中率变成可统计的指标。

5.2 术语表：这是 Galgame 翻译的真正门槛

报告 01 里提到 GalgameCriticism 的周报必须用「去注音」版 docx，因为原始稿的 【注音】 会漏进正文——这说明团队内部有一个手工标读音的工序。翻译流水线会把这个痛点放大十倍：作品名、声优名、厂商名、角色名，每一个都可能被译错。

来源提供什么怎么用
GalTransl（★2353）成熟的 glossary 机制 + 多后端（GPT/Claude/Deepseek/Sakura）直接复用它的术语表格式，不自己发明
HDEG（★27）以官方台本为基准校正 ASR、术语统一、多模型翻译处理 YouTube / 音声类内容（X-Reader 的第三类源）
accentjiten_anki（TianSalt）日语重音词典 → 结构化条目抽出"词 → 读音"层，给术语表补注音字段
NarouDownloader成为小说家吧的日文文本源术语表的语料来源之一

一个诚实的限制

accentjiten 是通用日语重音词典，不是 Galgame 专有名词库。它解决不了"ゆずソフト 该译成柚子社还是 Yuzu-Soft"，只能提供读音标注的格式与工具链。术语表本身仍然要人工建——但建一次就能复用，这是从"每次手工注音"到"资产化"的关键一步。

5.3 验收标准

  • 同一条 item 有原文 + 译文两份，原文不被改写
  • 翻译失败时原文照常投递（status: failed 只影响译文出口）
  • 术语命中率可统计，未命中词进 glossary_todo
  • 换引擎重跑不产生重复条目

06P2：接发布端（约 1 周，先只做"生成 manifest"）

这一步不自己写发布逻辑，而是产出一份符合 GalgameCriticism 契约的素材包，交给现成的 skill 去发。

聚合 manifest

{
  "source": "x-reader",
  "source_id": "weekly-265",
  "canonical_url": "https://...",
  "title": "本期 Galgame 情报速递",
  "blocks": [ /* 由若干 NormalizedItem + 译文组成 */ ],
  "images": [ { "local": "images/001.jpg", "origin": "https://...", "sha256": "..." } ],
  "author": "……",
  "published_at": "2026-10-21T00:00:00Z",
  "manifest_sha256": "……"
}

字段名与 weekly-cross-platform-sync 的 manifest 契约完全一致，所以可以直接喂给：

  • bilibili-weekly-article（转成 article.json 走图文排版）
  • zhihu-weekly-sync / weibo-weekly-sync / xiaoheihe-weekly-sync（跨平台搬运）

去重键对齐

用 GC 的规范：source + source_id + target_account + target_scope + content_type。X-Reader 已经有 delivery/ 这套按输出记账的机制，只需把"输出"从 telegram/qq/rss 扩展成 bilibili/zhihu/weibo/xiaoheihe，结构完全复用。

不要在这一步做自动发布

报告 01 已经证明：四个平台适配器全部依赖真实浏览器会话 + 扫码，且各自的坑被穷举了 14 条。EpsilonGG 的强项是数据与翻译，不是浏览器自动化。正确做法是产出 manifest 就停，把发布交给已经有 264 期实证的那套 skill，人来做审核闸门。

08搬过来的 6 条可用性做法

这部分是从 GalgameCriticism-skills 直接借的，也是"融合可用性工作"的实质内容。

① 契约先行，中间产物落盘

GC 的每一步都留一个可检查的中间文件：article.json、manifest.json、*_receipt.json。X-Reader 已经有 items/ 和 delivery/，P0/P1 要延续这个习惯——translations/ 和 manifest.json 都落盘，不进内存。好处是任何一步失败都能从中间产物续跑。

② 回执 + 回读，公开链接才算成功

GC 规定：草稿、编辑器、本地路径不能填在"成功"位置；没有回读通过只能标 submitted / pending_review / unknown / failed。X-Reader 的 delivery 状态只有 sent / failed / skipped，可以对齐成同一套语义，让两个系统的报告能拼在一起看。

③ 去重键要写进文档

GC 用 source + source_id + target_account + target_scope + content_type。X-Reader 用 source_id + item_id。两者可以合并成一条链：内容身份（前者）+ 分发身份（后者），写进 README，避免以后每次加平台都重新想一遍。

④ 人工闸门要显式标注

GC 的 bilibili skill 把"人工审核"写成第 3 步，且注明"必做，不可跳过"。这是很好的示范——把人的位置画进流程图，而不是假装全自动。EpsilonGG 的流水线也该在 manifest 之后插一个"人工确认译文"的闸门。

⑤ 仓库级规则文件

GC 有一份 AGENTS.md，规定目录同步、提交前脱敏扫描（用户名路径、令牌、Cookie、浏览器配置）、发布约定。X-Reader 的 README 已经很长（94 KB），但缺一份"给 agent 的短规则"。建议单独加 AGENTS.md，只写约束不写教程。

⑥ 双文档：面向人的 README + 面向 agent 的 SKILL

GC 每个 skill 都有两份文档，分工明确：README.md 讲"这是什么"（含流程图），SKILL.md 讲"怎么执行"（含命令与边界）。X-Reader 把两者混在 94 KB 的 README 里，新人能看懂但 agent 抓不住重点。拆开后两边都更好用。

一句话总结这个方案

不新造系统，只做三件事：把 X-rss 的出口接进 X-Reader（P0）、给已冻结的数据模型旁挂一个翻译层（P1）、产出符合别人契约的 manifest 交给成熟发布端（P2）。同时把 13 个零提交的 fork 砍到 5 个，让"最近更新"重新变得可信。

本报告基于 2026-10-21 抓取的 EpsilonGG 全部 17 个公开仓库：4 个原创（X-Reader、X-rss、VisualNovel-Interview-RSS、whirlpool_blog_archive）与 13 个 fork。
fork 状态通过 /repos/{owner}/{repo} 的 pushed_at 与 parent.pushed_at 逐一比对确认；X-Reader 的能力矩阵、NormalizedItem 字段、items/ 与 delivery/ 机制均引自其 README 原文。
方案中的文件路径与改动点基于仓库现有目录结构推导，实施前需在本地验证。
