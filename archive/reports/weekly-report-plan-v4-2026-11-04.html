0. 这一版改了什么

  1. 加业界栏，但它不能靠 X 自动生成。严格口径实测：14 天 2,370 条里只召回 3 条，2 条是噪音（自家众筹进度、DLsite 促销），1 条是 6 年前发售回顾。X 上真正的业界新闻接近 0——厂商官方号只发自家作品，破产、并购、讣告不会在自己号上宣布，名单里也没有行业媒体。所以这一栏初期以人工增添为主，RSS 召回为辅。
  2. 取消 12 条硬线，改成分档勾选：A 档必收、B 档建议、C 档备选，条数由档位截断决定，不写死数字。判卷从「等于 12」改成区间校验。
  3. 背景段改成三级降级，而不是「VNDB 查到就写」。实测发现 61% 的新作条目链接是 nitter 镜像（nitter.cf / nitter.meowing.monster），官网 URL 根本拿不到，所以「VNDB + 官网」这条校验链是断的，得换成「官方 X 号自证」。
  4. 月报固定在每月最后一个周日，窗口是「上月最后周日 + 1 → 本月最后周日」，28–35 天浮动。12 月天然落在圣诞后一两天（2026 是 12-27，+2 天），但 2028 年会漂到 12-31（+6），需要一条兜底。
一句话结论：新作栏的自动化是「挑」，业界栏的自动化只能是「找」。 前者 208 条里挑 12 条，规则能做完 90%；后者 14 天只有 3 条噪音，机器判不了「这件事重不重要」， 只能把候选摊开给人看。两栏的人工成本差 10 倍，不该用同一套流程。

1. 两栏形态

栏目条数数据来源自动化程度人工
新作资讯8–14 条（弹性，按分档截断）X 抓取（data/xreader/galgame/）聚合 / 分类 / 排序 / 去重 / 档案 / 配图 / 写稿 / 判卷 / 封面全自动勾选 + 修稿，约 8 分钟

两栏的顺序固定：新作在前、业界在后。理由是新作栏是「本周发生了什么」的事实部分，业界栏是「这周有什么值得说的」，后者需要前者做语境。原站的「周边信息」放在最后也是这个逻辑，只是我们用业界替掉了它。

2. 业界栏：召回容易，判定难

2.1 实测：X 上几乎没有

用最严格的口径跑了一遍：文本命中名单内 170 个制造商名 + 命中行业级动作词（设立 / 解散 / 并购 / 人事 / 讣告 / 众筹 / 诉讼 / 市场统计 / 协会 / 中止）+ 排除营销词（ご支援 / ご予約 / キャンペーン / セール / 抽選 …）。14 天 2,370 条里只剩 3 条：

来源命中实际是什么
kiss_staffクラウドファンディング自家众筹第 2 弹延长目标，博客更新通知
Moepedia_net創業DLsite 创业祭打折广告
youtan0309設立6 年前发售回顾，讲的是作品里的社团设立

把口径放宽（去掉「必须命中制造商名」）能召回 78 条，但第一条就是「キュアメイドカフェ 预约无需排队」、第二条是「Sunrise 被万代收购的动画产业采访」——精度不到 10%。放宽召回换来的不是覆盖，是噪音。

为什么会这样：① 厂商官方号只发自家作品，行业级消息发在媒体号和编辑个人号上；② 名单 185 个号里没有一家行业媒体；③ 破产、并购、讣告这类消息，当事方通常不首发在 X，而是官网公告或媒体爆料。

RSS 这条最值得做，因为它是标准协议，scripts/rss_to_items.py 已经存在。但要注意：这三家是综合游戏媒体，galgame 相关可能只占 10–20%，需要在入库时就用名单和关键词筛一遍，否则一周 189 条会把候选列表淹掉。

2.3 人工增添怎么落

人不需要碰 Markdown，只在 candidates.json 里加一个对象：

{
  "section": "industry",
  "manual": true,
  "title": "Nitroplus 官方商店闭站重建，11 月下旬重开",
  "summary": "官方公告称现有系统难以修补 PHP 漏洞，站点全面改修。",
  "source_url": "https://nitroplus.co.jp/company/info/",
  "source_handle": "nitroplus_staff",
  "date": "2026-11-02",
  "picked": true
}

四个字段必填：title（≤ 40 字）、summary（80–200 字）、source_url、date。source_handle 可空——很多消息来自官网而不是 X。

人工写的内容不过 LLM。这一栏的价值就在判断，让模型润色会引入它自己编的因果。只做两件机器检查：字数区间、source_url 可达（HEAD 200，或域名在白名单内）。

2.4 空栏怎么办

允许 0 条，不渲染「本周无业界动态」。原站汉化栏 15 期里有 2 期整栏缺席，做法就是标题都不出现。业界栏的缺席率会更高——按 X 的实测，不人工补的话基本每周都空。

3. 选材：分类 → 排序 → 去重 → 人筛

四个步骤全部在出题之前完成，人看到的是一份已经分好栏、排好序、去过重的列表。机器负责到「候选」，人负责「收不收」。

① 分类
按主语分两路。作品主语（『作品名』+ 动作）→ 新作栏； 主体主语（公司 / 品牌 / 人 / 行业）→ 业界栏。两路的抽取规则不同：前者抽书名号，后者抽名单内的制造商名与固定动作词。
② 排序
每栏一套权重。新作栏看动作权重 + 来源数 + 是否官方号 + 有无日期；业界栏看动作类型（讣告 / 并购 / 解散 > 众筹 / 人事 > 展会 / 统计）+ 是否首发 + 媒体是否跟进。
③ 去重
两层。栏内去重：同一作品同一动作的多条来源合并成一条（43% 的事件有 2 条以上来源）。 跨期去重：state/reported-events.json，指纹 sha1(归一化主语 + 动作)，锁 8 周。
④ 人筛
分档勾选，不设死线。A 档（必看，默认全收）/ B 档（建议）/ C 档（备选）。 人在 candidates.json 里改 picked，可增可删。

3.1 分档规则

档进入条件默认状态说明
Ascore ≥ 14，或「本周发售」+ 官方号首发全选漏掉会明显缺内容
B8 ≤ score < 14按 score 降序取前 6篇幅够就多收
Cscore < 8不选，折叠显示人想补冷门时翻

这样条数自然浮动：淡周 A 档可能只有 4 条，B 档补到 8；旺季 A 档就 12 条，直接 12 条不加 B。没有「必须 12 条」这回事，但也不会掉到 3 条——A 档兜住了下限。

3.2 判卷改成区间

检查项v3（死线）v4（区间）
新作栏条数= 126 ≤ n ≤ 18
业界栏条数—0 ≤ n ≤ 6
总条数= 126 ≤ n ≤ 22
总字数2,000–3,0001,200–3,600（按条数比例算，不写绝对值）
低于下限判失败告警但放行，标注「短周」

「短周放行」很重要：原站期与期浮动 3.4 倍，最小的一期只有 14 条三栏合计。硬性下限会逼着模型凑数，凑出来的必然是废话。

4. 背景段：三级降级，过不了就不写

原方案是「查 VNDB，查到就写」。实测发现两件事，把这条链打断了：

  • VNDB 标题匹配只有 58% 精确（12 样本：精确 7、前缀可救 3、错配 2）。错配的两个都是「短名 + 新作」，VNDB 按热度排把老作顶上来。
  • 官网 URL 拿不到。新作类条目 61% 带链接，但域名全是 nitter.cf / nitter.meowing.monster 镜像，不是官网。原文里提到「株式会社 / ブランド / より発売」的只有 3%。

所以校验源只能是发布这条消息的账号本身。改成三级：

级别条件能写什么覆盖率（估）
L0 自证来源账号是名单内的该厂牌官方号（category: manufacturer 且 handle 对应）厂牌名、发售日、平台——全部可写约 45%
L1 双源来源是信息号（bugbug / Moepedia / Getchu），且 VNDB 厂牌与原文表述归一后相等厂牌 + 发售日（相差 ≤ 7 天）约 30%
L2 单源只有 VNDB 能对上，或标题靠前缀猜的什么都不写，只写事件本身约 25%

L0 是这次的关键发现：如果消息就是厂牌自己发的，厂牌不需要外部校验——名单里那条记录的 name 就是答案。这比查 VNDB 可靠得多，也解释了为什么 L0 能覆盖近一半。

4.1 归一与一致性判定

归一：NFKC → 去空格 → 全角括号转半角 → 波浪号统一（～/~）→ 去「株式会社」「有限会社」前缀 → 小写
厂牌一致：归一后相等，或一方是另一方的前缀且长度 ≥ 4
发售日一致：相差 ≤ 7 天（VNDB 记的是首发日，主机版可能不同）
标题命中：归一后相等，或 X 名是 VNDB 名的前缀且长度 ≥ 6，或命中 aliases
日期窗口：VNDB released 必须落在事件日期 ± 18 个月内

「发售日相差 ≤ 7 天」而不是「相等」，是因为 VNDB 记 PC 首发日，Switch 版可能晚一周。超过 7 天就是两个不同的发售，不能合并。

4.2 不写背景段会长什么样

L2 的条目只有一句事件 + 一句补充，比原站的「三段式」薄。这是刻意的取舍：写错厂牌（比如把 ワンナイトアフター 标成 Lover Able 的开发商）比写短严重得多，而且读者不会去核。

5.2 12 月兜底

「最后一个周日」在 12 月并不总是落在圣诞后一两天。查了 2026–2035：

年份最后周日距圣诞处理
202612-27+2采用
202712-26+1采用
202812-31+6提前 7 天 → 12-24
202912-30+5提前 7 天 → 12-23
203012-29+4提前 7 天 → 12-22
203112-28+3采用（边界）

规则：12 月若最后周日晚于 12-28，则提前 7 天。提前而不是推后，是因为推后会跨到下一年 1 月，而当月发售已经结束，等于漏掉整月商战。提前到 12-22～12-24 能覆盖圣诞前的发售高峰（galgame 多在本月第 3–4 个周五发售）。

6.2 单期流程（周报 / 月报共用）

# ① 机器：聚合 + 分类 + 排序 + 去重 + 召回业界候选（无 LLM）
python scripts/weekly_prepare.py --week 2026-10-26
#    月报用 --month 2026-11，自动算窗口与期号

# ② 机器：VNDB / Steam 取档案与图，做三级降级判定
python -m weekly dossier --issue 261101-w

# ③ 人：打开 out/261101-w/candidates.json
#    · 新作栏：A 档已全选，B 档挑几条，可取消
#    · 业界栏：审 20–30 条召回候选；或直接手写 manual 条目
#    · 勾完把 picked 数量记下来（不强制等于某个数）

# ④ 机器：出题（只包含被勾中的条目）
python -m weekly prompt --issue 261101-w

# ⑤ 机器写稿 → 人修稿 → 判卷
python -m weekly apply --issue 261101-w --answer out/261101-w/answer/all.json

# ⑥ 定稿 → 封面（月报加一览图）→ 发布
python -m weekly confirm --issue 261101-w
python -m weekly publish --issue 261101-w
python scripts/push_site.py --path data/weekly/ --path public/images/weekly/

与 v3 的差别只在第 ② 步（档案与降级判定独立成一条命令）和第 ③ 步（两栏分档勾选，业界栏可手写）。人的动作只有一处：改 candidates.json，其余全是命令。

9. 需要你拍板

  1. 业界栏初期靠手写，能接受吗。按 X 的实测，不手写的话这栏每周都空。手写成本 2–3 分钟/条，一期 1–3 条。如果不想手写，M5 的 RSS 就得提前到 M1。
