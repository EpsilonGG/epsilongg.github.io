周报 v3：单栏起步，先跑通 X 能支撑的部分

按四条拍板收敛形态：不做周边栏、一览图只在月报带字、封面与正文不出现量化信息、 汉化栏留占位不补数据。周报因此从「三条栏」变成「一条栏 + 两个空壳」， 一次性投入降到 14 人日，但选材与跨周去重成了新的主要难点。

0. 这一版改了什么

四条决定都落到了具体位置上，不是删功能，是改形状：

  1. 不做周边栏 → 少 11.7 条/期、少约 20 张图，也少掉唯一没有图源的一栏。周报的图片瓶颈随之消失。
  2. 一览图只在月报带字 → 常规周报不做一览图，月报做一张带编号的对照图。省掉每周一次拼版，但月报需要跨 30 天窗口，而 data/xreader/ 只保留 14 天，保留期必须放宽到 40 天。
  3. 封面与正文不出现量化信息 → 不写「22 条 / 43 图」，短周不会显寒酸，也免掉一个统计口径。
  4. 汉化栏占位不补全 → 栏目、schema、适配器接口都留好，enabled: false，不进题面、不进渲染、不进判卷。
新发现：周报有日报不存在的问题——跨周重复。 279 个事件里，241 个只出现在 1 周，31 个横跨 2 周，7 个横跨 3 周。也就是约 14% 的事件会在两周以上的时间窗里反复被同一个人发推（体验版公告连发、PV 二投、发售倒计时）。 日报按日期切窗天然不会重复，周报不做「已报道事件」状态就会连着两周报同一件事。

单栏之后有一个副作用值得注意：原站「新作资讯」这个 h2 是为了分隔三栏才存在的。只剩一栏时，栏目标题变成纯噪音，正文直接从第一条开始。这也意味着页面模板要能处理「零个栏目」的情况，不能硬编码三个 h2。

2. 选材：208 挑 12

这是 v3 最大的工程变化。v2 假设「事件聚合完就差不多能用了」，实测不成立：一个完整周有 208 个事件，要挑出 12 条，淘汰率 94%。原站靠 9 个人挑，我们得靠规则挑。

2.1 动作分布

动作事件数/14 天占比说明
release15054%发售、定档、配信开始。含「今天发售」的复述
op_pv8229%OP、PV、宣传片、试听动画
master_up228%装盘完成，进量产
port124%主机版、移植、Switch/PS5
trial104%体验版公开
announce31%新品牌、制作决定。关键词收得最紧

delay（延期）在这 14 天里是 0 条——不是没有延期，而是延期公告几乎都同时含「発売日」，被 release 吞掉了。这说明动作判定不能是「命中即归类」的多标签，必须定优先级：delay > master_up > trial > port > release > op_pv > announce。

2.2 排序信号

规则先排，人只做减法。打分项全部来自已有字段，不需要新数据源：

信号权重取值方式
动作权重+10 / +8 / …release 10、master_up 8、trial 7、port 6、op_pv 5、announce 4
来源数+3 × log₂(1+n)多个号同时发同一事件 = 重要。43% 的事件有 2 条以上
官方号+2role == manufacturer 且 handle 属于该作品厂牌
有日期+1.5正则命中「N 月 N 日」或「N 年 N 月」。仅 40% 有
有价格+1仅 5%。几乎可以忽略，但不能给负分
本周内新−5事件首次出现早于本期窗口起点
已报道−∞命中 state/reported-events.json 直接排除

输出 candidates.json（按分数排序的 30 条，每条带 1–3 个来源原文），人在这 30 条里勾 12 条。这就是 v2 里的「编辑台 W4」，只是候选从 190 条降到 30 条，勾选时间从 30 分钟降到 8 分钟。

2.3 跨周去重

事件指纹 = sha1(归一化作品名 + 动作)。发版时写进 data/weekly/state/events.json，格式与日报的 state.py 一致（记录首次报道期号 + 最后出现时间）。

{
  "261101-w": {
    "reported_at": "2026-11-02T00:31:12+08:00",
    "events": {
      "9f2c1a…": { "work": "廃村少女［弐］ 外伝", "action": "release", "issue": "261101-w" }
    }
  }
}

两个细节：① 指纹只锁 8 周，之后自动失效（复刻版、再贩要用同一个作品名）；② 同一作品的不同动作是不同指纹，所以「上周发体验版、这周发售」能正常出两条。

3. 占位：汉化与周边怎么留口子

占位不是注释掉一段代码，是让空壳在每一层都合法。具体四层：

3.1 数据结构

{
  "issue": { "id": "261101-w", "kind": "galgame", "window": { "start": "2026-10-26", "end": "2026-11-01" } },
  "sections": {
    "new_releases": { "enabled": true,  "source": "x",   "items": [ … ] },
    "localization": { "enabled": false, "source": "bbs", "items": [] },
    "goods":        { "enabled": false, "source": "x+shop", "items": [] }
  }
}

enabled: false 的栏必须存在且形状合法，但不进题面、不进渲染、不进判卷。以后打开只改一个布尔，不用动 schema。

3.2 数据源接口

class Source(Protocol):
    name: str          # "x" / "bbs" / "shop"
    section: str       # "new_releases" / "localization" / "goods"
    def fetch(self, window: Window) -> list[Event]: ...

class XSource:      # 已实现，读 data/xreader/galgame/*.jsonl
class BbsSource:    # 占位：贴吧 / 绯月，M6 再做
    def fetch(self, window): raise NotImplementedError("汉化栏数据源未接入")

接口先定，是因为汉化栏的数据形状和 X 完全不同：BBS 是帖子 + 楼层，不是推文 + 作者。要抽的字段是「作品名 / 汉化组 / 版本（汉化补丁 / 官中 / 民间整合）/ 发布形态（补丁 / 硬盘版）/ 原帖链接」，没有一个是 X 的字段能映射的。如果等到做的时候才定接口，Event 结构会被迫返工。

3.3 渲染

页面模板按 enabled 过滤后再渲染，不渲染「本周无汉化情报」这种占位文案。原站 15 期里有 2 期整栏缺席，做法就是标题都不出现——照抄这个。

3.4 判卷

validate.py 只校验 enabled: true 的栏的条目。空壳栏只校验「键存在、items 是空数组」，避免以后打开时才发现形状不对。

4. 事实层：VNDB 只能当参考，不能当答案

新作栏的背景段（厂牌、剧本、原画、原发售日）是原站每条必写的。v2 假设「查 VNDB 就行」，实测 12 个样本：

结果数量例子
精确命中7廃村少女［弐］ 外伝、小金井荘と金色の揚羽蝶、さくらぶトライアングル
前缀可救3養花師の背徳愛（X 写短名，VNDB 带副标题）、ハイアングル、西園家のかくしゴト
错配2ワンナイトアフター → 命中 2011 年的 Lover Able；マブラヴ：ディメンションズ → 命中 Muv-Luv Alternative

错配的两个都是「短名 + 新作」，VNDB 按热度排就把老作顶上来。所以匹配必须过三道闸：

  1. 标题归一：NFKC、去空格、去波浪号差异（～ / ~）、去全角括号差异。
  2. 前缀或别名：X 名是 VNDB 名的前缀（长度 ≥ 6 字）才算命中，或命中 aliases。
  3. 发售日窗口：VNDB released 必须落在「事件日期 ± 18 个月」内。这一条能挡掉两个错配——Lover Able 是 2011 年，差 15 年。

三道都过不了就不写背景段，只写事件本身。这比写错厂牌好。另外实测 developers 字段 6/12 为空，厂牌要走 /release 的 producers 取，不要指望 /vn 的 developers。

5.2 一览图（仅月报，带字）

常规周报不做一览图。月报（每月第一周那期）做一张带编号的对照图：

  • 3 列网格，每格：01 编号 + VNDB 封面（3:4 裁切）+ 中文名（两行）+ 厂牌 + 发售日。
  • 编号与正文条目序号一致，正文里写「见图 01」就能对上。
  • 数据全部来自 dossier.json，不额外请求。

原站那张图只解决「一眼看到有哪些新作」，不解决「哪部是哪部」——没有编号、没有名字、尺寸每次都不一样（1192×1548 到 2436×1838）。这是我们唯一有结构性优势的图，值得做好。

月报的前置条件：data/xreader/ 只保留 14 天，月报要 30 天。保留期必须改到 40 天（约 2,300 → 6,600 条，JSONL 从 3 MB 涨到 9 MB，可接受）。这是 M4 的硬前置。

7. 工作流

核心原则：周报是日报管线的第二个 kind，不是第二套管线。model.py / roster.py / adapters/ / state.py / validate.py / publish.py 全部复用，只新增事件层与选材层。

7.1 五个命令

# 1. 聚合 + 打分，出 candidates.json 与 prompt（无 LLM）
python scripts/weekly_prepare.py --week 2026-10-26

# 2. 人勾选：改 out/261101-w/candidates.json 里的 picked: true（12 条）
#    也可以用 --pick 1,4,7,12,... 一次性给

# 3. 写稿后判卷合并
python -m weekly apply --issue 261101-w --answer out/261101-w/answer/all.json

# 4. 定稿
python -m weekly confirm --issue 261101-w

# 5. 发布（封面自动生成）
python -m weekly publish --issue 261101-w
python scripts/push_site.py --path data/weekly/ --path public/images/weekly/

与日报的 daily build → prompt → apply → confirm → publish 完全对称，只是把 build 拆成 weekly_prepare（聚合）+ 人工勾选（pick）。

8. 判卷

闸门查什么失败处理
L1 结构条目数 10–12、每条第 1 段 ≥ 40 字、总字数 2,000–3,000、sections 三个键齐全整份退回
L2 来源每条 sources 里的 handle 必须在 candidates 里出现过，URL 域名白名单整份退回
L3 事实文本里的日期、价格、版本数、厂牌名，必须能在 sources 原文或 dossier 里逐字找到按条拒收，其余照发
L4 图片每张图有 source_url、最短边 ≥ 600、sexual == 0、pHash 不与本期已有图重复按条拒收

L3 的「按条拒收」是关键：周报 12 条，掉 1 条还能发；整份作废会让人不想跑。日报做不到按条拒收是因为它是「一个人一段」的连续叙事，周报每条独立，天然可以拆。

10. 需要你拍板

  1. 期号用周日还是周一。我建议周日（261101-w），与日报「被覆盖的那一天」口径一致；代价是发布时刻在周一凌晨。
  2. 声优版周报做不做。X 能支撑，但声优的事件单位是「人 × 活动」，不是「作品 × 动作」，events.py 要再写一套。建议 M4 之后再定。
  3. 勾选这一步要不要留。留，质量最好，但每周 8 分钟人工；不留，全自动，但 94% 的淘汰率完全交给规则，会漏掉重要的冷门作品。我倾向留，至少前 8 周留。
一句话总结：砍掉两栏之后，周报的难点从「素材从哪来」变成了「208 条里挑哪 12 条」。 M1 要解决的是选材，不是写稿——写稿这一层日报已经证明可行。
