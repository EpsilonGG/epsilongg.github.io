周报 v5：预览版先行，全览复核，未选即发布

把「人必须勾选」改成「机器先出一份能直接发的预览版，同时给一份带编号的全览」。 人不操作就发预览版，操作了只重写变动的那几条。分数线退居为排序器，不再是需要理解的概念。 月报取消 12 月兜底，固定每月最后一个周日。

数据基线同 v4：data/xreader/galgame/ 2,370 条、208 事件/完整周、业界严格召回 3 条。
新增设计：两阶段产出、decision.json 增量重写、全览清单编号、08:00 兜底发布。
写于 2026-11-04，取代 v4（weekly-report-plan-v4-2026-11-04.html）。

0. 这一版改了什么

  1. 人从「必须勾」变成「可以不管」。机器先按默认规则出一份完整预览版（已写稿、已配图、已过判卷），同时生成一份带编号的全览清单。人不操作，08:00 自动发预览版；操作了，只重写变动的那几条。
  2. 分数线退居为排序器。你不需要理解 A 档 ≥ 14 是什么意思——它只决定「预览版默认选哪些」和「全览里怎么排」。你只需要看全览里的编号，说「加 23、41，去掉 7」。
  3. 月报取消 12 月兜底。就是每月最后一个周日，2028-12-31 就发 12-31，不管距圣诞几天。
一句话结论：这一版把「人工判断」从流程的必经环节降级为可选的优化环节。 代价是多一次增量重写，收益是这周忙的时候周报照样能发出去——而不是因为没人勾选就断更。

1. 两阶段流程

00:30 准备
聚合 → 分类 → 排序 → 去重 → 编号冻结。出 candidates.json，每条带一个稳定的编号（E01–E30 / I01–I20）。 同时按默认规则填好 picks：A 档全选、B 档取前 6。
00:35 档案
VNDB / Steam 取档案与图，做三级降级判定。只对 picks 里的条目请求，避免 30 条全查。
00:40 写稿
出预览版。LLM 只写被 pick 的条目 → report.json（状态 preview）→ 判卷 → 封面。 这份文件此时已经可以直接发布。
00:45 全览
出 overview.md。本周全部候选按编号列出，已选的打 [x]、未选打 [ ]。 周报列 A+B 档（约 40 条），月报列 A+B 档（约 60 条）并折叠 C 档。
00:45–08:00
人的窗口。看 overview.md，要么回一句「加 23、41，去掉 7」，要么直接改 decision.json。不操作也没关系。
08:00 定稿
检查 decision.json。不存在 → 发布预览版。
存在 → 增量重写（只写新增的、移除取消的、保留已写的不动）→ 判卷 → 发布。

关键点：预览版在 00:45 就已经是完整可发布的成品，不是草稿。全览复核是「优化」，不是「补齐」。这样任何一天出问题（没人看、模型挂了、人不在），最坏结果是发出一份按规则选好的周报，而不是断更。

1.1 兜底判定的实现

不引入额外状态机，就看一个文件存不存在：

# scripts/weekly/decide.py
def resolve(ws: Path) -> Path:
    d = ws / "decision.json"
    if d.exists():
        return rerun_incremental(ws, d)   # 增量重写
    return ws / "report.json"             # 预览版原样

这样人也可以「先写 decision 但故意不改任何东西」来强制走一遍重写，便于测试。

2. 全览清单

给人看的东西必须能一眼扫完，所以只有四列：编号、标题、来源、当前状态。分数、档位、指纹全部收起来——它们只在排序时用过一次。

人的回复只要一句话：「E04 加上，E07 去掉，I02 不要」。编号是冻结的，所以隔一天再回也对得上。

2.1 编号为什么必须冻结

编号在 00:30 生成候选时就写进 candidates.json 的 no 字段，之后任何一次重跑都不重算。原因有两个：

  • 人会隔天才回。如果编号随分数重排，昨天的「加 23」今天就指向别的东西了。
  • 增量抓取会插新条目。周报窗口内如果 CI 又补抓了一批，新条目排在末尾拿 E31 起，不打乱已有编号。

编号规则：新作栏 E + 两位序号（E01–E99），业界栏 I + 两位序号。月报候选多，用三位（E001）。

2.2 月报的全览会长很多

月报窗口 28–35 天，事件量约 600–800 个。全览不能全列，否则人根本扫不完。所以：

档周报全览月报全览
A全列（约 10 条）全列（约 20 条）
B全列（约 30 条）只列前 40 条
C折叠成一行计数折叠成一行计数
合计可见约 40 行约 60 行

60 行是上限——超过这个数，人就不看了，直接放行预览版，全览就白做了。

3. 增量重写

预览版已经写了 12 条，人又加 3 条、删 2 条。三种处理方式，选第三种：

方式做法问题
全量重写13 条全部重新写慢、贵，而且会冲掉人手工改过的句子
只写增量新增的 3 条单独写删除的 2 条还留在文件里，需要手工删
增量 + 差量合并新增写、删除移除、保留不动采用
 
def rerun_incremental(ws, decision):
    report = load(ws / "report.json")
    for sec, d in decision["sections"].items():
        keep = [it for it in report["sections"][sec]["items"] if it["id"] not in d["remove"]]
        fresh = write_items([c for c in candidates if c["no"] in d["add"]])   # 只调这几条
        report["sections"][sec]["items"] = reorder(keep + fresh, candidates)
    report["revision"] = report.get("revision", 1) + 1
    return report

revision 每次重写 +1，页面上不显示，但发布时写进 issue.revision，便于事后查「这期是不是人改过」。

3.1 保护人工修改

每条带一个 edited_by_human: true 标记。人改过的条目在重跑时即使落在 remove 里也不删，只在末尾留一行提示「E07 被人工编辑过，未移除，请确认」。这条规则是为了防止「人在 00:50 改了一句，08:00 重跑把它冲掉」。

4. 分数线现在是什么角色

你不需要看懂它，因为它只做两件事：

  1. 决定预览版默认选哪些。A 档全选、B 档按分数取前 6。这是「机器替你做的第一版选择」。
  2. 决定全览里的顺序。分高的排前面，所以你要是只有 3 分钟，看前 15 行就够了。

它不决定你能不能改、改多少、总数必须几条。那些都由你在全览里说。

所以「先按这个顺序跑」是对的。跑 3–4 期之后，把预览版和你实际改的结果对一遍： 如果某类条目你每次都加，说明它的分太低；每次都删，说明分太高。这就是回标——不需要先设计一套精确的分数， 让数据告诉你该怎么调。

4.1 一个必须写的上限

A 档全选会失控：旺季 208 个事件里 A 档可能 20 条，预览版就会写到 20 条。所以加一条硬约束：A 档最多 14 条，超出的降级到 B。这样预览版条数恒在 6–14 之间，不随事件量爆炸。

5. 月报：取消 12 月兜底

规则简化成一句：每月最后一个周日。不再判断距圣诞几天。

月份发布日窗口天数
2026-1111-29（日）10-26 → 11-2935
2026-1212-27（日）11-30 → 12-2728
2027-0101-31（日）12-28 → 01-3135
2028-1212-31（日）12-04 → 12-3128

2028 年会落在 12-31，距圣诞 6 天。这没关系——月报覆盖的是整月发售，不是圣诞档；12 月末那几天本来就有年末商战的新作，晚一点反而收得更全。取消兜底之后，代码里少一个分支，人也不用记特例。

期号仍是 YYMMDD-m，替代当周周报（同一天不出两份）。

9. 三个还没定的

  1. 08:00 这个时点。现在的假设是「周一早上发布，人在上班前扫一眼」。如果你习惯晚上看，改到 20:00 也行，只是发布晚一天。
  2. overview.md 还是 overview.html。Markdown 便于你在对话里回编号，HTML 便于扫读。我倾向两个都出——生成成本几乎为零，各取所需。
  3. 业界栏手写内容的存放。现在设计成写在 decision.json 里，跟着这一期走。如果同一件事要在两期之间延续（比如「闭站重建，11 月下旬重开」），需要一条「跟踪项」机制，M6 再说。
一句话总结：预览版是保底，全览是提优。 这样即使某一周完全没人管，周报也不会断——而这一点，比「每期都精确选对 12 条」重要得多。
