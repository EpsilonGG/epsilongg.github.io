0. 这一版改了什么

上一版只读了正文纯文本，得出「原文无配图、无脚注、无来源链接」。抓了 27 期原始节点后，前两条要改，第三条成立：

  1. 原文图很多，而且图是正文的一半工作量。近 15 期 374 条配 645 张图，1.72 张/条；一张图注都没有。周报的成本重心不在写字，在找图、选图、排图。
  2. 有「总结性图片」，但它不是信息图。每月第一周那期会有一条「X 月新作本周发售」，配一张当月新作的拼版图，尺寸每次都不一样（1192×1548 到 2436×1838 都有），无文字、无标注、无图例。原站从不做图表。
  3. 无来源链接，但每期都有封面。封面是独立字段（2048×871），不进正文；同时被站点用来自动生成 1200×630 的分享卡（og.hikarinagi.org/og/article/{id}），卡上有标题两行截断、VOL.267、作者、日期区间、logo。
一句话结论：照抄正文结构只要 1 天，凑齐一期 43 张图要一整套新管线。 周报能不能跑起来，取决于「图片从哪来」这一件事，而不是取决于「文章怎么写」。

1. 样本与方法

站点是 Nuxt 单页应用，直接抓 HTML 拿不到正文（前端渲染，且对无头浏览器有挑战页）。 但列表页与详情页都走 /api/v3/articles，返回的是编辑器节点树 （heading / paragraph / image_block），带 width、height、caption。 这比抓正文文本可靠得多，也是这次能拿到图片数据的唯一原因。

1.1 一个必须避开的结构陷阱

2025-06 到 2026-05 那批（id 30 / 112 / 122 / 131 / 145 / 154 / 162 / 168）把每条小标题也写成了 h2， 和「新作资讯 / 汉化情报 / 周边信息」同级。结果栏目和条目在 DOM 里平铺，机器分不清哪个是栏、哪个是条。 2026-06 之后统一成 h2 栏目 + h3 条目，才稳定下来。

对我们的意义：我们自己的周报 schema 必须把「栏」和「条」分成两个字段， 而不是靠标题层级推断。日报已经吃过这个亏（works 是数组、一条一个作品），周报同理： sections[] 里嵌 items[]，每项带 action、works[]、images[]、sources[]。

2.1 月度条目：唯一带「总结图」的地方

27 期里出现 10 次（基本一月一次），固定形态是：一张拼版图 + 一句概述 + 每部作品一行的清单。

十次里清单长度是 3–10 部，拼版图尺寸从 1192×1548（竖）到 2436×1838（近方）都有， 完全没有标准化。这说明那张图是编辑现拼的，不是模板生成的。

这是唯一值得「做得比原站好」的地方。原站的拼版图只解决了「一眼看到有哪些新作」， 不解决「哪部是哪部」。我们有 VNDB 的封面 + 中文名 + 厂牌，可以做成带编号和厂牌的对照图， 读者不需要再去搜。这也是我们唯一有结构性优势的图。

3. 一条的解剖

3.1 图文位置：图在两头，字在中间

把每条拆成 I（图）和 P（段）的序列，27 期 652 条里最常见的四种形态：

序列条数占比读法
I P I P24538%头图 → 事件段 → 尾图 → 背景段（图跟着哪段走并不固定）
I P P I P10216%头图 → 事件 → 背景 → 尾图 → 价格/日期
I P P7712%头图 + 两段，最省
I P I P P426%信息量大时再加一段
I P P P366%三段的纯文字条目（多见于汉化栏）

八成以上条目以图开头，且头图紧贴小标题、不与正文同段。这个位置关系很关键： 它意味着「图 = 这条新闻的视觉锚点」，读者扫标题 + 头图就能决定读不读。

每条的图数分布（近 15 期 374 条）：1 张 108 条、2 张 259 条、3 张 5 条、4 张 1 条。 两张是绝对主流，且第二张几乎总在最后一个段落之后，起「收尾」作用。

3.2 文字：两段式，第一句几乎固定

  • 段落数：2 段 243 条（65%）、3 段 94 条（25%）、1 段 11 条。也就是说「事件 + 背景」就是标准形态。
  • 89% 的条目第一段以「本周，」开头。这是一个廉价的、但极其有效的时态锚点，读者一眼知道这是本周发生的事。
  • 96% 的条目含同一句套话「感兴趣的玩家可以前往相关网站了解详情」。这是纯排版冗余，我们不必抄，省下的字数正好用来写背景。
  • 背景段的事实密度：47% 含剧本/原画，40% 含价格，72% 含具体日期，只有 17% 明说「原版是哪一年哪家出的」。
事实类型覆盖率我们能不能自动拿到
具体日期（发售/截止/开始）72%能。原文/官网/X 正文正则，配合 VNDB released

4. 图：三类素材，一套位置

4.1 数量与形状

1,182 张图里有尺寸记录的 1,176 张：横向 809（69%）、竖向 206（18%）、近方 161（14%）。 横图是游戏截图与主视觉，竖图是商品海报与抱枕/立牌这类长条物料，方图多是头像式的人物特写。 三种形状混排在同一栏里，原站的处理是统一宽度 100%、高度自适应——不裁、不统一比例。

这一点和我们的视觉规范冲突：我们是黑白灰、圆角 6px、无阴影。如果照抄「宽度 100% 自适应」， 一栏里会出现十几张高度不一的图，页面节奏会散。更合适的是固定 3:2 容器 + object-fit: cover， 把竖图裁成横图（商品图裁掉上下通常无损信息，因为主体在中段）。

4.2 素材只有三类，没有图表

类型估计占比来源能不能自动拿
主视觉 / KV约 40%官网首图、官方 X 公告图、Steam header_image能。Steam 最稳，官网次之
游戏截图 / CG约 35%官网截图页、Steam screenshots、VNDB screenshots能。VNDB 单作 10 张起，带 sexual 标记可过滤
商品图 / 活动海报约 25%官方商店页、活动特设页难。多数在 X 上，抓不到（见 §5）

没有一张是信息图：没有时间线、没有销量柱状、没有价格对比表。27 期、1,182 张图，零图表。 所以「设计总结性图片」这件事，在原站根本不存在——我们如果要，是从零加的一个新元素，不是复刻。

4.3 零图注，是刻意的

近 15 期 645 张图，caption 字段全部为 null，没有一条图注。图与文字的归属完全靠位置：图紧跟在某个 h3 之后， 就属于那条。这个做法在「一条一图」时没问题，但一条两图时读者其实分不清哪张是哪张。

我们的选择：默认不加图注，但给两类图开例外。
理由：43 条图注 = 43 个新的出错点，而且图注写错比不写更糟（读者会以为那是官方说法）。
例外一：月度拼版图，必须写「本月 9 部新作，从左到右：…」，否则读者不知道在看什么。
例外二：商品图，写一句「抱枕套 13,200 日元（含税）」——这类图不带文字就完全无法自解释。
全期图注上限 5 条，每条 ≤ 20 字，进判卷。

4.4 封面：一个比例，两个用途

封面是独立字段，不进正文。27 期比例恒定 2.35:1（2560×1089 → 3525×1500 → 2048×871， 像素在降，比例没动）。它有两个用途：列表页缩略图、分享卡底图。

分享卡是站点自动生成的（og.hikarinagi.org/og/article/{id}，1200×630）， 把封面当底图，左侧压一层白色渐变，压上标题。卡片元素固定：

关键判断：带字封面不必上 satori。我们的 scripts/daily-image/render.mjs 已经是 「HTML 模板 + Playwright 截图 + sharp 压 WebP」，字体用的是全量 CJK（不是 NotoSub-* 子集）， 换一份 1200×630 的模板就能出封面。satori 要另外解决字体子集与断行，成本反而更高。

5. 素材从哪来（实测）

这是上一版最大的缺口——当时只写了「汉化栏没数据源」，没意识到图也没有。现在把四个来源都测了一遍：

来源能给什么实测结论
X 抓取（现有管线） 文字、时间、作者 galgame 2,370 条里只有 7 条带 media（0.3%）；voice 6,877 条里 9 条（0.1%） 不能供图
Steam appdetails header_image、8 张截图、中文名、发售日、价格 无 key；l=schinese 直接给官方中文名 主力
VNDB /vn 封面、10 张截图（带 sexual/violence）、staff、发售日 已验证 screenshots.url 可用；单次查询即可拿到全部 主力
官网 og:image KV、活动海报 需按作品找官网 URL；成功率取决于是否有官网 兜底
三个后果：
① X 抓取链路要查：media 字段几乎全空（9,247 条里 16 条有值）， 要么 provider 没返回图，要么中间层丢了。本地 data/items/ 是 CI 产物、现在为空， 得在 CI 里打一次点才能定位——但这是最高性价比的一件事：修好之后周边栏（11.7 条/期，最缺图的一栏）立刻有素材。
② Steam 是意外收获：它同时解决了「官方中文名」「发售日」「价格」「封面」「截图」四件事，而汉化栏要的正是这四个。汉化栏的数据缺口，一半可以靠 Steam 补上。
③ 周边栏仍然最难：商品图在官方商店页和 X 上，Steam/VNDB 都没有。这一栏要么接受「用作品 KV 代替商品图」，要么把 X 图片修好。

7.3 三项容易被低估的成本

  1. 版权与署名。KV、截图、商品图的版权都在原权利方，不在我们。页脚要加一行「图片版权归原权利方，仅作报道引用」，且每张图要能追到 source_url。这不是工作量问题，是合规问题。
  2. R18 素材过滤。VNDB 的 sexual 标记能挡掉一部分，但商品图（抱枕套、挂画）在 VNDB 里没有标记。这一层必须有人工兜底，且要留「已复核」记录。
  3. 封面字体。如果哪天要重做模板，记得用全量 CJK——NotoSub-* 是子集，会大面积空白。这个坑日报已经踩过一次。

8.2 新增 W5：图片先行

原站的产出顺序是「先有事件，再配图」。但机器做的时候，反过来的成功率更高： 先确定「这周有哪 8 张（或 43 张）能用的图」，再决定写哪几条。理由是图是硬约束—— 一条新闻写得再好，找不到图，在周报里就站不住（原站 100% 的条目都有图，没有例外）。

周日 23:15  trigger_fetch（现有）
      23:40  事件聚合 → 候选 190 条
      23:42  图片取材：对候选 Top 60 拉 Steam / VNDB，得可用图 55 张
      23:45  人挑图：勾掉不要的 → 剩 43 张（5 分钟）
      23:50  按「有图」过滤候选 → 出题面（只包含有图的条目）
      23:55  LLM 写作
      00:05  apply + 四道闸门
      00:10  渲染封面 + 一览图
      00:15  发布

这个顺序还有一个副作用：它天然限制了条目数。图不够的那周，条目自然少—— 正好复刻原站「有多少写多少」的节奏，不用另外设计规则。

8.3 图片子流水线：三档

档做什么技术成本
I1 直取原图下载、裁成 3:2、压 600/960/原宽 WebP、写清单Python + sharp（现有 optimize_images.mjs 已能做变体）低。是纯 IO
I2 拼版月度新作一览：4 列网格，纯拼图不带字sharp composite低。半小时能写完
I3 带字封面 1200×630、带编号的一览图HTML 模板 + Playwright + sharp（复用 daily-image）中。模板要调版式

三档的选择标准很简单：图里要不要出现中文。不要中文就用 sharp，要中文就走 Playwright。 不要为了「统一」把 I1 也塞进浏览器——43 张图走一遍浏览器要几十秒，纯浪费。

9. 判卷：加第四道闸门

上一版定了 L1 结构 / L2 文风 / L3 事实。图片既然是一半的工作量，就得有对应的闸门， 否则「图糊了、重复了、来源丢了」这类问题会一路漏到线上。

闸门查什么失败处理
L1 结构三栏顺序、条数区间（8–40）、每条 1–4 张图、标题含《》整份拒收
L2 文风禁用词表、副标题不写「XX 侧」、套话不出现、句长按条拒收
L3 事实日期、价格、版本数、staff 必须能在 sources 或作品档案里逐字找到按条拒收
L4 图片见下按图替换，换不到则整条降级

L4 的具体阈值

  • 每期图片总数 20–60 张（E 方案放宽到 6–12）
  • 单张最短边 ≥ 600px；体积 ≤ 500KB（压完）
  • 封面固定 1200×630，体积 ≤ 300KB
  • VNDB 来源的图 sexual 必须为 0；非 VNDB 来源必须有「已复核」标记
  • 同一期内 pHash 距离 < 6 视为重复，只留一张
  • 每张图必须有 source_url，且域名在白名单里（steamstatic.com / vndb.org / 官方站）
  • 图注总数 ≤ 5，每条 ≤ 20 字

待定（需要拍板）

  1. 周边栏做不做。它是原站最大的一栏（11.7 条/期），也是最缺图的一栏。做，就得先修 X 图片链路；不做，周报会明显比原站「薄」。
  2. 一览图带不带字。带字（Playwright）读者更省事，但不带字（sharp）零风险、零字体依赖。我倾向带字，且只在月度那期带。
  3. 封面要不要显示条数。22 条 / 43 图 这种量化信息放在封面上，好处是诚实，坏处是短周会显得寒酸。
  4. 声优周报与 Galgame 周报要不要同一天。两版口径不同，同日发会让读者对比；隔天发则失去「周报日」的仪式感。

样本抓取脚本未入库（一次性分析用）：/api/v3/articles?page=1..5&page_size=50 取列表， /api/v3/articles/{id} 取节点树；27 期 JSON 共约 850KB，可随时重抓。
