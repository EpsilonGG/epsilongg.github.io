周报：把「一周的作品动态」做成能自动跑的栏目

拆解 Hikarinagi《Gal 周报》的结构，对照本站日报管线，给出元素清单、四种内容方案与四套工作流。

样本：【Gal周报267期】十月新作本周发售，《樱花云＊绯红恋》官中将登陆Steam （Hikarinagi，2026-11-01，授权转载自 B 站 opus，22 条正文 + 10 人文案 + 5 人审核）。
基线：data/xreader/galgame/ 与 voice/ 2026-10-21 → 11-03 共 14 天真实抓取（2,252 / 6,706 条）， 以及已上线的 4 期日报（261031、261101、261101-g、261102）。
写于 2026-11-03。本文只做决策参考，不改变任何现有行为。

1,126一周 Galgame 条目（实测折算）
194规则聚合后的事件数／周
22原站一期正文条数
21.8 万字一周原文，一份题面塞不下

0. 先说结论

1. 周报的单位是「事件」，日报的单位是「发言」。这是所有分歧的源头。 日报写「某人今天说了什么」，一句话一个人；周报写「某部作品这周发生了什么」，一段一件事。 两者的聚合键不同（account vs 作品 × 动作），判卷对象不同（handle vs work）， 选材逻辑也不同。把日报的时间窗从 1 天改成 7 天，得到的是一份很长的日报，不是周报。

2. 素材量够，但结构不对。 两周 2,252 条 Galgame 条目（折一周 1,126 条）、111 个号、479 部作品；按「作品 × 动作」粗聚合， 两周压到 388 个事件，折一周 194 个，和原站一期 22 条同一个数量级，选材压力可控。 真正的问题是62% 的条目归不进任何事件（没有『作品名』或没有动作词）， 以及汉化情报几乎没有数据——14 天只有 9 条，且没有一条来自海外发行商。

3. 三处硬约束必须先解决，否则写了也跑不起来。 ① 一周 21.8 万字，是日报单期题面（8.4 万字节）的七倍，必须先在数据层聚合再出题； ② 现有 filter 规则主动删掉周边信息（Moepedia 的 drop_if 里有 キーホルダー／タペストリー／色紙，max_items: 5），周报要另一套规则集； ③ 周报每句话都带数字（日期、价格、版本数），判卷要从「有没有 sources」升级到「数字能不能对上」。

4. 推荐路线：Galgame 周报走「编辑台 → 事件层」，声优周报走「日报 reduce」。 前者内容单位变了，必须新建；后者主体还是人，7 份日报的 people 汇总就能出稿，几乎零数据层成本。 两件事不要用同一套代码硬凑。

1. 原文结构拆解

└── 文末：文案 9 人 / 审核 5 人 / 原文链接 / 授权转载声明

三个栏目是固定顺序的，栏目内按重要性排。没有「本周回顾」「编者按」这类内容—— 标题本身就是导读，这跟日报必须写「今日看点」把散点串起来完全不同。

1.2 一条的最小结构：三段式

22 条里，除了「十月新作本周发售」这个列表条目，其余 21 条都是同一个模板。以《Lilac》NS 版为例：

段原文作用可自动化程度
① 事件 本周，Frontwing 宣布制作《Lilac》NS 版，并同步公开了游戏的发售日期，感兴趣的玩家可以前往相关网站了解详情。 谁、对哪部作品、做了什么 LLM 组句，但主体/作品/动作三元组必须来自事件表
② 背景 本作原版是 Frontwing 于 2023 年发售的 galgame，改编自 Project RICORO 的同名舞台剧。本作由河野悠花、浅生咏负责剧本，大枪苇人负责原画。 档案：原厂牌、原发售年、类型、剧本、原画 纯查表。VNDB + 累积 registry 能给到厂牌/日期/人员
③ 交易 其中"side Witch"和"side Wizard"是剧情相同但角色性别相异的两个版本。NS 版售价 3480 日元（含税），预计于 2026 年 11 月 5 日发售。 版本分档、价格、发售日 规则抽取 + 事实判卷。这是最容易写错、也最该被机器管住的一段

三段的信息来源完全不同：① 来自本周的动态，② 来自长期档案，③ 来自公告原文。混在一起写是文风，分开生产是工程。 把 ② 做成查表，周报的成本立刻从「每期查十几部作品的资料」降到「维护一张作品表」。

2.4 三个硬缺口

① 汉化情报没有源。 14 天里提到「中国語／簡体字／英語版／Steam版」的条目只有 9 条，来自 7 个账号， 全部是日本厂牌顺口提一句「海外版也上了」。而原文这条讲的是 Shiravune 代理、Steam 页面上线、支持三种语言—— Shiravune 不在名单里，NekoNyan、Sekai Project、JAST、Kagura 也都不在。 名单 185 个号里只有 1 个发行商（akaeroCore，4 个语言号）。 不补源，这一栏写不出来；补源，是唯一必须新增数据的地方。

② 价格和版本几乎不在 X 上。 5% 的事件含价格。原文那种「完全生产限定版 12980／通常版 8980／下载版 8800／NS 早期下载版 7920」 来自官网和商店页，不是推文。要么放弃价格（周报降级为「告知型」），要么接商店页抓取。

③ 现有降噪规则会删掉周边。 daily-roster-galgame.json 里 Moepedia 的 drop_if 含 キーホルダー／タペストリー／色紙／プレゼント， max_items: 5。日报这么做是对的（一天只写一句话），周报这么做等于自断一栏。 周报必须有自己的 filter 段，而不是共用名单里的那一份。

3. 内容方案：周报到底写什么

四个方案，差别不在「写得好不好」，而在需要哪些数据、要判几道卷、每周要几个人盯。

3.1 方案 A：全仿四段

照原文来：头条 + 新作资讯 + 汉化情报 + 周边信息，每期 20–26 条。

  • 需要的数据：事件表（作品×动作）、作品档案（厂牌/人员/原发售日）、价格与版本（商店页）、汉化源（发行商/Steam）。
  • 判卷强度：L1 结构 + L2 归属 + L3 事实 + L4 术语，四道全上。价格与日期都要能对上。
  • 新增模块：events、extract、works、sections、prompt、apply， 外加一个非 X 适配器（汉化源）和一个商店页抓取。
  • 风险：周边栏条数最多、事实最杂（价格区间、活动起止、抽选条件），也是最容易写错的一栏。 第一版就做全，判卷会长期红。

3.2 方案 B：两段（新作 + 汉化）

只做信息密度最高的两栏，每期 10–14 条。周边留到 P2。

  • 需要的数据：事件表 + 作品档案 + 汉化源。不需要价格抓取（发售日 + 平台足够）。
  • 判卷强度：L1–L3，但事实闸门只查日期与平台，不查价格。
  • 新增模块：与 A 相同，少一个商店页抓取、少一套周边规则。
  • 优点：一期 12 条，判卷跑得动，人复核 10 分钟内能过。原文的头条结构也能保住 （一条「本周发售」+ 一条「官中/移植」）。
  • 缺点：不像「周报」，更像「本周新作简报」。读者拿不到周边信息。

3.3 方案 C：只出结构化清单，不写成文

不出段落，页面直接渲染事件表（作品 / 动作 / 日期 / 平台 / 厂牌 / 来源链接），配一句机器生成的摘要。

  • 需要的数据：事件表 + 档案表。不需要 LLM 写作。
  • 判卷强度：只有 L1 结构 + L2 归属。因为没有人写的句子，就没有「编造」的空间。
  • 新增模块：events、works、页面表格。工作量是 A 的三分之一。
  • 优点：一周就能上线；数据可以先用两周校准规则；日后想写成文，事件表已经在了。
  • 缺点：可读性差，跟「周报」的期待不符。适合做中间产物，不适合做终态。

3.4 方案 D：双版（Galgame 四段 + 声优三段）

两个版各自成篇，同一周发两期。声优周报建议的栏目（原文没有，需自己定）：

  • 出演情报：新番、新作游戏、舞台、朗读剧的主演决定
  • 作品与音声：角色歌、专辑、音声作品发售，销量里程碑
  • 活动与人：生诞祭、线下活动开票、移籍／独立／毕业

这三栏的素材，日报里已经每天在产出（people[].summary + works）， 所以声优周报不需要事件层——把 7 天的 report.json 按人合并、去重、只留有「状态变化」的，就能出稿。 这是唯一一个「周报 = 日报的 reduce」成立的地方，原因见 §4.3。

一句话总结这张表：选材、事实、排序全部交给规则，LLM 只负责把结构化的三元组写成中文。 这不是为了省钱，是为了可判卷。让模型自己挑事件、自己算日期、自己决定谁上头条， 判卷就只能查「这句话像不像」，而周报最不能错的就是日期和价格。

4. 工作流方案

4.1 W1：在 daily 里加 --window week

scripts/daily/
  window.py   + WeekWindow          # 7 天半开区间
  issue.py    + weekly 期号
  cli.py      + --window week
  export.py   不动（按 account 分组）
  apply.py    不动（判 handle 归属）
  • 成本最低：三个文件改，一天能跑出「很长的日报」。
  • 致命问题：export.py 按账号分组、build_report 生成 people 表、 validate_answer 要求 handle 在本期账号里——整套语义是「人」，周报要的是「作品」。 硬套的结果是：周报的每条内容都要先挂到一个人名下，而「某厂宣布移植」这件事的主体是作品，不是账号。 只在做声优周报时成立（主体确实是人）。

4.2 W2：新建 scripts/weekly/

scripts/weekly/

  events.py     作品 × 动作 聚合
  extract.py    日期 / 价格 / 平台 / 语言
  works.py      registry 查询与写回（VNDB 兜底）
  sections.py   栏目映射 + 打分 + 封顶
  prompt.py     按事件出题

  cli.py        prepare / prompt / apply / confirm / publish

复用：daily.model / daily.roster / daily.adapters / daily.filter（换规则集）/ daily.state
  • 优点：日报完全不受影响；周报可以有自己的判卷、自己的 schema、自己的页面。 filter 与 adapters 是纯函数与接口，复用没有副作用。
  • 成本：9 个新文件 + 1 个 collection + 3 个页面 + 1 个 schema。
  • 适合：Galgame 周报（内容单位变了，必须新建）。

4.3 W3：周报 = 7 份日报的 reduce

输入  data/daily/261027-g/report.json
      data/daily/261028-g/report.json
      …（7 份）
      只读 works[] + highlights[] + people[].summary
处理  按作品名合并 works、按人去重 people、丢掉「同一天说过两次」的
输出  data/weekly/261102-wg/report.json
  • 优点：零数据层工作。日报已经过了判卷、每条都有 sources， 汇总只是字符串合并 + 去重。一天能上线。
  • 致命限制：日报的 works 只写「哪个作品 / 什么事」，没有价格、版本、人员； 周边与活动在 filter 阶段就被删了；同一件事会连续 3 天出现在 works 里（需要按作品名去重并取最新）。 所以它只能产出「本周新作动向」这一栏，做不了汉化和周边。
  • 适合：声优周报（people 本来就是主体，去重后正好是「这周谁做了什么」）。

4.4 W4：编辑台（脚本出候选表，人挑，LLM 润色）

① python -m weekly prepare --week 2026-11-02
   → out/261102-wg/events.md    190 条事件，带 key / 动作 / 日期 / 价格 / 来源
② 人在 events.md 里把要用的条目勾出来（改 picks.json，20 行）
③ python -m weekly prompt --issue 261102-wg
   → 只对 picks 出题，题面 8 条事件，模型写 8 段
④ apply / confirm / publish
  • 优点：质量最高、风险最低，而且能校准规则——人挑两周，就知道哪类事件该自动进、哪类永远不该。 这不是「偷懒方案」，是把人工判断变成规则的过程。
  • 成本：每周 30–60 分钟人工；代码量与 W2 相同（picks.json 只是一层过滤）。
  • 适合：P0 阶段的前两周，以及所有「第一次做」的栏目。

4.5 对比与组合

方案改动面能做的栏目判卷上线速度长期维护
W1 daily --window week3 个文件只有声优（人主体）复用最快语义拧，越改越乱

推荐组合：声优周报走 W3，Galgame 周报走 W4 → W2。

理由不是「哪个先进」，而是两个版的内容单位根本不同： 声优周报的主体还是人，日报 7 天的 people 已经是判过卷的成品，再写一套事件层是重复建设； Galgame 周报的主体是作品，日报里根本没有这个维度，只能新建。 而 Galgame 这一侧先走 W4，是因为规则还没校准——第一周就把 190 条事件全自动写出来， 一定会出现「17 年前本日发售」混进「本周新作」这类错，人工挑两周比事后返工便宜。

5. 判卷：周报要多一道「事实闸门」

日报的判卷回答三个问题：这句话有来源吗？这个人在本期吗？字数超了吗？ 周报还要回答第四个：这句话里的数字，原文里有吗？

层查什么实现失败处理
L1 结构栏目、条数上限、字段齐全JSON Schema（schemas/weekly.schema.json）整份拒收
L2 归属work 在本期事件表里；sources 命中 keyapply.py（同 validate_answer）整份拒收
L3 事实文本里的日期／价格／版本数／语言，必须能在 sources 原文或 registry 里逐字找到facts.py：抽 token → 归一 → 比对按条拒收
L4 术语glossary.avoid 里的写法不许出现check_glossary.py（已有）报错，人工改
L5 重复同一 (work, action) 只许出现一次；与上周标题不重复apply.py按条拒收

为什么 L3 按条拒收，而日报是整份拒收？ 日报一期就是一篇文章，缺一段就读不通，整份作废是对的；周报是 20 条彼此独立的短讯， 一条价格写错不该拖累其余 19 条。拒收的条目进 out/<期号>/rejected.json， 日志逐条列出原因，页面上不渲染——宁可少一条，不可错一条。

L3 的归一化规则（不归一一定误报）

日期  11月27日 ≡ 11/27 ≡ 2026-11-27      价格  1,050円 ≡ 1050日元 ≡ 1050
版本  4 种 ≡ 四种 ≡ 4版本                语言  简中 ≡ 简体中文 ≡ 中国語（簡体字）

规则表放在 data/facts-normalize.json，改写法不用改代码——和 glossary.json 同一个思路。

6. 期号、出口与发布节奏

6.1 期号三个方案

方案形态优点缺点
ISO 周2026-W45国际通用，一眼知道是第几周跨年周（第 53 周、1 月 1 日归上周）容易算错
沿用日期261102-w / 261102-wg与日报 261102-g 同构；日期 = 该周周一；跨年无坑读者看不出「第几期」
连续期号weekly-3读者有追更感，仿原站要维护计数器，补录会错位

建议：数据层用「沿用日期」，显示层两个都写。 目录名 data/weekly/261102-wg/，页面标题写 Gal 周报 · 2026 年第 45 周（第 3 期）。 期号管「覆盖哪一周」，issue.seq 管「第几期」——和日报「期号管日期、published_at 管时刻」是同一个原则： 一个字段只回答一个问题。

6.3 节奏

  • 覆盖窗口：JST 周一 00:00 → 下周一 00:00（半开区间，与日报同一套写法）。
  • 发布时间：周一 08:00（北京）。周日夜里发会漏掉周日晚的公告；周一早上是周报的自然阅读时间。
  • 抓取：不新增抓取任务，复用现有两个 workflow（30／20 分钟一轮）。周报只是多读一次库。
  • 自动化：单独一个 FREQ=WEEKLY;BYDAY=MO;BYHOUR=8;BYMINUTE=0 的任务，不要并进 23:15 的日报任务—— 两者失败原因不同，混在一起会让「日报挂了」和「周报挂了」分不清。

8. 风险与未决

风险表现缓解
汉化源缺失这一栏只能空着或写「本周无」P2 补名单；在那之前方案 B 少一栏，改成「新作 + 移植」
事实判卷成本L3 误报率高会让人绕过闸门归一化规则先跑 200 条真实事件校准，误报率 < 5% 再上

62% 条目归不进事件素材利用率低，可能漏掉真新闻先接受；两周后看「人工补进去的条目」长什么样，再扩关键词表
版权原站是授权转载，我们不能照搬周报是自己写的事实性综述，每条带来源 key，文末给原文/官网链接；不复制原站句子
期号与归档周报和日报混在 /daily/ 里会乱独立路由 /weekly/、独立 collection、独立目录

待定（需要拍板的三件事）

  1. 周报要不要做周边栏？ 数据够（62 事件／14 天），但事实最杂。建议先不做，跑两周再定。

  3. 期号显示要不要「第 N 期」？ 要的话得先定 issue.seq 由谁写（prepare 数目录，还是人手填）。
