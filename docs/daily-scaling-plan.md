# 日报扩容方案：几十人 → 上百人，综合 + 分类两种视图

> 适用：本站「日报」栏目（`/daily/`）。
> 现状：三段版式已落地（今日看点 / 互动 / 名单），数据全部是结构化 frontmatter。
> 本文是**后续**扩容的方案，不是已完成的功能。最后更新：2026-10-25。

---

## 0. 先给结论

1. **瓶颈不是页面，是"喂给模型的输入量"和"名单维护"**。100 人 × 3 条 ≈ 300 条推文，一次塞给模型既贵又不准。
2. **一份数据、多种视图**是唯一划算的做法：分类视图不重新抓取、不重新摘要，只对同一份数据 filter + 重排。
3. 分三期：**名单化** → **分类视图** → **map-reduce 摘要**。前两期纯工程，第三期才有真成本。
4. 现在这套三段结构化字段（`highlights` / `interactions` / `people`）已经是为扩容留的口子——不用重写，只需要在上面长东西。

---

## 1. 两个参考项目各自给了什么

### 1.1 juya-ai-daily（橘鸦 AI 日报）

- **一天一条，标题带日期**；正文是「**概览** → **要闻**」：先用几句话把当天总起来，再分条展开。这正是本轮改版采用的顺序（看点在前）。
- **同一份内容多形态分发**：文章（知乎 / 公众号）、视频（B 站 / YouTube）、RSS（第三方订阅、二次加工）。
- Markdown 备份进 Git 仓库，读者也能直接看源文。

**能直接借的**：概览先行（已实现）、一份内容多出口（二期加 RSS / JSON）。

> 说明：`github.com/imjuya/juya-ai-daily` 目前返回 404（仓库已删除或改名）。上面的结论来自它的公开产出物（知乎专栏的「概览 / 要闻」结构）以及第三方抓取该日报的项目，**不是仓库源码**。

### 1.2 vikiboss/60s

- **数据生产与接口服务彻底分离**：抓取跑在 GitHub Actions，产出静态 JSON，CDN 缓存；接口只负责读。
- **一份数据多种 encoding**：`?encoding=json|text|image`，同一份内容换壳输出。
- **LLM 只在生产侧跑**（用 Gemini 在定时任务里处理），请求时永远不调模型。
- 内容形态是「精选 N 条 + 一句收尾微语」——短、可扫读。

**能直接借的**：生产/渲染分离（我们已经是）、一份数据多出口、LLM 只在生产侧。

### 1.3 两者合起来

```
抓取（X-Reader CI） → 结构化数据 → 本地 LLM 标注 → 站点构建 → 多种视图 / 多种出口
        ↑ 已有            ↑ 本轮已做       ↑ 已有（手动）      ↑ 已有      ↑ 二期
```

本轮改版其实已经把"结构化数据"这一步做对了，剩下的都是在这一层上加东西。

## 2. 目标形态

### 2.1 三种视图

| 视图 | 路由 | 内容 |
| --- | --- | --- |
| 综合 | `/daily/<date>/` | 全部分类合在一起（现在这个） |
| 分类 | `/daily/<date>/<category>/` | 单类：类内看点 → 类内互动 → 类内名单 |
| 日期列表 | `/daily/` | 日期 + 首段看点 + 分类入口 |

**单人主页（`/daily/<handle>/`）先不做**。真有人要追某一个人时再说——分类已经能覆盖 90% 的诉求，而单人页会把页面数乘以人数。

### 2.2 一份数据两种读法

- **综合视图**：看点 = 跨类热点（由 reduce 步骤产出）；互动 = 跨类互动也放这里。
- **分类视图**：看点 = 类内热点（由 map 步骤产出）；互动 = 只保留类内的。
- **分类视图不是新内容**，只是同一份数据的另一种排列。跨类互动只在综合视图出现，分类视图不重复。

## 3. 数据结构改造（二期）

### 3.1 名单成为唯一事实来源

新增 `src/config/daily-roster.json`：

```json
{
  "categories": [
    { "id": "vtuber", "label": "VTuber" },
    { "id": "seiyuu", "label": "声优" },
    { "id": "illust", "label": "插画 / 3D" },
    { "id": "circle", "label": "社团 / 厂商" }
  ],
  "accounts": [
    { "handle": "322yui3",     "name": "乙倉ゆい", "category": "vtuber", "active": true },
    { "handle": "asuparama40", "name": "アスパラ", "category": "seiyuu", "active": true },
    { "handle": "old_account", "name": "已停更",   "category": "vtuber", "active": false }
  ]
}
```

规则：

- `active: false` 暂停某人，但历史日报不动。
- **不在名单里的 handle 归入「其他」并在构建时告警**——这是防止漏配的关键，不然新增账号会静默消失。
- 名单顺序 = 日报里的显示顺序。**不再按当日推文数排序**：人多了以后顺序每天变会让读者找不到人。
- **一个人只给一个 `category`**。跨类的人（VTuber 兼声优）用 `tags: []` 补充，不要给多个分类——多分类会让综合视图重复计数，分类视图也会重复出现。

### 3.2 数据仍然存在 Markdown frontmatter 里

**建议不改成 JSON 文件**，理由是：

- 现在 6 人 ~30 行 YAML，100 人约 300 行——机器生成的文件，长不是问题；
- 保留 Astro content collection 就白拿 `draft` 过滤、Zod 校验、`render()`；
- 改成独立 JSON 就要自己写 loader、自己实现草稿过滤，多一套机制。

**触发重新评估的条件**：超过 200 人，或者 `git diff` 因为 frontmatter 太长变得没法看。到那时再拆 `src/data/daily/<date>.json` + 自定义 loader。

⚠️ 唯一的坑是 **YAML 引号**：`summary` 里有 `:`、`"`、`#` 时必须用双引号包住（脚本已经产出 `summary: ""`，模型只替换引号内的内容）。三期加校验测试兜住。

## 4. 上百人的成本控制（三期核心）

### 4.1 问题量化

| 人数 | 日均推文 | 送入模型的字数 | 一次性摘要的问题 |
| --- | --- | --- | --- |
| 6 | ~26 | ~6 千 | 没问题 |
| 30 | ~130 | ~3 万 | 开始变慢，要点容易漏 |
| 100 | ~300 | ~7 万字 | 贵、慢、注意力分散，中间的人基本被忽略 |

### 4.2 map-reduce 摘要

- **Map（每分类一次，4–8 次）**：输入该类所有人的推文，输出该类的 `{类内看点, 类内互动, 每人一句}`。
- **Reduce（1 次）**：输入各分类的看点和互动，输出**全局看点**（跨类热点）+ **跨类互动**。

好处：单次输入可控（每类 10–30 人）；可以并行；某类失败只重试那一类；`每人一句` 在 map 阶段就按类分好了，分类视图直接能用。

### 4.3 确定性预筛（不花钱的部分，先做这个）

这三步在**不调模型**的前提下就能砍掉大部分输入：

1. **没活动的账号直接跳过**：`accounts` 里没有就不进 map。
2. **互动候选用字段抽，不靠模型猜**：从 items 里取 `in_reply_to_screen_name`、`quoted_status`、`retweeted_status`，只在**名单内**建边（A→B）。有边才把这一对交给模型写成人话；没有边就不调。这能把"互动"从"让模型通读 300 条找关系"变成"几十条候选里挑"。
3. **低价值推文折叠**：纯 RT、纯表情、与本人前一条高度相似的，只计数不送模型（"今天以转发为主"一句话就够）。

### 4.4 增量与缓存

- 摘要结果的缓存键：`handle + 当日推文内容 hash`。重跑时只重算变化的账号。
- 分类视图**不重新摘要**，只读综合视图已经算好的 `people[].summary` 重新分组。

---

## 5. 页面与构建量

- 每天生成：1 个综合页 + N 个分类页（N = 当日有人活动的分类数，通常 3–6）。
- 一年约 365 × (1+5) ≈ 2200 页。本机 13 页约 10 秒，粗估 2000 页 2–4 分钟，可接受；CI 有 6 小时上限，不是问题。
- **控制页面总量**：只给最近 30 天生成分类页，更早的只保留综合页。或者干脆分类视图只做"该类最新一期"（`/daily/<category>/`），不做历史分类页——**推荐后者**，页面数直接降到常数级。

> 推荐：`/daily/<category>/` = 该分类的最新一期；历史分类通过综合页上的分类锚点/筛选进入。这样既满足"按分类看"，又不会让页面数随天数线性膨胀。

## 6. 输出形态（多出口）

| 出口 | 现状 | 二期 | 说明 |
| --- | --- | --- | --- |
| HTML 综合 | ✅ | — | 已有 |
| HTML 分类 | — | ✅ | `/daily/<category>/`（最新一期） |
| RSS | ❌ 日报不进 RSS | ✅ `/daily/rss.xml` | **与 blog 的 feed 分开**，不动现有订阅者的收件内容 |
| JSON | — | ✅ `/daily/<date>.json` | 给第三方或以后自己做 App；对应 60s 的 `encoding` 思路 |

## 7. 质量闸门

新增 `tests/test_daily.py`（纯 Python，读文件，不构建）：

1. 每个 `src/content/daily/*.md` 的 frontmatter 能解析；
2. `accounts` 与 `people[].handle` 集合一致——防止脚本漏人、或手改时多出一个人；
3. `people[].handle` 都在 `daily-roster.json` 里（二期）；
4. 发布态（`draft: false`）的 `highlights` 非空、`people[].summary` 非空率 ≥ 90%；
5. 每条 `summary` ≤ 60 字（防止模型写成小作文）；
6. `summary` 里的 `:` / `#` 有正确引号（YAML 解析测试天然覆盖）。

已有的构建期兜底：`DailyLayout.astro` 在 `highlights` 为空、`people` 全空时打 `console.warn`，构建日志可见。

`npm run links` 已经能覆盖 `@mention` 和名单里的主页链接（都在 `dist` 里）。

## 8. 三期路线图

| 期 | 做什么 | 完成后的能力 | 风险 |
| --- | --- | --- | --- |
| **一期**（2026-10-25 已完成） | 三段版式、结构化 frontmatter、`@` 自动链接、空值自动省略 | 6–10 人，日报可读性达标 | 低 |
| **二期** | roster 配置 + 分类视图（`/daily/<category>/`）+ `/daily/rss.xml` + `tests/test_daily.py` | 几十人，能按类看 | 中：分类边界要一次想清楚 |
| **三期** | map-reduce 摘要 + 互动候选抽取 + 增量缓存 + `/daily/<date>.json` | 上百人可用 | 中高：本地批处理要有人盯 |

**验收标准**

- 二期：30 人时 `npm run build` 仍 < 60 秒；分类页不出现空页；RSS 只新增 `/daily/rss.xml`，blog 的 feed 内容不变。
- 三期：100 人时摘要步骤总耗时 < 20 分钟；某一分类失败不影响其他分类出稿；token 成本可估算。

---

## 9. 明确不做

- **不在 CI 里跑 LLM**：保持零 API key、零服务器。这条是整套方案的前提，扩容也不能破。
- **不做实时抓取**：一天一次足够，日报的价值在筛选不在速度。
- **不做图片版 / 视频版日报**：需要渲染引擎，违背轻量化。
- **不做每人独立主页**（`/daily/<handle>/`）：页面数乘以人数，收益不明。

---

## 10. 现在就要遵守的两条

1. **增删监控账号改 X-Reader 的 `accounts.yaml`**，不要手改日报文件——`accounts` 和 `people` 是脚本从数据推导的。
2. **日报文件只由脚本生成 + WorkBuddy 填三段**。`title` / `pubDate` / `accounts` / `people[].handle` 手改会和抓取数据脱节，下一期日报就会对不上。
