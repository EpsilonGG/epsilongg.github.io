# 博客写作指南

[← 返回仓库首页](../README.md) ｜ [项目说明](project.md) ｜ [Fork 指南](fork.md)

写给两种读者：几个月后回来改文章的自己，以及被叫来「按这个站点的格式写一篇」的 AI。
第 9 节有一段可以直接复制的提示词，把格式约束一次说清。

## 0. 三十秒版本

1. 新建 `src/content/blog/<slug>.md`（文件名就是 URL）。
2. 填 frontmatter：`title`、`description`、`pubDate` 三件套。
3. 正文用 Markdown 写。**图片加 `title` 就是图注，`[^1]` 就是注释。**

```markdown
---
title: 文章标题
description: 一句话摘要
pubDate: 2026-03-01
---

正文，需要解释的地方打个注释[^1]。

![替代文字](/images/blog/my-post/01.jpg "图注：这张图在说什么")

[^1]: 注释正文，点击正文里的数字会在页面底部弹出来。
```

## 1. 文件位置与 URL

| 项 | 规则 |
| --- | --- |
| 位置 | `src/content/blog/` 下，一个 `.md` 一篇文章 |
| 文件名 | 即 slug，会变成 `/blog/<slug>/` |
| 命名 | 小写英文 + 连字符，例如 `my-first-post.md`（中文文件名能用但不建议） |
| 改标题 | 不影响链接，随便改 |
| 改文件名 | **等于换链接**，旧地址会 404 |
| 格式 | 只支持 `.md`，不支持 `.mdx`（没装 MDX 集成） |

嵌套目录也支持（`src/content/blog/2026/03/xxx.md`），但 slug 会带上目录层级，不推荐。

## 2. frontmatter 字段

```yaml
---
title: 文章标题
description: 一句话摘要，会出现在首页、归档、RSS 与搜索结果里
pubDate: 2026-03-01
updatedDate: 2026-03-05   # 可选
tags:                     # 可选，默认空数组。只能从六个里选
  - 翻译访谈
  - 视觉小说
draft: false              # 可选，默认 false
source: original          # 可选，默认 original。ai = AI 整理
---
```

| 字段 | 必填 | 类型 | 说明 |
| --- | --- | --- | --- |
| `title` | ✅ | 字符串 | 不能为空。会渲染成 `<h1>`，**正文里不要再写一级标题** |
| `description` | 建议填 | 字符串 | 填了不能是空字符串。留空则 meta description 退化成「标题 · 站点名」 |
| `pubDate` | ✅ | 日期 | `2026-03-01` 或 `2026-03-01T08:00:00+08:00` 都行 |
| `updatedDate` | ❌ | 日期 | **不能早于 `pubDate`**，否则构建失败 |
| `tags` | ❌ | 字符串数组 | 显示在文章底部；不会生成标签页（本站没有标签路由）。**封闭集合**，见下表 |
| `draft` | ❌ | 布尔 | `true` 时：不生成页面、不进首页/归档/RSS/sitemap。**开发环境同样不显示** |
| `source` | ❌ | `original` \| `ai` | 内容来源。**默认 `original`**（本人原创，或转载/整理自其它网站但由人工完成）。`ai` 表示由 AI 参与整理/生成；单篇与列表项都会显示「AI 整理」标记，且默认不进「笔记」列表，需手动开启滑块才出现 |

字段写错（拼错、类型不对、日期非法）会让 `npm run build` 直接失败并指出是哪个文件，不会静默跳过。

### 2.0 标签只有六个

`src/config/tags.json` 是唯一来源，`src/content.config.ts` 会拦下任何白名单外的值：

| 标签 | 放什么 |
| --- | --- |
| `翻译访谈` | 从外站翻译过来的访谈（绝大多数文章都属于这一类） |
| `视觉小说` | 主题是视觉小说 / 文字冒险作品或它们的作者 |
| `游戏` | 主题是游戏本身（卡牌、独立游戏、厂商、发行） |
| `画集` | 画集、插画、画师 |
| `声优` | 声优本人 |
| `其它` | 放不进上面五个的 |

一篇文章最多两个标签，第一个是「这是什么内容」，第二个是「讲的是哪块」。
**不要在文章里就地发明新标签**：想加，先改 `tags.json`，再改 schema 注释，再改文章——
否则构建会红，且列表筛选器会出现只有一篇的碎标签。


### 2.1 内容来源与 AI 披露

「笔记」栏目用 `source` 一个字段区分两类内容，**不另开独立栏目**：

- **`original`（默认）**：本人原创，或转载/整理自其它网站但由人工完成。默认列表的栏目名就叫 **「原创与转载」**，涵盖这两类。
- **`ai`**：由 AI 参与整理/生成的文章。出于披露透明，单篇页面与列表项都会出现一个 **「AI 整理」** 小标记；并且**默认不在「笔记」列表里出现**——访客需要在筛选区勾选 **「含 AI 整理」** 滑块，列表才会把它们并入，栏目名随之变为「全部（含 AI 整理）」。

设计意图：绝大多数访客只想看人工内容，所以 AI 整理的文章默认隐藏、按需开启；「AI 整理」标记则保证一旦展示就明确披露。转载自其它网站的内容（人工完成）仍属于 `original`，无需特殊标记。

## 3. 正文语法

用的是 GFM（GitHub Flavored Markdown），以下都支持：

| 语法 | 写法 | 备注 |
| --- | --- | --- |
| 标题 | `## 二级` / `### 三级` | 从 `##` 开始，`#` 留给标题字段 |
| 粗体 / 斜体 | `**粗**` / `*斜*` | 中文不用斜体，见第 7 节 |
| 列表 | `-` / `1.` | 支持嵌套 |
| 表格 | GFM 表格 | 首行表头，第二行 `---` |
| 引用 | `> 引用` | 左侧竖线样式，不带斜体 |
| 分隔线 | `---` 单独一行 | |
| 行内代码 | `` `code` `` | |
| 代码块 | ` ```ts ` | 支持语法高亮，浅色/深色双主题 |
| 删除线 | `~~删除~~` | |
| 任务列表 | `- [x] 完成` | |
| 脚注 | `[^1]` | 见第 5 节 |
| 自动链接 | `<https://example.com>` | |

**不支持**：MDX、HTML 里的 `<style>` / `<script>`（会被过滤）、`$数学公式$`（没开 math）。

> **小心半角波浪号 `~`**：本项目的处理器把**一对**半角 `~` 当成删除线，`~文本~` 也会被划掉。
> 作品副标题常写成 `《加奈~妹妹~》`，直接粘进来就会变成 ~~妹妹~~。
> 写日文/作品名时用全角 `～`（`《加奈～妹妹～》`），或者把半角波浪号转义成 `\~`。
> 单个孤立出现的 `~`（如 `3~4年`）不受影响。

正文里可以直接写 HTML，比如 `<figure>`、`<img>`、`<kbd>`、`<sub>`，写法和 GitHub 上一致。

## 4. 图片与图注

### 4.1 推荐：Markdown 简写

```markdown
![替代文字](/images/blog/my-post/01.jpg "图注：C99 主视觉图，画师 Hiten")
```

第三个参数（引号里的部分）就是**图注**。构建时会自动变成：

```html
<figure class="article-figure">
  <img src="..." alt="替代文字">
  <figcaption class="article-figure__caption">图注：C99 主视觉图，画师 Hiten</figcaption>
</figure>
```

图注是真正的 HTML 文本：能选中、能被搜索引擎读到、不依赖 JavaScript，也不会在页面加载后突然冒出来。

> 只有「独占一个段落」的图片才会被升级成 figure。段落里夹在文字中间的小图标保持行内，不加图注。
> 转换逻辑在 `src/lib/markdown-figure.mjs`。

**连续两张以上**「带图注的独占段落图」会自动并成一组，宽屏并排、手机上仍是一行一张：

```markdown
![左图](/images/blog/my-post/01.jpg "左图图注")

![右图](/images/blog/my-post/02.jpg "右图图注")
```

输出是 `<div class="article-figure-grid">` 里装两个 `<figure>`。中间**不要**插正文，插了就不并组。

比正文栏窄的图会自动**居中**，图注的左边**对齐图片的左边**（不是正文栏的左边），所以图注只在图片宽度内折行。这是样式自动处理的，写文章时不用管；想改观感去 `components.css` 搜「文章 · 图片与图注」。

### 4.2 不要手写 figure

`width` / `height` 现在由构建过程自动补（见 4.3），所以**不需要**再手写 `<figure>` 块。手写原始 HTML 有两个坏处：

1. 绕过所有 Markdown 插件——拿不到 WebP 变体、`srcset`、`loading="lazy"`、`referrerpolicy`；
2. `<figure>` 块内部不能有空行，写起来容易踩坑。

只有在「图注里要放链接或特殊排版」这类 Markdown 表达不了的情况下才手写，并且记得手动补 `loading="lazy" decoding="async"`。

### 4.3 图片存放与自动优化

| 项 | 规则 |
| --- | --- |
| 目录 | `public/images/blog/<文章 slug>/` |
| 引用 | 用根路径 `/images/blog/<slug>/01.jpg`，**不要用相对路径** |
| 命名 | `01.jpg`、`02.jpg` 顺序编号，方便排序 |
| 格式 | 照片用 JPEG（质量 85 左右），带透明/文字用 PNG，动图用 GIF |
| 尺寸 | 正文宽度约 608px，2 倍屏 1216px；存 1000–1400px 宽足够 |

不用写 `alt` 也能显示，但**一定要写**：读屏软件靠它，图片挂掉时也靠它。

放好图片就完事，剩下的是自动的。`npm run dev` / `npm run build` 会先跑 `scripts/optimize_images.mjs`：

- 为每张图生成 **WebP 变体**（600 / 960 / 原宽，只有明显更窄才单独出）；
- 把原始宽高和变体清单写进 `src/data/image-manifest.json`；
- 构建时 `src/lib/markdown-images.mjs` 读清单，把图包成 `<picture>` 并补 `width` / `height`。

产物里的 `.webp` 是**派生文件**，已在 `.gitignore` 里，不用提交。手工重跑：

```bash
npm run images         # 增量（只处理改动过的图）
npm run images:force   # 全部重做
```

效果参考：52 张图源文件 7.0 MB，手机端（600w）实际下载量约 1.8 MB，是原来的 26%。

### 4.4 远程图片（轻量化转载）

转载外站文章时，图片可以**不下载到仓库**，直接在 `![]()` 里写原站的完整地址：

```md
![采访现场](https://www.gamespark.jp/imgs/zoom/1209290.jpg "原文配图")
```

构建时不会去请求这张图，HTML 里就是 `<img src="https://…">`，仓库里零字节。图注、`<figure>` 升级照常生效。

**必须用 Markdown 写法**。手写 `<figure><img src="https://…">` 属于原始 HTML，不经过 Markdown 插件，拿不到 `referrerpolicy="no-referrer"`（也就挡不住防盗链），也不会有 `loading="lazy"`。

**什么情况用远程、什么情况本地化**：

| 情况 | 建议 | 理由 |
| --- | --- | --- |
| 图片少（≤10 张）、单张 < 500 KB | 远程 | 省事，仓库轻 |
| 图片多（15 张以上）或单张 > 800 KB | 本地化 + 压缩 | 几十张外链图会把首屏拖慢，且没法出响应式尺寸 |
| 原文随时可能下架（活动页、限时特辑） | 本地化 | 原文一删图就全挂 |
| B 站专栏 | 本地化 | 现成的流程，且图片要取 `@1400w_85q` 高清版 |

**用远程图之前先跑一次体检**（会真的去请求每一张，报状态码、类型、体积）：

```bash
python scripts/check_remote_images.py
# 网络需要代理时
python scripts/check_remote_images.py --proxy http://127.0.0.1:7897
```

坏链返回退出码 1，可以接进 CI。**以后每隔几个月重跑一次**——这是远程图唯一的长期风险：原站删图、换路径、加签名参数，构建过程都发现不了（构建只拼 HTML，不请求图片）。

其它已知限制：

- 访客的浏览器会直接连原站，会暴露访客 IP 给第三方；原站慢的话页面也跟着慢
- RSS 只输出摘要，不受影响；OG 图用的是站点默认图，也不受影响

**远程图的宽高**：构建时不会联网，所以默认拿不到尺寸，图片加载前高度为 0，滚动时会跳一下。跑一次下面这条命令就把尺寸记下来（写进 `src/data/remote-images.json`，要提交）：

```bash
python scripts/check_remote_images.py --write-dims
```

之后构建时会自动给这些图补上 `width` / `height`，跳动就没了。原站换图（尺寸变了）时重跑一次即可；忘了重跑也不会出错，只是那几个 `width` / `height` 会偏。

### 4.5 翻译/转载：把原文配图补齐

译文最容易偷的懒，是只留一张封面图，正文里的截图全丢——读者看不到访谈里在说哪一幕，图注也就没了意义。
**规则：原文正文里有的图，译文里要有；原文的 `figcaption` 要翻译。**

流程（以 Game\*Spark 为例）：

1. **定位正文容器**：`<article class="arti-body">`。别的站点先搜 `<article`、`class="…content…"` 再定。
2. **按顺序取 `<figure>` 里的 `img`，跳过 `<iframe>`**（YouTube 嵌入不是图，不要当图下载）。
3. **下载**：带桌面 UA + `Referer: https://www.gamespark.jp/`，否则 403；
   注意该站 `src` 用**单引号**（`src='https://…'`），懒加载站点还要试 `data-src` / `data-original`。
   存成 `public/images/blog/<slug>/01.png`、`02.jpg`…，**编号即出现顺序**。
4. **核对**：下载后过一遍尺寸，宽度 0 或只有几 KB 的是失败页，重下（大站偶尔超时，重试通常就好）。
5. **插入**：每张图独占一段；位置对齐原文出现处；两张同主题的图**紧邻**放，构建时自动并成两列图版。
6. **写图注**：翻译原文 `figcaption`；原文没有就自己写一句这张图在说什么，句末带句号。
   不加 `▲`、不加「图：」前缀。同一场景的重复肖像（棚拍 6 张几乎一样的）只留 2–3 张。

```bash
npm run images      # 生成 WebP 变体，写 src/data/image-manifest.json（要提交）
npm run build
grep -c '<figure' dist/blog/<slug>/index.html     # 应等于插图数
grep -o '<del>' dist/blog/<slug>/index.html | wc -l   # 应为 0
```

源图宽度小于 960 时，`<picture>` 只会出一个原宽变体（不会放大），2× 屏上略软但可接受；
想要更清晰只能换更大的源图地址，不要用 CSS 拉伸。

## 5. 注释（脚注）

### 5.1 写法

正文里在需要解释的词后面加 `[^标识]`，然后在**文章任意位置**（习惯放在末尾）写定义：

```markdown
rurudo 从小学开始临摹自己喜欢的漫画[^1]，那时候还住在家里。

[^1]: 这里可以写一整段解释，也可以放 [链接](https://example.com/)。
```

标识可以随便取（`[^1]`、`[^note-a]`、`[^译注]` 都行），但必须和定义一一对应。**显示的数字按出现顺序自动编号**，和标识本身无关。

### 5.2 点击后的行为

- 正文里会渲染成一个小的方块数字。
- 点击它，**页面底部滑出一个面板**显示这条注释，右上角 `×` 关闭；按 `Esc`、点面板外面也能关。
- 关闭后焦点回到刚才那个数字，键盘操作不会丢位置。
- 点击**不会**跳转页面（脚本接管了默认的锚点跳转）。

### 5.3 文章末尾的完整列表

所有注释会自动汇总到文章末尾的「注释」区块，按顺序排列，每条后面有一个 `↩` 回到正文对应位置。

也就是说同一份内容有两个入口：**看的时候点一下就近看，需要通读的时候拉到文末**。

### 5.4 注意

- 注释内容支持行内格式（链接、代码、粗体），但**建议控制在两三行以内**——底部面板最高只有 45vh，太长要滚动。
- 注释定义之间要有空行，多段注释需要缩进（和标准 GFM 脚注一致）。
- 脚本没加载时（禁用 JS）数字仍然是一个普通锚点，点了会跳到文末的注释，功能不丢。

## 6. 代码块

````markdown
```ts
const a: string = 'hello';
```
````

- 语言标识写在开头（`ts`、`js`、`bash`、`json`、`md`…），写错不影响渲染，只是没高亮。
- 代码块自动跟随站点主题切换（浅色 `github-light` / 深色 `github-dark`）。
- 行内代码用单反引号，适合写路径、命令、字段名。

## 7. 排版约定

这些不是语法限制，是让整站看起来一致的约定：

| 约定 | 说明 |
| --- | --- |
| 从 `##` 开始 | 文章标题已经是 `<h1>`，正文里再用 `#` 会出现两个一级标题 |
| 中文不用斜体 | 中文斜体在多数系统字体下是强行倾斜，很难看；强调用粗体 |
| 一个段落只讲一件事 | 段落之间留空行，长段落拆开 |
| 引用块不滥用 | 只用来引用别人的原话，不要用来做强调框 |
| 数字与英文两侧留空格 | `使用 Node 22 运行`，不要写 `使用Node22运行` |
| 标题不加句号 | `## 怎么开始的` 而不是 `## 怎么开始的。` |

## 9. 给 AI 的提示词

新建文章时把下面这段连同主题一起丢给 AI，格式基本不会跑偏：

```text
请为我的 Astro 博客写一篇文章，严格遵守以下格式：

1. 文件路径：src/content/blog/<英文短横线 slug>.md（只输出文件内容）
2. frontmatter 必须有 title、description、pubDate；可选 tags、draft、source。
   - pubDate 格式 YYYY-MM-DD
   - description 一句话，不超过 60 字
   - source 取值 original（默认，原创或人工转载）或 ai（AI 参与整理/生成）。
     若 source: ai，单篇和列表都会出现「AI 整理」标记，且默认不进「笔记」列表，需开滑块才显示。
3. 正文从 ## 开始，不要写一级标题（# 由 title 生成）。
4. 图片用：![替代文字](/images/blog/<slug>/01.jpg "图注文字")
   —— 第三个参数是图注，必须写；图片按 01、02 顺序编号。
5. 需要补充说明的地方用脚注：[^1]，并在文末集中写 [^1]: 内容。
   脚注控制在两三行以内，可以带链接。
6. 中文不用斜体；中英文之间留空格；代码块标注语言。
7. 不要写 HTML 的 <style> / <script>；不要用 MDX 语法。
8. 只输出 Markdown 文件内容，不要额外解释。
```
