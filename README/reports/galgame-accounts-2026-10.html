0 一句话结论

信息号能凑出 13 个，厂商侧个人号只能凑出 14 个，而且质量差一档。前者是「有人在替读者做筛选」，后者是「作者偶尔发一句工作进度」——两者的信息密度不是一回事。真正每天值得抓的厂商侧只有三个：@Famishin（ゆずソフト代表，日更、内部视角）、@nakazawatakumi（中澤工，制作幕后解说）、@digitarou（Nitroplus 代表，企划口径）。

先解决容量问题，再谈加人。X-Reader 的 update.yml 现在是 302 个账号跑 19.6 分钟、超时线 20 分钟。再加 27 个约 +1.8 分钟，直接超时。名单可以现在就定，但上线必须等「拆成两个 workflow」那一步——即你说的两个 accounts.yaml 独立抓。

2026-10-29 已解决：CI 拆成 update.yml（声优版 237 个）与 update-galgame.yml（Galgame 版 177 个，独立 data-galgame/），名单也拆成两份 JSON。本页 27 个候选里，@seiya_saiga、@youtan0309、@aikouka23 已作为信息号入册启用；剩下 25 个（信息号 11 + 厂商侧个人号 14）仍在等排期。最新状态看 daily-roster-2026-10.html。

4 落地建议

4.1 分批收，不要一次全进

批范围人数理由
P0信息号里的 优先 + 个人号全部10每日都有产出：@getchucom（发售日历）、@bugbug_info（新作介绍）、6 个个人号。这一批决定 Galgame 版有没有内容。
P1厂商侧 优先3@Famishin、@nakazawatakumi、@digitarou。为「某人新作动向」提供一手引用。
P2其余平台号 + 剧作者14有量但杂。等 P0 跑两周、看过日报实际产出再决定。

4.2 名单字段（写进 daily-roster.json 时）

{
  "handle": "getchucom",
  "name": "Getchu.com",
  "category": "galgame",
  "role": "info-platform",
  "active": true,
  "note": "新作预约 / 特典 / 发售日倒数，最接近发售日历",
  "filter": { "drop_kinds": ["promo"], "max_items": 3 }
}

role 建议四值：info-personal / info-platform / scenario / director / owner。厂商侧个人号要挂 max_items: 1——他们一天发五条日常，全收会把声优栏目挤掉。

4.3 还没定的事

  1. 要不要 @youtan0309（见 §1.1 的注）。
  2. 要不要 @uitachibana3（见 §3 的注）。
  3. 拆 CI 的方案：新 workflow 单独抓 accounts.galgame.yaml → data/items/galgame.jsonl，与主库互不阻塞。这一步不定，名单再准也上不了线。
  4. Galgame 版是「独立一期」还是「主日报里的一个栏目」。独立一期意味着新的期号序列、新的 6 个出口、新的金文件——工作量是主日报的一半。

5 方法与可信度

  • 182 个 handle 全部实查：118（信息号侧）+ 48（厂商侧）+ 16 个空号／404。
  • 重试是必须的：厂商侧 48 个里 13 个需要重试才拿到 200（@Famishin 第 5 次、@kobuichi 第 4 次、@Butch_Gen／@Toshi_Ikebukuro／@hozumik 第 3 次）。按「一次 404 即判死」会误删 8 个活号。
  • 活账号的来源：ja.wikipedia 的 prop=extlinks 命中率最高（12 个），品牌条目的 extlinks 还能捞出 staff 个人号（@Famishin、@rodorin、@rosshii02）。
  • 走不通的路（记下来免得再试）：x.com 直连、Bing／DuckDuckGo（地理重定向到中文无关结果）、api.fxtwitter.com/2/search（返回 {code:404, results:[]}）、/followers 与 /following（404）。
  • 判定口径：不只看名字——要求简介含作品名／公司名，或近 20 条原创属本行业，或与已知厂商号互动。存疑一律丢弃，宁缺勿滥。
