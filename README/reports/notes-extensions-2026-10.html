0 结论先说

你给的三个页面加起来，其实只演示了三样东西：提示框、GitHub 仓库卡、媒体标签。没有表格、没有数学、没有图表——fuwari 那篇 Markdown 拓展全文只有 156 个英文单词，短得超出预期。所以「笔记拓展」这件事比看起来小得多。

1 三个参考页到底给了什么

1.1 fuwari · Markdown Extended

只有两节：

  • GitHub 仓库卡：::github{repo="owner/repo"}。页面里写明「on page load, the repository information is pulled from the GitHub API」——也就是客户端请求，不是构建期生成。
  • Admonitions：note / tip / important / warning / caution 五种，语法 :::note，支持 :::note[自定义标题]，另外也认 GitHub 的 > [!NOTE] 写法。

就这些。整页 156 words，没有表格、数学、mermaid、脚注的任何演示。

1.2 fuwari · Video

这页更直接：没有任何组件。正文就是一句「把 YouTube 或其它平台的嵌入代码复制粘贴进 markdown 文件」，然后一个 <iframe width="100%" height="468" src="https://www.youtube.com/embed/…">。## YouTube 与 ## Bilibili 两个小节下面各只有一个 iframe，没有语法说明、没有参数、没有封面图。

1.3 PaperMod · Audio and Video

Hugo 的短代码：{{< audio src="/path.mp3" >}} 与 {{< video src="/path.mp4" >}}。文中紧接着就给了等价的裸 HTML——<audio controls><source …></audio>、<video controls><source …></video>。也就是说短代码只是省几个字符，产物就是浏览器原生播放器。

2.1 提示框：写法与边界

:::caution[剧透提醒]
本文涉及《边缘行者》与《边缘行者 2》的重大剧透。
:::

渲染成 <blockquote class="callout callout--caution">。五种类型不靠颜色区分（本站只有黑白灰），靠左边线的粗细：note / tip 是 2px，important / warning / caution 是 4px 且用正文色。

三条边界：::: 必须顶格且前后空行；里面不能套提示框；类型名写错不报错，退化成 note——这是故意的，宁可样式不对也不要内容消失。

3 一个必须记住的坑

这是本轮实测出来的，值得单独一节：satteri 的 features.directive 只负责解析，不负责渲染。

只把开关打开、不挂处理器，会发生什么？

# 开 directive、没挂插件时的产物
<div class="prose" data-pagefind-body></div>      ← 整篇正文空了

# 挂上 markdown-admonition.mjs 之后
<div class="prose" data-pagefind-body>
<p>开头这一段是普通段落，应该照常渲染。</p>
<blockquote class="callout callout--note">
<p class="callout__title">说明</p>
<p>默认标题的提示。</p>
</blockquote>
…

构建成功、退出码 0、没有任何警告——只是内容没了。这类「解析类开关」的共性风险是：它改变的是语法树，而语法树到 HTML 那一步缺处理器时不会报错，只会静默丢弃。教训是——凡是打开一个解析开关，都要拿一条真实内容跑一遍产物、肉眼看 HTML，不能只看构建通过。

4 Quartz：是不是只能换架构

是。三条理由：

  1. 它是一个独立的静态站点生成器，不是插件。Quartz 5 要求 Node ≥ 22，流程是 npx quartz create → npx quartz plugin install --from-config → npx quartz build，内容放在它自己的 content/。和 Astro 并存等于两套构建、两套路由、两套部署。
  2. 它的招牌功能都长在「构建期链接图 + 客户端运行时」上。graph view、backlinks、popover 预览、wikilinks、Bases、Canvas——前三个要浏览器端渲染，后三个要 Obsidian 的文件组织方式。搬不过来。
  3. 它是「数字花园」的形态假设。文件夹即目录树、每篇是一个节点、靠 [[链接]] 织网。本站是「栏目 + 时间线」（笔记 / 日报），结构上就不是一个东西。

但有三件事不用换架构也能学：

Quartz 的做法本质本站能不能做结论
Backlinks（反向链接） 构建期扫全站 [[链接]] 与 md 内链，算出「谁引用了这一篇」 能。本站笔记之间已经有互链，扫 md 的链接就能算，纯静态输出一段 HTML，0 JS 值得做
CustomOgImages（satori） HTML/CSS → 图片，所以能在图上排版标题与作者 已经用更便宜的方式做了：scripts/make_og.mjs 只裁图不写字 已学
插件 / 发射器分层 emitter 的职责是「产出一个文件」，配置决定开哪些 已经是这个思路：image-manifest.json、og-manifest.json 都是「构建前算好、提交进仓、页面只读清单」 已有
Graph view / Popover / Wikilinks 客户端渲染 + 全站索引 不做。8 篇笔记画出来的图是 8 个点；popover 要 JS；wikilinks 要改写作习惯 不做

4.1 关于 satori 那件事，值得说清楚

Quartz 的 CustomOgImages 用 satori 把 HTML/CSS 转成图片，默认 1200×630，支持明暗两套、支持 frontmatter 覆盖（优先级：frontmatter 的 socialImage > 自动生成 > 默认图）。这套东西真正的成本不在代码，在字体——satori 要把字形解析成路径，中文标题就得塞一份 CJK 字体进去，动辄几 MB，构建期还要逐字排版。

本站的选择是「只裁图、不写字」：npm run og 把站点背景图切成 1200×630 当全站默认图，把每篇笔记正文的第一张本地图按 attention 裁一张当专属图，清单写进 src/data/og-manifest.json。同一个目标（分享出去能看出是哪一篇），成本是几十行 sharp 调用、0 个字体文件、0 毫秒构建期排版。
