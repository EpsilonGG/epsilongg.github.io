0. 先说结论

1. M5 的难点不是「画图」，是「跨机一致」。 同一份 report.json、同一个模板，在 Windows 和 CI 的 Linux 上必须出同一张 PNG。 决定这件事的不是渲染质量，而是字体能不能钉死。所以选型的第一顺位是「能内嵌固定字体文件」， 不是「谁画得好看」。计划里选 @resvg/resvg-js 就是这个逻辑，不是因为它新。

2. M5 真正值钱的产物只有一张：OG 封面（1200×630）。 它决定「这条链接发到 X / Discord / Telegram 里长什么样」。内页卡片（1080×1440）是加分项， 一期 3 张就够，多了没人翻。如果只做一件事，就做封面 + og:image 接线， 4 个工作包就能上线，不必等 8 个全做完。

3. M6 的产物是五份文本，不是视频；而时长必须先定。 按这一期的真实字数，全文照念 9.7 分钟——对「日报」这个形态太长，没人看完。 精简到「看点 + 作品动态 + 互动 + 前 10 人」是 4.7 分钟，这才是可发布的长度。 这个取舍决定了 M6.1 的口播稿到底从哪几段取材，应该在写代码之前定下来。

为什么不是「无头 Chrome」——它不是慢，是不可判定

计划里的验收标准是「同一份数据两次渲染，PNG 字节完全相同」。无头 Chrome 做不到这一条， 而且失败时你没法判断是自己写错了还是环境变了：Chromium 升级会改字距，系统装了新字体会改 fallback， CI 的字体包和本机不一样会改断行。一条会随环境漂移的验收标准，等于没有标准。

为什么 resvg 能过——它把「字体」变成了输入而不是环境

resvg 是纯 Rust 实现（tiny-skia 光栅化 + fontdb 字体库）， 不给系统字体留后门：你给它几个 .ttf/.otf，它就用这几个，找不到就报错而不是悄悄 fallback。 所以「同一份数据 + 同一个模板 + 同一个字体文件 = 同一张图」这条在它这里是可以成立的， 在 Chrome 和 sharp 那里只能靠祈祷。

一处要更正计划文档：§07 的对比表里写 @resvg/resvg-js 是「WASM」， 实际它是 napi 预编译原生二进制（每个平台一个 .node 文件，npm 按平台装）。 这不影响结论，但影响两件事：① 首次安装会多下几 MB 平台二进制；② 换 Node 大版本时可能需要重装， CI 里最好固定 Node 版本（仓库已经 engines.node >= 22.23.4，够用）。

M5 的三个坑（都会在第一天遇到）

  1. 中文字体不能靠系统。 仓库 public/fonts/ 只有 Inter / Cormorant / Fira Code， 全都没中文。完整的中文字体 5–15 MB，不该进 git——计划的方案是下载到 node_modules/.cache/、 记 SHA、--pin 时校验。这条必须在写模板之前做完，否则模板的折行全是按错字体调的。
  2. SVG 没有自动折行。 <text> 不会自己换行，CJK 也没有空格可断。 必须自己算：全角字符按 1em、半角按 ~0.5em 估宽，标点不能出现在行首（「、。」要跟着前一个字）。 这件事写起来不难，但一定要有单元测试，否则「某期多了一个字就溢出一行」永远发现不了。
  3. 不要自动缩字号。 溢出时缩字号会让同一套模板出两种字号，多页翻起来像两种设计。 正确做法是模板声明容量（最多几行 × 每行几字），超了就截断加省略号——难看但是可预测。

3. M5 的最小可用路径：4 个包，不是 8 个

计划里 8 个工作包是完整形态。如果只想先拿到「分享出去有张图」这个收益，做到第 4 步就够了：

顺序做什么产出验收（可自动判定）
1M5.1 选型验证一段结论 + 一张对照图resvg 出的中文与浏览器截图并排，字形/断行可接受

4M5.4 只做封面模板templates/daily/cover.svg同一期连跑两次 PNG 字节相同
5M5.8 OG 接线og:image 指向封面npm run links 通过；缺图时退回默认分享图

剩下的 M5.5（生成 + manifest）、M5.6（只认 confirmed）、M5.7（稳定性测试）是「内页卡片」需要的； M5.6 那条其实应该提前——没定稿的一期不该能出图，否则图上写的东西和站点上的可能不一致。

可优化点（做的时候顺手就能拿到）

  • 按 claim 粒度做增量：manifest.json 记每页的 claims 路径， 改一条 highlights[1] 只重渲封面，其余页直接复用上次的 PNG。一期 4 页时省不了多少， 但这是「只改一个字也要重跑全部」和「改哪渲哪」的区别。
  • 封面用固定浅色，不跟随主题：站点有背景图模式，但分享出去的图应该永远一样—— 深色主题的人分享出去是浅色封面，这是对的，不是 bug。
  • 图片不进 RSS：计划里已明确不做 <enclosure>，理由成立（部分阅读器会把条目撑变形）。 OG 图只在 HTML 的 <meta> 里出现，不进 feed。

4. M6：三条路线，产物是五份文本

先把边界钉住：M6 不生成音频、不渲染视频。这不是排期问题，是范围问题—— 一旦要出片，项目就从「静态站 + 本地脚本」变成「有渲染管线」，构建时间、机器要求、失败模式全换一套。 判据写在计划里：连续做满 10 期、每期人工制作稳定超过 1 小时，才回头评估配音（仍然不做成片渲染）。

路线怎么来优点缺点结论
A. 纯规则派生 从 report.json 按固定模板拼句子，零模型调用 免费、可复现、跑 100 期都一样 读起来是「把书面语念出来」，没有口语连接词，长句不会拆 做骨架开场/结尾/名单用它
B. 一次模型改写 走现有 prompt → answer → apply 通道，把书面稿改写成口播稿 口语自然；判卷和来源校验现成 每期多一次模型调用；改写可能改变事实（要靠 sources 兜） 主体用它只改 narration，不改事实
C. 分镜级结构化 segment JSON：镜号 / 时长 / 画面类型 / 字幕 / 素材 一个没参与生成的人拿着就能剪 工作量最大；分镜质量取决于对「视频长什么样」的想象，容易做成没人用的字段 先留字段M6.2 之后再填

计划要的五份产物，对应关系是：

产物给谁用从哪来能不能自动生成
narration.md 口播稿念的人 / TTS路线 B 改写能（要判卷）
storyboard.md 分镜剪的人段落 → 镜号 + 画面类型半自动（画面类型靠规则，镜头感靠人）

5. M6 唯一没定的参数：时长

计划末尾自己留了一个问题：「视频稿的时长目标是多少？」——这个数不定，M6.1 就不知道从哪几段取材。 用这一期的真实字数算了一遍（语速按计划里的 5.2 字/秒）：

取材范围字数时长评价
全文（含 52 人）3,0119.7 分钟太长。日报的时效性撑不住 10 分钟，看到第 5 分钟已经忘了开头
看点 + 作品 + 互动 + 前 20 人1,8616.0 分钟偏长，但能接受（相当于一条深度短视频）
看点 + 作品 + 互动 + 前 15 人1,6655.3 分钟合适
看点 + 作品 + 互动 + 前 10 人1,4704.7 分钟推荐 5 分钟以内，前 10 人是当天最活跃的，够用

建议把目标定成「4–5 分钟」，取材固定为「看点 + 作品动态 + 互动 + 前 10 人」。 理由不是审美：这四段正好是页面上顺序固定、且都已带 sources 的部分， 其余 42 人只有一句话，念出来是名单朗读，观众会走。 如果哪一期前 10 人不足 10 个，就按实际人数念，不要补。

6. 用户侧会提的建议（以及该怎么回）

这一节是把「如果读者/观众来提需求，他们会说什么」提前写下来。每条都标了是否采纳和代价， 省得下一个会话重新讨论一遍。

会有人提的建议采纳？理由 / 代价
「分享到 X 的时候能不能有张图，别只有一行灰字」 采纳 这就是 M5 的封面。成本最低、收益最直接，优先做。
「图里的字我想复制」 不采纳 图片本来就不能选字。回应是：图永远配正文，且 alt 写全文摘要——这比「图里能选字」更有用。
「能不能一期一张图就够，别刷屏」 采纳 一期 1 张封面 + 最多 3 张卡片。超过 3 张，读者会当成广告。
「能不能直接听，不要我自己念」 本轮不做 配音会把项目推成「有渲染管线」。缓解：口播稿是纯文本，贴进任何 TTS 就能听；/daily/<id>.txt 现在就能这么用。
「视频有字幕文件吗，我想自己剪」 采纳 M6.3 的 SRT/VTT。注意它不对应真实音频（没有音频），只是剪辑起点，这一点要写在文件头。
「手机上图片会不会糊」 已覆盖 1200×630（分享卡）与 1080×1440（竖版卡片）两档够用。不要 4K：文件大、渲染慢、看不出差别。
「暗色主题下封面能不能也是暗的」 不采纳 分享出去的图应该永远一样。跟随主题会让同一期出现两个版本的封面，缓存和 OG 校验都会乱。
「能不能给我一份今天所有推文的清单」 已有 /daily/<id>.json 里有 people[].sources（item key），但 key 不是链接。真要清单得另开一个出口，成本高、需求弱，先不做。
