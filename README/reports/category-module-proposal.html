调查报告

笔记页底部加「分类」模块，有必要吗？

对照「链接库 · 工具与服务」的模块形态，评估在 /blog/ 底部增加文章分类的收益与代价。

2026-10-24 站点：epsilongg.github.io 结论：暂缓

结论先行

现在不建议做。信息量撑不起来，而且会和现有的标签筛选打架。

全站目前只有 4 篇正式文章。按现有标签切分，最细的一层是「声优 / 剧作 / 画集 / 视觉小说」，每类正好 1 篇——一个每格只装一篇文章的分类格子，和正上方的文章列表是同一份内容。真正值得做的时间点，大约是文章到 12 篇、且至少 4 个主题各自有 3 篇以上的时候。

如果只是想让访客「一眼看到有哪些主题」，有成本低得多的做法（见第 5 节方案 B，约 20 行代码），不必动数据结构。

「访谈」「翻译」是形态标签，四篇全中，做分类时没有区分度；「声优 / 剧作 / 画集 / 视觉小说」是主题标签，但每个只有一篇。也就是说，现在能做出 4 个分类格子，每格点进去只有一篇文章——和列表页本身完全等价。

/blog/ 现在已有什么

  • 站内搜索：标题 / 摘要 / 标签三个字段，实时过滤。
  • 标签筛选：上表 6 个标签全部渲染成按钮，支持多选 AND 组合。
  • AI 整理滑块：默认只看原创与转载，勾选后并入 source: ai 的文章。
  • 分页：每页 10 篇，作用于「筛选后的结果集」，当前文章数不足一页所以控件是隐藏的。
  • 按年份分组：列表主体是 2025 / 2024 / 2023 / 2022 这样的年份小节。

换句话说，「按主题看文章」这个需求，标签筛选已经实现了，而且是 AND 组合、与搜索和分页联动的。再叠一层「分类」，功能上是重复的。

02「工具与服务」这个模块到底是什么

它由 src/components/IconGrid.astro + .icon-grid / .icon-tile 样式构成，8 个条目：

  • 结构：48×48 图标（自带圆角与描边的 2 倍图）→ 名称（0.875rem / 500）→ 一行说明（12px，灰）。
  • 排布：grid-template-columns: repeat(auto-fill, minmax(9.5rem, 1fr))，桌面一行约 5 个，窄屏自动降列。
  • 无图兜底：没有图标时用 monogram（名称前两字）画一个描边方块。

它能成立的前提是：条目都是「有品牌标识的外部服务」，访客靠 logo 就能在一眼之内完成识别。MDN、Astro、ChatGPT 的图标本身就是信息，文字只是补充。

文章分类不具备这个前提：没有 logo，也没有「一眼认出来」的视觉锚点。真套上去，8 个彩色 logo 会变成 4 个一模一样的汉字方块（下节方案 B-1 的模拟图就是这个效果）。

03四个具体障碍

1. 信息量与列表重复

4 个分类，每格 1 篇。用户点进去看到的内容，和他在页面上方刚滑过的列表完全一样。

2. 和标签筛选功能重叠

标签栏已经能做「按主题过滤」，再引入分类，等于同一件事有两个入口、两套命名。

3. 视觉逻辑错位

图标格子的识别逻辑是「认 logo」。文章没有 logo，只能退化成字母块，比文字列表更难扫读。

4. 维护成本翻倍

每篇新文章要同时填 tags 和 category，两套分类法迟早会漂移（同一主题在一处叫「声优」、另一处叫「配音」）。

还有一个位置问题：/blog/ 底部目前是「返回顶部」按钮的落点，列表本身按年份分组已经收尾。在底部再放一个导航模块，等于让访客滑到底之后又被要求做一次选择，而这次选择的结果还是同一批文章。

04三个方案，直接对比

方案做什么改动收益风险
A · 不做
推荐		 保持现状，标签筛选继续兼任「分类」 0 零成本、零维护，界面不重复 访客无法「一眼看到主题全景」，但 4 篇文章本来也一眼看得完
B · 底部「按主题浏览」

06建议

现在选 A：不做。把这次的工作量留给内容——4 篇文章 26,849 字、50 条注释、41 张配图，已经是一份相当扎实的「翻译访谈集」；再加一个每格 1 篇的分类模块，不会让它更像一个栏目，只会让页面多一层噪音。

如果你希望访客明确感知到「这里是有主题的」，那就选 B-2：底部一行「按主题浏览」，20–30 行代码，点击后复用现有标签筛选，不加路由、不改 schema、随时能撤。这是成本最低的折中。

什么时候该升级到 C

  • 正式文章 ≥ 12 篇；
  • 且至少 4 个主题各自 ≥ 3 篇（否则分类页会大面积「只有一篇」）；
  • 且出现了「一个主题横跨访谈 / 翻译 / 随笔等多种形态」的情况——那时分类和标签才真正分工：分类管主题，标签管形态。

到那一步再动手，收益是现在的好几倍，而且不用回头改今天的决定——B-2 的条目结构可以直接升级成 C 的分类入口。

若最终选 C，要改的东西

  1. src/content.config.ts：加 category 字段（枚举，来自配置文件），带默认值，避免旧文章报错。
  2. src/config/categories.ts：分类的 id / 名称 / 描述 / 顺序，和 src/config/ 的「数据只在配置里」约定保持一致。
  3. src/pages/blog/c/[category].astro：新路由，复用 archive-filter 的列表样式；注意「AI 整理」文章默认不列出，这个路由也要遵守同一规则。
  4. src/pages/blog.astro：底部插入分类入口。
  5. src/layouts/ArticleLayout.astro：文章页显示所属分类（可放在标签旁）。
  6. sitemap / RSS 无需改动，新路由会被自动收录；但分类页要自己写 <title> 与描述，别让搜索结果里出现「分类 - 分类」这种重复标题。

以上都不涉及新增依赖，仍然符合「Astro + 原生 CSS + 零后端」的约束。C 的代价不在技术，而在每篇文章要长期维护两个分类字段。

本报告基于 2026-10-24 的仓库状态：4 篇正式文章、6 个标签、/blog/ 已具备搜索 / 标签筛选 / AI 滑块 / 分页；「工具与服务」8 个条目。
