2 · 方向一：把日报的「互动」做厚

2.1 先诊断：现在那 1–2 条算不算互动

翻最近的 Galgame 版正本，互动栏长这样：

  • 「CyberworksKoho 转发 bugbug_info 关于某作原画挂毯样品到货的通知」
  • 「Moepedia_net 转述 POISON_NEW1992 的某作角色介绍」
  • 「getchucom 为 SMEE 某作更新 SD 亚克力立牌特典样本，并继续开放预约」

这三条的共同点是：一个人转述另一个人（或一个号）的公告。前者是放大器链条，后者根本不是互动，只是把一条作品情报换了个说法。题面里「两人以上」的判据被满足得很轻松——两个账号名出现在同一句里就算——于是模型每次都选最安全的写法。

三个成因，按可修程度排序：

  1. 材料里没有创作者。日报只抓 201 个号，其中 179 是品牌官号、22 是信息号；导演、剧本、画师共 203 个账号里 202 个不在抓取范围。真正会互相回应的人（编剧接画师的话、导演感谢声优）根本没有推文进题面。
  2. 转推被压成放大器。dedupe.py 用 identity_key 把转发归并到原作者行，「谁转了谁」只留在 amplifiers 里，不在正文材料里，模型看不见。
  3. 互提材料太稀。461 个号、9,007 条推文里只有 698 次名单内提及，96% 是转推；非转推的 29 次里，很多还是「转发时顺带 @ 了原作者」。也就是说，即使明天就把 202 个创作者加进抓取，今天的缓存也生不出丰富的互动。
所以第一步不是写规则，是改抓取与题面。只改 prompt 的「互动」定义，模型仍然只能从同样的转推里挑句子，结果不会变。

2.2 三步走方案

第一步 · 有控制地把创作者请进抓取

不要一次加 202 个。按名单 1-1 的档位和互提边打分，先挑 20–30 个：

  • 优先第一、二表 ① / ② 档（7 天内有发言的：导演・剧本 67 行、画师 73 行），他们当天有材料的概率最高；
  • 优先在互提边里出现过的号（缓存里已有 337 条有向边，如 pulltop_latte → will_ensemble 18 次、ammolite_game → appetite_game 17 次、poison_ex1992 → poison_new1992 17 次）；
  • 每个号按惯例配 filter（drop_kinds:["repost"]、max_items:3–5），防止个人号日常灌进题面；
  • 分类建议新增 category: creator（周报 class_priority 已经有 creator 这一级，语义对得上），并在 categories[] 里登记标签；若不想动栏目，可暂用 category: info + tags:["创作者"]，但这两种做法都要同步改测试里钉死的 handle 集合。

代价要如实算：一期题面已经是 200–500 条。新增 30 个号、每号 3–5 条，约增加 90–150 条材料，token 量涨 20–40%。先按 20 个试两期，看互动栏是否真的变厚，再决定扩到多少。

第二步 · 预计算「互动候选」，别让模型在几百条里找

出题脚本时，把互提关系先算好，作为题面里独立的一节（例：## 互动候选），每条给 item key、发言方、被提及方、原文。模型只需要从候选里选，而不是从全部材料里发现：

候选规则（从缓存 / X-Reader 条目算，均可复现）
1. A 引用 B 且附自己的话      → 强候选（引用推文，正文非空）
2. A 回复 B                   → 强候选（RSS 的 "R to @" / reply_to 字段）
3. A 原创里 @B 且非公告模板    → 中候选（排除 "発売/予約/セール" -only）
4. A 与 B 同日提同一作品       → 弱候选（归入 highlights，不占互动名额）
纯 RT、单向转述公告             → 直接排除，不算互动

现有解析层已经留下 is_quote / is_reply 标记，但缓存的 content 只留标题、引用正文被丢掉。要落地这一步，需在抓取适配层把 引用正文与回复对象保留下来（或直接在 X-Reader 侧读 quote / reply_to 字段）。这一步动的是 scripts/daily/，属于保护集，必须先登记豁免。

第三步 · 把「互动」从一种写法拆成四种

在 prompt 里给判据和例子（简中、≤60 字、sources 至少两个来自不同账号的 item key）：

类型判据例句
回应 / 致谢引用或回复，且内容有具体事「编剧 A 引用画师 B 的新立绘，说角色表情改了三版」
同场 / 共演两条材料指向同一场活动、同一天「导演 A 与声优 B 同日晒出试玩会后台合照」
同一作品两端名单 1-1 里同一作品的不同岗位「某作编剧 A 与原画 B 先后谈同一段剧情的取舍」
跨媒体呼应X 官宣 + B 站中文社区反应「官号公布新作后，B 站号当天转发了 PV 评论」（B 站名单独立文件，只做材料不写进 X 名单）

同时在 validate.py 里加一条硬校验：interactions[] 的 sources 必须指向 两个以上不同账号 的 item key，否则判失败。这样「一句话里塞两个账号名」的取巧写法会自动被拦下。

保护集提醒：scripts/daily/、data/daily/、schemas/report.schema.json 都在日报保护集里。改 prompt 模板、校验脚本或 schema 之前，必须在 tests/daily-protection-waivers.json 登记路径、日期与理由；改完 prompt 还要把 PROMPT_VERSION +1（当前 5），否则缓存继续用旧题面。提交后 diff 归零，清空豁免登记。

3 · 方向二：让周报的「业界动向」能上线

3.1 不是没数据，是三道开关没开

三处都在 weekly/rules.json（不在日报保护集，可单独改、可回退）：

  1. publish.disabled_display_columns 删掉 "业界动向" —— 发布层不再整栏剥除；底层三栏和 91 处断言都不用动。
  2. default_excluded.columns 改成 ["作品情报","品牌动向"] —— 无作品名的业界条目不再被「未标注作品」默认删掉；只排除另两栏。
  3. prefilter.keep_if 补 記事 / レビュー / 速報 / ニュース / スクープ / 発表会 —— 现有词表有「業界/业界/采访/考察」但漏了媒体稿件的常用词，bugbug_info 的评价类信号进不了自动入稿桶。

04 号周报的筛选结论仍然有效：创作者身份 ≠ 业界信源。之前 187 个 Galgame 号里 23 个带「经常聊业界信息」标签，逐条看完真信源只有 bugbug_info（記事/レビュー/ランキング/速報）与 aikouka23（流通/廃盤/版本考据）；18 个被标成「业界号」的创作者全是个人号，一个都不能用。

3.3 栏目内部建议分层

业界动向整栏上线后，建议按五个子题写，而不是混成一段流水账：公司与人事（解散、移転、人事）、渠道与流通（廃盤、流通、回収）、平台与展会（Steam、DLsite、WePlay、Messe）、奖项与排行（萌奖、销量榜）、本地化与翻译（汉化、译入语、母语审校）。这五类正好对应 prefilter.keep_if 现有的词，不需要另建分类体系。

上线节奏：先只改三处 rules.json，连看 2–3 期质量；业界栏偶尔空栏是正常现象，不要为了填满而放宽 keep_if。若长期太薄，再按 A/B 级扩源，且每加一号都要在名单 1-1 里写明理由。
