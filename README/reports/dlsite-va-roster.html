0. 先说结论

你要的是「销售额 + 发售作品数前 100 的声优」。这两件事的可获得性差很多，先说清楚：

1. 「按销售额排名的声优榜」不存在官方版本。 DLsite 男性向（maniax）没有声优列表页，声优名只作为作品信息的一部分写在作品页里。 这是 swsem 那篇统计文章自己写明的事实（「DLsiteの男性向け（同人）には、声優名の一覧ページがありません」）， 也是它能做起来的理由。所以没有任何官方数字能把「销售额」归到某个人头上。

2. 能拿到的只有两个替代口径。 作品数（有现成数据库，可复现，2026 年数据）和 销量 proxy （有人拿「历史销量前 100 部作品」反推声优排名，2023 年数据，只列到 top15）。两者衡量的不是同一件事。

3. 推特三号（主号／小号／告知号）我只填核实过的。 100 人 × 3 个号 = 300 个 handle，公开网络上没有这样一份清单，逐个搜也验证不了。 我不会猜 handle——错的 handle 会让你的日报去抓陌生人的账号。目前核实到 12 人， 其余留空并给出补齐方法。

3. 为什么「小号／告知号」几乎全是空的

不是没查，是这三类号的性质不同：

  • 主号相对好找：DLsite 作品页、Ci-en 创作者页、サークル 的推文里经常直接写。
  • 小号（裏垢／サブ垢）大多故意不与主号互链。能确认的路径只有两条： 本人在主号上公开说过，或两个号在同一时间发同一张图。靠名字相似度去猜是错的， 而且会把完全无关的人卷进来。
  • 告知号（告知専用／作品用）只有部分人有。很多人的做法是「主号 + Ci-en」， 没有第三个号——所以这一列空着往往是事实，不是缺数据。

还有一条我刻意没做的事：不把同人音声名義和现实身份对应起来。 这个行业里很多人用与公开活动完全分开的名義，这是她们的劳动条件，不是待解谜题。 清单只记「她本人公开用于宣传的账号」，不去做跨名義的身份归并。 你建 roster 时也建议守同一条线：只加那些自己在公开场合挂出来的号。

补齐剩下 88 人的三条路（按效率排）

  1. 先看 swsem 的作品页 → 找サークル → 看サークル的 X。 表 A 最后一列就是每个人的作品页，点进去能看到「よく出演するサークル」。 サークル 发新作时几乎一定 @ 声优，从那里能拿到最准的 handle。
  2. Ci-en 创作者页。很多声优自己开了 Ci-en，页面侧栏直接挂 X 链接。 搜 site:ci-en.dlsite.com <人名> 命中率很高。
  3. 最后才用 X 搜索。直接搜人名，认「置顶／简介里写了作品名」的那个号。 注意同名不同人极多（尤其两三个汉字的名字），必须用作品名交叉验证。

补完之后建议的落地方式：把这张表当成候选池， 人工筛过的才写进 src/config/daily-roster.json 的 accounts， 每个号加 active 与 category 两个字段——这样以后分类视图和增量抓取都能直接用。

4. 六个轻量化日报项目，各自值得借什么

下面六个都确认仓库可访问（2026-10-25 实测）。不引用 star 数：静态页拿不到，未认证 API 会被代理 IP 限流， 与其写个大概不如不写。

4.1 vikiboss/60s — 60s API

你已经在参考的那个。核心不是「60 秒读完」，而是架构：

  • 生产与渲染彻底分离：抓取跑在 Actions，产出静态 JSON，CDN 缓存，接口只负责读。
  • 一份数据多种 encoding（?encoding=json|text|image）。
  • LLM 只在生产侧跑，请求时永远不碰模型。

能借：「一份数据多种出口」正是你分类／综合两套视图的理论基础。 别借：image 版（要渲染引擎，和零依赖冲突）。

4.2 newsnext/newsnow — 实时热榜阅读器

注意：原来的 ourongxing/newsnow 现在 301 到 newsnext/newsnow，作者换了组织，引用时用新地址。

  • 每个数据源一个适配器文件（server/sources/*.ts），加源不改核心逻辑。
  • 前端只读 API，不自己抓。

能借：源适配器这个结构。你现在只有 X 一个源， 但 digest 已经在读 items/ 下所有 *.jsonl，以后加 RSS／YouTube 时 一个源一个文件 + 统一 NormalizedItem，比在 daily_digest.py 里堆 if 好得多。

4.3 bobkingdom/TrendRadar — 多平台热点 + 推送

这个最值得你细看，因为它把推送模式拆成了三种：

  • 当日汇总（daily）：推当天所有匹配内容，包含之前推过的。
  • 当前榜单（current）：推当前榜上的，持续在榜的每次都出现。
  • 增量监控（incremental）：只推新增，零重复。

能借：「增量监控」正好对应日报最本质的问题——今天谁有新动态。 你现在的 people[].summary 留空即省略，本质就是手动版增量；上了 roster 之后 可以让脚本按「上次出现时间」自动跳过连续几天没动静的人，省 token 也省版面。 另外它用关键词频率做热点排序（纯确定性计算，不花 token）， 这个思路可以拿来给 highlights 排序——先算哪几条被多人提到，再交给模型写。

4.4 imsyy/DailyHotApi — 热榜 API

  • 数据与页面彻底分开，API 先行；
  • RSS 是一等输出，不是事后补的；
  • 零服务器（Vercel / serverless）。

能借：「RSS 一等公民」。你的日报现在不进 RSS，理由是怕改变现有订阅者的收件内容—— 那就另开一条 /daily/rss.xml，和 blog 的 feed 分开，谁想订谁订。 JSON 同理（/daily/<date>.json），对应 60s 的 encoding 思路。

4.5 YeeKal/ai-daily — AI 新闻聚合与推送

  • Python 3.12 + uv，systemd 定时（dnews-push.service 按 push_cron 触发）；
  • 按板块分组，另外生成「跨板块洞察」——当天最早一次推送额外触发；
  • LLM key 走 .env，不进仓库。

能借：这个「板块分组 + 跨板块洞察」就是你要的分类视图 + 综合视图， 而且它给出了一个很实用的工程细节：洞察只在每天第一次跑的时候生成一次， 后面几次复用——避免同一天反复调模型。这条直接可以搬。

4.6 yiduobianhua/daily60s — 每天 60 秒读懂世界

极简到极致：一个 main.py + 一个 workflow，fork 后在 Secrets 里配好就能跑。

能借：「fork 即用」的部署体验。你的项目定位是给人 fork 的个人站， 日报这条链路如果能做到「fork 后只改 accounts.yaml 就能跑」， 比现在「本地跑 Python + 本地跑 WorkBuddy + push」三步要友好得多。 但别照搬「全自动」——你刻意保留本地 LLM 那一步是为了能审校，这个取舍是对的。

另外你点名的 juya-ai-daily：github.com/imjuya/juya-ai-daily 目前 404。 仓库已删除或改名，我没法看源码。能确认的只有它的产出物形态： 「概览 → 要闻」的顺序（先用几句话总起来，再分条展开）、一天一条带日期、 同一份内容分发成文章／视频／RSS。本轮日报的「今日看点放最前」就是照这个顺序做的。

5. 落到你这个项目，最值得先做的五条

  1. 把「增量」当成一等概念。TrendRadar 的三种模式里，只有增量模式回答了 「今天有什么是新的」。roster 加上 lastSeen，连续 N 天没动静的人不占版面。
  2. 先用确定性规则排序，再交给模型写。哪几条被多人提到、谁和谁互相 @， 这些都能算出来（TrendRadar 的关键词频率、你自己的 interactions 抽取）。 模型只负责把已经排好的事实写成句子，highlights 的质量会稳很多。
  3. 洞察一天只生成一次。ai-daily 的做法：第一次跑生成跨板块洞察，后续复用。 你现在每天只跑一次，但上了分类视图之后会变成「一次生成 N 个类内看点 + 1 个全局看点」， 这时候缓存就必要了。
  4. 源适配器化。newsnow 一个源一个文件。你已经在读 items/*.jsonl， 趁现在只有一个源，把「源 → NormalizedItem」这层抽出来，以后加 RSS 不用改核心。
  5. RSS / JSON 另开出口，不动现有 feed。DailyHotApi 把 RSS 当一等公民。 日报单独一条 /daily/rss.xml，订阅者自己选。

6. 顺带回答：「分类页只保留最新一期」是什么意思

这是我上一版方案里没写清楚的一句话，现在方案文档里已经补了一节。意思是：

分类页的路由里没有日期。 /daily/asmr/ 永远显示 ASMR 这一类 最近一天的内容，第二天被覆盖，旧内容不另建页面。

对比另一种做法 /daily/<date>/<category>/（每天每个分类各一页）：

做法30 天 × 6 分类的页数随天数
/daily/<date>/<category>/30×6 + 30 + 1 = 211线性增长
/daily/<category>/（最新一期）6 + 30 + 1 = 37分类部分恒定

纯静态站里，页数直接等于构建时间和 npm run links 的检查量。 211 页里有 180 页是「上个月的分类」，实际没人翻。

代价是看不了「10 月 20 日那天 ASMR 分类都有什么」。 补偿办法不是补页面，而是在 /daily/<date>/ 上做客户端分类筛选—— 和笔记页 archive-filter.ts 的标签筛选同一套思路，当天的内容本来就在那一页里。 真要归档，JSON 输出里也有全量数据。
