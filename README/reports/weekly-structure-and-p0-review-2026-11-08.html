1.3 为什么会被分到两个层级

三条原因，都不是随手放的：

  1. 运行方式不同。weekly_studio 的调用形式是 python -m weekly_studio，Python 只会在 sys.path 根上找这个包名。它必须待在仓库根，否则 -m 找不到。而 scripts/weekly/ 是被 scripts/weekly.py 这个门面「先塞 sys.path 再 import」的，天然属于 scripts/。
  2. 责任边界不同。A 套有 publish.py——它是唯一能把稿子写进 data/weekly/ 的代码；B 套从设计上就拒绝发布（连子命令都不给）。放进同一个包里，「能不能发布」就从包级约束降级成模块细节，保护语义会被稀释。
  3. 出生时间不同。A 套是 2026-11-04 的 M1–M5 交付；B 套是 11-06 夜起为绕开「日报保护集零改动」另起的旁路。B 套刻意不改 A 套一行，所以只能另立一个包。

顺带一个命名坑：scripts/weekly.py（门面）与 scripts/weekly/（包）同名。import weekly 一定解析到包，所以门面里只能写 from weekly.xxx import。这个坑在 scripts/weekly.py 的注释里已经写明了——合并目录时它是第一个会踩的雷。

P0-2 那句「A 档偏斜、全 L0」用了两个内部术语，先解释清楚，否则没法判断。

术语一：A / B / C 档 = 自动选稿的分数档

每个事件按 docs/weekly-report.md §7.2 算一个分，然后分三档：

档分数线自动初稿怎么用全览
A≥ 14 分全选，但最多 14 条（超出的降级到 B）全列
B8 – 14 分按分降序取前 6 条全列
C< 8 分不选全列

「A 档偏斜 167 / 21 / 0」的意思是：255 个事件里 167 个都够到 A 档（65%），21 个 B，C 档一个都没有。而 A 档只取 14 条——也就是说「A 档」这个标签完全没起到筛选作用，实际起作用的只是「按分数排前 14」。你要判断的是：这种「绝大多数都算重要」的评分口径能不能接受，还是要把分数线抬上去。

术语二：L0 / L1 / L2 = 背景段的三级降级

成稿里每个作品下面有一段背景（厂牌、发售日、平台）。这段内容按「证据强度」分三级，写不出就不写：

L0 自证消息来自该厂牌自己的官方号（category == manufacturer 且 handle 对得上）厂牌、发售日、平台
L1 双源信息号的说法 + VNDB 的厂牌归一相等，发售日差 ≤ 7 天厂牌 + 发售日
L2 单源只有 VNDB，或标题靠前缀猜什么都不写

「全 L0」的意思是：20 条成稿的背景段全部停在一句话级别（厂牌 / 发售日 / 平台），没有一条走到 L1 那种「两个来源互相印证后可以说得更细」的状态。你要判断的是：这个深度够不够发——如果够，L1 那套交叉验证就可以先不做；如果不够，就得回头补 L1 的触发率。
