日报的 token 成本：一次 5.2 万，能压到多少

用 2026-10-25 那一期的真实数据实测，不是估算。

样本：127 个账号、去重后 342 条推文，briefing 原文 91,874 字。
计数：tiktoken o200k_base（GPT-4o/4.1 系列编码）。对日文混合文本， Claude 与 Gemini 的分词结果与它相差约 ±10%。
测量日期 2026-10-26。

52,552输入 token / 期
5,565输出 token / 期
178 万每月（30 期）
31%压到最低时的占比

0. 先说结论

1. 成本几乎全在输入，而且大头是「读起来没用」的东西。 一期约 5.9 万 token，其中输入 52,552、输出 5,565、写作规范 1,200。 输入的 13% 是每条推文后面那行 https://x.com/…/status/…——成稿根本不用它，页面上的链接是从 handle 拼的。

2. 最有效的一招不是截断，是换一份输入。 把 briefing 压成「编辑视图」（去 URL、去互动数、去纯转发、每账号挑带公告关键词的条目）， 5.25 万直接掉到 1.19 万，省 77%，而写稿要用的信息一条没少—— 这一期就是这么写的，成稿质量没有下降。相比之下，按账号硬截到前 2 条只能省 52%， 而且会丢掉话多的人的关键公告。

3. 现在的 174 万/月，压到 52 万/月只需要改一个默认参数。 压缩脚本已经写好并在用了（scripts/daily_condense.py）， 现在缺的只是「让自动化默认走压缩路径，而不是整篇读」。

1. 一次日报的钱花在哪

先把「一次」拆开。日报这一步的输入有两块：briefing 全文，和写作规范 （docs/daily-report-guide.md 的要点 + 四段格式说明，约 1,200 token，固定开销）。 输出就是填好的那四段加 114 行「详细」。

2. 七个方案，实测

同一份 briefing，七种喂法。都按「单期总成本 = 输入 + 输出」算，输出恒为 5,565。

#方案输入单期合计相对现状每月（30 期）评价
A现状：全量 briefing 52,55259,317100%178 万 最贵
BA − status URL 45,62152,38688%157 万 零损失
CB − 互动数 43,22749,99284%150 万 零损失
DC − 纯转发 38,64345,40877%136 万 丢掉「本人没说话但转了」的那部分
ED + 每账号只留前 2 条 25,13531,90054%96 万 会漏掉第 3 条之后才发的发售公告
Fdaily_condense 3/90 14,89721,66237%65 万 本报告在用关键词优先，不会漏公告
Gdaily_condense 2/70 11,89118,65631%56 万 最省这一期的成稿就是这么来的

F 和 G 的区别只在两个参数：每账号最多显示几条、每条截到多少字。它们不是「截断」， 因为带公告关键词的条目会被优先挑出来，不受条数上限约束—— 所以「她今天发了一条发售公告，但排在第六」这种情况不会漏。

为什么 E（按账号硬截断）不推荐： --per-account 是按「互动数 + 时间」排序取前 N 条。抓取里互动数经常整排是 0， 于是稳定排序把它退化成「当天最早 N 条」——下午发的发售公告会整段消失。 这个坑之前踩过一次，已从默认行为里去掉。F/G 换成「关键词优先」才没有这个问题。

3. 对免费额度意味着什么

免费档位通常按「每月多少 token」给，各家差别很大，所以这里只给倍数，不给具体厂商的额度：

每月额度A 现状C 零损失F 3/90G 2/70
50 万超 3.6 倍超 3.0 倍超 1.3 倍略超 1.1 倍
100 万超 1.8 倍超 1.5 倍够，余 35%够，余 44%
200 万够，余 11%够，余 25%够，余 68%够，余 72%

也就是说：只要月额度在 200 万以下，现状就是紧的—— 一次失败重试、一次补录两期，就会顶到上限。压到 G 之后，同样额度下能跑两倍的量。

4. 还有三个不靠改格式的杠杆

  1. 降低频次。日报不必每天出。周一到周五出、周末合并成一期，期数从 30 降到 22， 成本同比例降到 73%。代价是存档的颗粒度变粗，而「期号 = 发布时间」这个约定正是为了细颗粒度存档。
  2. 缩「详细」的篇幅。输出里 80% 是 114 行每人一句。只给「当天确实有事」的人写， 其余留空不渲染，输出能砍掉一半左右（约 −2,500 token/期）。这条不影响输入，随时可以改。
  3. 两阶段写作。先只喂压缩视图让模型挑出「今天值得展开的 10 个人」， 再只把这 10 个人的原文喂第二次。总量约 1.2 万 + 0.4 万 = 1.6 万，比 G 略高， 换来的是这 10 个人能看到全文而不是截断版。只有在「关键信息常出现在长推文后半段」时才值得。

5. 已经落地的部分

压缩脚本已经写好了，就是这份报告里 F/G 两行用的那个： scripts/daily_condense.py。它做四件事，全是规则、不调模型：

  • 去掉每条推文后面的 status URL
  • 去掉 [❤N 🔁N] 互动数
  • 默认丢掉纯转发（--keep-rt 可保留）
  • 每个账号先挑「带公告关键词」的条目，再按原顺序补到上限

自动化现在就跑在 G 这一档（--per-account 2 --width 70）。 想换成 F 或别的档位，改自动化提示词里那一行参数就行，脚本不用动。

剩下唯一没动的，是 briefing 本身的生成——它仍然把全量原文写到 out/<期号>.briefing.txt 留档。这份留档不花钱（不喂模型）， 出事时能回头查「当时到底抓到的是什么」，建议保留。

6. 建议

选项做什么月成本适合
保持现状不改，整篇读178 万额度 ≥ 300 万，且不介意等
只做零损失项briefing 生成时就不写 URL 和互动数150 万想少改，但收益有限（−16%）
默认 G就用现在的压缩脚本，2/7056 万推荐：质量已验证，省 69%
G + 缩「详细」再给 people 设个条数上限约 49 万想让页面更短，顺带省钱

我的建议是默认 G，暂时不碰 A 到 E 那些格式层面的改动。理由： G 已经在真实数据上跑过一期，成稿和「整篇读」写出来的没有质量差别； 而 B/C 这类「只删 URL」的方案虽然零风险，但省下的 16% 不足以改变额度档位， 不值得为它改一次 briefing 的生成逻辑（改了还要重新对齐测试和留档格式）。
