# 译文用语规范

[← 返回仓库首页](../README.md) ｜ [写作指南](blog-guide.md) ｜ [项目说明](project.md)

这份文档管两件事：**同一个词怎么译**，和**同一类句子怎么写**。
它和 `data/glossary.json` 是一对：词表管「词」，这份文档管「句子和标点」。

为什么需要它：译到第 20 篇时，真正拖慢速度的不是生词，是「上次那个词我怎么译的来着」。
把口径写死，第 20 篇和第 2 篇才像同一个人写的。

---

## 1. 三个文件，各管一段

| 文件 | 管什么 | 谁改 |
| --- | --- | --- |
| `data/glossary.json` | 词：日文原词 → 本站统一译法，附「不该出现的写法」 | 每篇译完补几条 |
| `README/translation-style.md`（本文） | 句子：标点、人称、数字、敬语、台词的写法 | 很少改，改之前先想清楚 |
| `src/content/blog/<slug>.md` | 单篇的实际取舍 | 随时 |

术语表是**可执行的**：`npm run check:glossary` 会统计每个词的出现次数，
并把「明确不该出现的写法」列出来。它不判断译得好不好，只判断**一致不一致**。

```bash
npm run check:glossary            # 报告，永远退出 0
python scripts/check_glossary.py --strict   # 有异形就退出 1，可接 CI
python scripts/check_glossary.py --term 声优  # 只看一条
```

## 2. 词：术语表怎么用

**译之前**：打开 `data/glossary.json` 当词表扫一遍。里面有的词，照 `zh` 写，不要临场发挥。

**译之后**：把这篇新出现的、以后还会遇到的词补进去。一条三行：

```json
{ "ja": "立ち絵", "zh": "立绘", "avoid": ["站姿图"], "note": "作画环节，保留原词。" }
```

三条纪律：

1. **`avoid` 只放「明确错」的写法**，不要放「我不太喜欢」的写法。
   放太宽会天天报警，报警多了就没人看了。比如「配音」是动词、「声优」是职业，
   两者都合法，就不该把「配音」写进 `avoid`。
2. **一条一个概念**。「シナリオ（剧本）」和「スクリプト（脚本）」必须分开，
   混在一条里，检查器就分不清程序脚本和作品文本。
3. **`note` 写「为什么」，不写「是什么」**。是什么看 `zh` 就知道，
   值得写下来的是「为什么这里不能用另一个词」。

## 3. 句子：已经定下来的写法

### 3.1 标点

| 场景 | 写法 | 说明 |
| --- | --- | --- |
| 普通引用、强调 | 弯引号 `"…"` | 全站统一，不用直角引号 `「」` 做普通引用 |
| 作品内 UI、台词、专有名词 | 直角引号 `「…」` | 让读者一眼分清「这是游戏里写的」和「这是作者在说」 |
| 作品名 | 书名号 `《…》` | 系列名不拆：《沙加 frontier2》不写成《沙加》frontier2 |
| 插入语、语气中断 | 破折号 `——` | 访谈里的 `――` 一律转成 `——` |
| 省略、迟疑 | 六点省略号 `……` | 不用三点 `...`，也不用 `。。。` |
| 数字范围 | `3–5`（短横）或 `3～5` | 不用 `3~5`：半角 `~` 成对出现会被渲染成删除线 |

### 3.2 中英混排

- 中文与英文/数字之间**留一个半角空格**：`Astro 7`、`2026 年 10 月`、`X-Reader 抓取`。
- 英文专有名词保持原样，不音译：`Nitter`、`Steam`、`itch.io`。
- 日文人名首次出现给假名，之后只写汉字：`新島夕（にいじま ゆう）` → 后文「新岛夕」。

### 3.3 人称与敬语

- 访谈提问者用「——」，受访者用「名字：」，**不写「记者：」**。
- 日语的「〜氏」不译成「该氏」，直接写名字；需要敬称时用「先生 / 女士」，全篇统一。
- 第一人称按人物口吻走：角色说「俺」译「我」，不硬加「老子」这类方言味，除非原文明确是方言。

### 3.4 台词与图注

- 台词保留原文的断句节奏，**宁可短，不要为了通顺把两句并一句**。
- 图注：翻译原文 `figcaption`；原文没有就写一句「这张图在说什么」，句末带句号；
  不加 `▲`、不加「图：」前缀。详见 [写作指南 4.5](blog-guide.md)。

### 3.5 不确定的地方

用注释，不要用括号硬塞。写法见 [写作指南第 5 节](blog-guide.md)：

```markdown
原文这里用的是「〜じゃ」，是老年男性角色的固定语尾[^1]。

[^1]: 日语虚构作品里的「役割語」，用特定语尾标记角色属性。中文没有完全对应的手段。
```

## 4. 怎么积累（这是重点）

术语集不是「整理出来的」，是**每篇顺手攒出来的**。三步，每步都不超过五分钟：

**译前（2 分钟）**：`npm run check:glossary` 看一眼现有词表；把这篇会反复出现的 5–10 个词先定下来。

**译后（3 分钟）**：把新词补进 `data/glossary.json`。判断标准很简单——
**这个词如果下次译错，读者会觉得「前后不是一个人」吗？** 会，就补；不会，就别补。
词表膨胀到 200 条也没人看，60–80 条是能真正用起来的量级。

**每月一次**：跑 `npm run check:glossary`，看「异形」列。
有异形 → 要么改正文，要么把那个写法收编为正式译法（说明当初的规则定错了）。
**规则服从语感，不是语感服从规则。**

### 为什么不自动抽取

试过用分词 + 频次自动提候选词，结果是满屏「作品」「游戏」「先生」。
术语的价值在「有争议」，而争议只有人知道。所以这里只做**检查**，不做**抽取**：
机器负责「你说过的和现在写的不一样」，人负责「哪个才对」。

## 5. 什么时候该改这份文档

- 同一类句子连着三篇都写得不顺手 → 是规则错了，改规则。
- 某个 `avoid` 连着三篇都误报 → 是词表太严，删掉那条。
- 新开一个内容方向（比如开始译小说而不是访谈）→ 单独加一节，不要改访谈那一节。

改完记得跑一次 `npm run build` 和 `npm run check:glossary`，
确认没有把已经发布的文章改成不合规的样子。
