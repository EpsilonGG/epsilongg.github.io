实现方案：AI 整理发布文章

为 EpsilonGG 个人主页（Astro 静态站）提供「区分 AI 整理 / 原创」内容的可选方案 · 仅作提案，尚未实现

调研说明（关于 eryuemu.com）： 通过公开抓取，eryuemu.com 首页仅能取到简介区（二月木的个人博客，主修自动化，记录折腾大模型 / WSL2 / Linux / eSIM / QQ 机器人 / 书法与二次元），其「最近文章」列表疑似由前端 JS 渲染，抓取结果未包含文章条目与任何 AI 相关标签；其标准 /sitemap.xml、/rss.xml 也未能在该地址取到。
因此下文不依赖对 eryuemu 内部实现的还原，而是基于「静态站点 + 内容集合」的通用做法，给出一套可落地的方案；若你后续能提供该站某篇具体的 AI 整理文章链接，方案可进一步对齐。

1. 什么是「AI 整理发布文章」

通常指作者用大模型参与「采集 → 摘要 / 翻译 / 重写 / 校对 → 排版发布」中的部分或全部环节，但仍由人把关、署名与归档的内容。与之相对的是完全原创（手写）的文章。区分的核心目的有二：

  • 透明度：让读者知道哪些内容是 AI 协助 / 整理过的，满足诚实署名与平台规范。
  • 检索 / 订阅偏好：让读者能只看重原创，或只看 AI 整理的速览 / 译文。

2. 通用做法（静态站点常见）

无论哪类静态生成器，思路一致：在文章元数据里加一个「来源 / 是否 AI 协助」字段，构建时据此渲染徽章、提供筛选或独立栏目，并在 RSS / SEO 中保持透明。

  • 元数据字段：frontmatter 里加 source: ai / source: original，或布尔 aiAssisted: true。
  • 徽章展示：文章卡片（列表页）与文章页头部显示 AI 整理 标签。
  • 筛选 / 独立栏目：列表页加一个「仅看 AI 整理」开关；或单独开一个 /ai/ 栏目。
  • RSS 分轨：可选提供只含 AI 整理文章的订阅源。

3. 给本项目的实现方案

本项目已有「笔记」（/blog/ 列表，支持搜索、标签筛选、分页）与文章页。在此基础上做区分，影响面小、可渐进。

3.1 数据模型

在 src/content.config.ts 的 Zod schema 里新增一个可选字段（兼容现有文章，不填默认为原创）：

source: z.enum(["original", "ai"]).default("original")
// 或轻量写法： aiAssisted: z.boolean().default(false)

文章 frontmatter 示例：

---
title: （译）xxx 专访
description: 由 AI 协助翻译与校对的访谈整理
pubDate: 2026-03-01
tags: [访谈, 翻译]
source: ai            # 新增：标明为 AI 整理 / 协助
---

3.2 展示层（徽章）

在「笔记」列表的每一条、以及 ArticleLayout.astro 文章头部，依据 source === 'ai' 渲染徽章：

{post.data.source === 'ai' && (
  <span class="article-badge">AI 整理</span>
)}

CSS 沿用现有设计 token（黑白灰、6px 圆角），徽章用细边框 + 小号字，不引入强调色。

3.3 两种路线（二选一或并存）

路线做法优点代价
A. 轻量标签 直接把 AI 整理 作为普通标签；复用现有标签筛选栏即可「按标签筛选」。 零 schema 改动、零新 UI；立刻可用。 语义弱（和普通标签混在一起），无法做「仅看 AI / 仅看原创」的互斥切换。
B. 独立字段 + 徽章 + 开关 新增 source 字段，列表页加一个「仅看 AI 整理」切换，文章页显示徽章。 语义清晰、透明、可做互斥筛选与潜在独立栏目。 改 schema + 列表页筛选逻辑 + 文章页头部，工作量中等。
推荐：先做 B 的徽章部分（透明度收益最大、改动最小），筛选 / 独立栏目作为可选项后续再加。

3.4 与现有搜索 / 标签 / 分页的集成

  • 搜索与标签筛选逻辑集中在 src/scripts/archive-filter.ts，按 DOM 上的 data-* 工作；若要支持「仅看 AI 整理」，可在每个列表项上挂 data-source="ai"，并在该脚本里加一个互斥开关（AND 组合，与现有逻辑一致）。
  • 「每页 10 篇」的分页已作用于筛选结果集，新增筛选不会影响分页结构。
  • 若做独立栏目（如 /ai/），可参考现有 /blog/[slug].astro 与列表页，用 getStaticPaths 生成；但需注意与「笔记」列表的路由不冲突（例如用 /blog/ai/ 或单独的 /ai/）。

3.5 RSS 与 SEO 注意

  • 若提供「仅 AI」订阅源，建议在 rss.xml.ts 里新增一个带查询/路径的源，并在页脚说明，避免读者混淆。
  • 无论用哪种路线，都应在文章显著位置（徽章 + 文末说明）标注 AI 参与程度，符合各平台对 AI 生成内容的披露要求。

4. 工作量与决策清单（供决定是否做）

  1. 是否要做区分？ 当前仅 1 篇译文，区分的价值有限；若后续 AI 整理内容增多，再做更划算。
  2. 路线选择： A（标签，零成本）还是 B（字段 + 徽章 + 开关）？
  3. 是否需要独立栏目 / 独立 RSS？ 还是仅在列表与文章页标注即可？
  4. 披露措辞： 统一用「AI 整理 / AI 协助 / AI 翻译」中哪一个，规则写进写作指南 README/blog-guide.md。
