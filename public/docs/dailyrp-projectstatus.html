00这份文档管什么、不管什么

范围就是你给的那句话：「日报的代码基础（即除了数据源账号群选择之外的内容）」。 把这句话翻译成能验收的东西，就是下面这张表。

在范围内在范围外
源适配器接口、统一内容模型、日报 Schema、增量状态、输出路径、版本规则 决定关注谁、关注多少人、怎么分组
跨源去重、增量筛选、确定性排序、分类字段、待生成数据导出 每个账号属于哪个分类（结构由 M2 定义，内容是数据）
分类摘要 / 今日看点 / 全局洞察的生成通道、校验、确认、缓存 摘要写成什么调性（那是提示词和审校的事，不是代码的事）
站点、独立 Feed、JSON、文字导出 页面视觉改版（现有版式够用，M4 只换数据源）
图片生产、视频稿的结构与导出 配音、视频渲染（M6 明确不做，见 8.4）

为什么要把这条边界写死。「选谁」和「怎么生产」是两件耦合度极低的事， 但混在一起做就会互相拖：名单还没定，采集就没法测；采集没测，名单也没法验证。 先把机器造完，名单是一份 JSON，填进去就能跑。机器对名单的要求只有一条： 每个 handle 必须能映射到一个分类，映射不上就进「其他」并告警。

三个贯穿全程的约束

脚本不调模型

模型是外部角色。脚本负责「出题」和「判卷」，不负责答题。CI 里零 API key、零服务器这条不能破。

构建期不联网

抓取发生在别处，构建只读仓库里的文件。构建慢一点可以，构建时断网必须还能出站。

每个里程碑可独立发布

做完 M2 的站点要和做完 M1 的一模一样，不能出现「等 M3 完成才能上线」的中间态。

盘点时发现的三个既有问题

这三个不是假设，是拿仓库里的 213 条样例数据实测出来的。写在这里是因为它们正好各自对应 M2 的一个工作包——里程碑不是凭空排的，是从具体毛病倒推的。 三条现在都已在 M2 修掉（① M2.1、② M2.2、③ M2.4），下面保留原始记录。

① 按 UTC 分天，边界上的推文进错日报

_date_of() 拿到带时区的时间戳后直接 .date()，取的是 UTC 日期； 但期号用的是 JST，脚本顶部也写着「用 JST 才不会把深夜的推分错天」。两者对不上。

实测：以 2026-10-23 为例，正确窗口（JST 自然日）有 28 条， 脚本实际取到 26 条——数量看着只差 2，但集合差 8 条： 5 条被漏掉（10-23 凌晨 00:10–07:53 JST 发的）， 3 条被错收（其实是 10-24 凌晨的）。

已修 M2.1（2026-10-25）：新增 window.IssueWindow， Item.date() 一律换算到 JST 再取日期，窗口是半开区间 [当天 00:00, 次日 00:00)。同一个 10-23 现在是 28 条、账号集合不变。

② 同一条推文被两个账号收录，被当成「互相扩散」

样例里 item_id 2113601516565311503 出现两次，publisher 分别是 re_re_tsubame 和 mirai_chiroru，canonical_url 却指向不同账号， 两条的 is_retweet 都是 true、retweeted_by 都是自己。 也就是说：同一条推文，两个账号各转发了一次。

现有链路把它算成两件独立的事，于是 26102322 那期写下了「两位发了同一段说明，等于互相帮着扩散」—— 读者会以为是两个人在互相呼应，实际是同一条内容被转了两次。 正确的模型是一条内容 + 一组传播者（amplifiers）， 这样「谁帮着扩散」照样能写出来，但不会被误读成两个独立发言。

已修 M2.2（2026-10-25）：dedupe.merge() 按 source + native_id 合并， 重复项不丢、账号并进 amplifiers。这条推现在跑出来是 1 条内容、2 个传播者。

③ 「按互动排序」实际上等于按文件行序

build_briefing() 用 likes + retweets 排序取前 5 条， 但样例里 metadata.stats 全是 {}，等于全部 0 分。 Python 的排序是稳定的，全 0 就原样保留输入顺序——实际顺序就是 JSONL 的行序， 而 JSONL 的行序取决于抓取时的返回顺序，不是任何有意义的东西。

这条的教训不是「排序写错了」，而是排序键必须在文档里写死，并且不能依赖一个可能为空的字段。 M2 的排序键定为 (published_at, source, native_id)，互动数只作为同一秒内的次级参考。

已修 M2.4（2026-10-25）：order.py 固定三级键；账号顺序改成名单序， 不再按当日条数——同一天的账号顺序不该取决于谁话多。

已修 2026-10-25：build_briefing() 的每账号 5 条上限整个拿掉。 抓取从来没截过，被截的只是喂给模型的那一段——一天发 10 条的人，模型只看得到 5 条。 现在默认全给，需要压 token 时用 --per-account N 显式收窄。

三条都关掉了，但不是同一天关的。① 在 M2.1 就能修，因为它不依赖任何新模型—— 时间戳本来就在，只是被算错了。②③ 必须等去重与排序模型落定，先改等于在旧结构上打补丁。 这就是「先修结构，再修行为」的实际含义。

三条排序原则

  1. 单向依赖。只允许后面的里程碑依赖前面的，不允许回改前面已验收的接口。 发现前面设计错了，就改接口 + 版本号，不要在调用方打补丁。
  2. 每个里程碑结束时站点必须能发布。M1–M4 期间站点一直读旧数据， 直到 M4 一次性切换。中间任何一步停下来，线上都是好的。
  3. 数据向后兼容。每个里程碑都要能读上一个里程碑写出的文件。 schema_version 只在破坏性变更时加一，加字段不算。

03M1 · 架构与数据协议

M1 架构与数据协议 第 1 期

输入相同的标准化数据，能够生成结构一致的日报数据。

为什么先做这个

现在所有的「数据」都以两种形态同时存在：X-Reader 的原始 JSONL，和手写在 Markdown frontmatter 里的四段。 中间没有协议，所以每一环都只能靠人眼对齐。M1 要做的就是把这个中间层固定下来—— 一旦「一个条目长什么样」「一份日报长什么样」被写进 schema， 后面五个里程碑就都变成「按协议填内容」，而不是「再想一遍数据结构」。

这一步不产生任何用户可见的变化。这是刻意的：M1 的正确性只能用测试证明，不能用浏览器证明。

三份 schema 各自管什么

文件管谁写谁读
item.schema.json 一个标准化条目 适配器 M2 采集、去重
report.schema.json 一份日报的全部字段 M3 合并、M4 迁移 M4 站点、M5 图片、M6 视频稿
generation.schema.json 模型回答的形状（M3 用） 模型 M3 校验

为什么不装 jsonschema。整套脚本目前零第三方依赖， 这是它能被 CI 在任意机器上跑起来的原因。三份 schema 只用到 type / required / enum / minLength / maxLength / pattern / items / properties 这八个关键字， 写一个 120 行的校验器比引一个依赖划算——而且报错信息可以写成中文、带上文件路径。 schema 文件仍然是标准 JSON Schema，以后想换库随时能换。

04M2 · 采集、增量与排序

M2 采集、增量与排序 第 1 期

重复运行不会产生重复条目；迟到数据与旧内容可以正确区分。

为什么这一步最难

「去重」听起来是个技术活，实际上是个语义决定：同一条推文被两个人转发， 算一件事还是两件事？昨天发但今天才抓到的推，算今天的还是昨天的？ 这些决定一旦写错，后面 M3 写出来的摘要会跟着错，而且错得很自然—— 读者看不出来，只有对过原始数据的人才知道。

§1 的三个问题全部落在这一步。M2 结束之后，它们应该都消失。

进度：M2 已完成（2026-10-25）。七个工作包全部落地， 新增 window.py / dedupe.py / incremental.py / order.py / roster.py / export.py 六个模块， 外加 src/config/daily-roster.json 与 31 条测试。

顺序是刻意的：先切窗、再判态、最后去重。 判态必须在去重之前——账本按 key 记，同一条内容的多条记录要各自判一次， 否则「第二次运行跳过多少条」会随去重实现漂移（先合并的话 28 会变成 27）。

实测：--date 2026-10-23 从 26 条变 28 条（去重后 27 条内容）， 连跑两次第二次 skipped_duplicate 正好 28； 2113601516565311503 现在是 1 条内容、amplifiers 长度 2； 未知 handle 归 other 且 stderr 一行告警，不抛异常。 全量 Ran 147 tests ... OK。

关键设计

五种状态，各自有去处

「增量」不是「只要新的」，而是把每一条都归到一个可解释的类别里， 然后决定这一类进不进今天的日报。这个表就是 M2 的验收标准。

状态判定进日报？去处
new 在窗口内，key 未见过 进 正常条目
duplicate 在窗口内，key 已见过且内容 hash 未变 不进 计入 counts.skipped_duplicate
updated 在窗口内，key 已见过但 hash 变了（编辑、补图） 进 覆盖旧版本，留 previous_hash
late 发布时间早于窗口起点，但第一次见到 不进当天 late[] 记录，可补进对应日期的未确认期
future 发布时间晚于窗口终点（时钟偏差或时区写错） 不进 隔离到 quarantine[]，构建日志告警

「迟到」和「旧内容」的区别就是 first_seen。 一条 10 月 1 日的推，如果 10 月 1 日就抓到了，那它是「旧内容」，属于 10 月 1 日那一期，今天重跑应该判 duplicate； 如果 10 月 25 日才第一次抓到，那它是「迟到数据」，不能塞进 10 月 25 日的日报—— 读者会以为今天发生了什么旧事。正确做法是进 late[]，由人决定要不要补一期历史。

去重的身份键

按优先级取第一个可用的：

  1. source + native_id——最强，同一条推就是同一个 native_id
  2. canonical_url 归一化后——给没有稳定 id 的数据源兜底
  3. sha256(account + normalized_text + published_at 到分钟)——最后一道，只用于无 id 无 url 的情况

前两条命中时，不丢弃重复项，而是把它的 account 追加进 amplifiers。 §1 问题②里的那条推文，去重后是「1 条内容、2 个传播者」，而不是「2 条内容、0 个互动」。

排序键

items  : (published_at, source, native_id)      # 三级，保证同一秒内也稳定
accounts: roster.index(handle)                  # 名单序，不按当日条数
people  : (category.index, roster.index)        # 类内按名单序
categories: roster.categories 的声明顺序

刻意不把互动数放进主排序键。样例数据的 stats 全是空的， 真数据里也经常缺失；把一个可能为空的字段放进排序键，等于让输出顺序随抓取质量漂移。 互动数只在 M3 选「哪几条值得写」时作为参考，不影响输出的结构。

    { "id": "seiyuu", "label": "声优" },

这一步的形态：出题与判卷分离

整套方案的前提是「CI 里不跑模型」。所以脚本不能自己调用模型，只能做两件事： 把该问的问题整理成文件，和把回答验一遍再合并。 模型（本地 WorkBuddy）是夹在中间的一个外部角色，它读文件、写文件，脚本对它一无所知。

M2 产物generate.json → daily prompt出题 → WorkBuddy答题 → daily apply判卷 → daily confirm定稿

这个形状有个副作用，而且是好的：整个生成过程可以被完整重放。 out/<id>/prompt/ 和 answer/ 都在，出了问题能查到 是题出错了还是答错了，而不是「模型今天状态不好」。

关键设计

模型回答的形状

回答是纯 JSON，不是 Markdown。原因：要校验就得有结构； Markdown 里抽结构等于用正则解析自然语言，迟早出错。 

{
  "category": "seiyuu",
  "summary": "…",                                  // 分类摘要
  "highlights":   [ { "text": "…", "sources": ["x:2113…"] } ],
  "interactions": [ { "text": "…", "sources": ["x:2113…", "x:2114…"] } ],
  "people": [
    { "handle": "asuparama40", "summary": "…", "sources": ["x:2113…"] }
  ]
}

三条硬规则（校验器执行）

  1. 没有来源的句子不收。sources 为空、或引用了不存在的 item key， 整份回答判失败。这条防的是模型「补一句听起来合理的话」—— 日报是转述，不是创作，每句话都得能指回一条推文。
  2. handle 必须在名单内。模型不许发明账号。 不在名单里的 handle 直接报错，而不是静默丢弃——静默丢弃会让一个账号连续几天消失而没人发现。
  3. 长度上限。description ≤ 50 字（和现有 schema 一致）、 单条 summary ≤ 60 字、highlights 2–4 条。 超限报错，不自动截断——截断会把一句话截成语义不通的半句。

定稿与重跑

操作对 draft对 confirmed
apply 合并 拒绝，提示先 --reopen
confirm 全部分类已 apply 且校验通过 → 置 confirmed 幂等，不改 confirmed_at
reopen 无意义，拒绝 当前版本存进 history/<n>.json，状态回 draft
render-images / script（M5 / M6） 拒绝 允许

history/ 的意义是「确认过的版本永远不消失」。 定稿之后发现某句写错了，走 reopen 改完再 confirm， 旧版还在 history/1.json 里，能 diff 出改了什么。

缓存键

input_hash = sha256(
    category_id
  + sorted(item.key + item.content_hash for item in 该分类条目)
  + prompt_template_version
)

只跟「输入内容」和「提示词版本」有关，跟时间无关。所以重跑同一份数据不会重算； 改了一句提示词会让所有分类失效（prompt_template_version 加一），这是想要的。

出口闸门 · M3

confirm 之后 apply → 退出码非 0； reopen 之后 apply → 成功，且 history/1.json 存在、内容等于 reopen 前的 report。

  • 不实现 map-reduce 的并行调度。串行跑 4–8 个分类已经够快，并行会把「哪一步失败」变复杂。
  • 不做自动重试。判卷失败就把错误给人看，人改完再 apply——自动重试会把「模型理解错了」变成「多试几次碰对了」。

关键设计

数据放哪

const dailyReports = defineCollection({
  loader: glob({ base: './data/daily', pattern: '*/report.json',
                 generateId: ({ entry }) => entry.split('/')[0] }),

三个理由：① 构建期就是读文件，不联网、不需要额外 loader； ② Zod 校验在构建期跑，字段写错直接让 npm run build 失败并指出文件； ③ report.json 进 git，改一句摘要就是一个可 review 的 diff。

先解决「渲染器」这个前置问题

现有文档里写过「不做图片版，因为要引入渲染引擎」。M5 要做，就必须先把这个矛盾解决掉， 否则第一个工作包就会卡住。结论：用 SVG 做版式、用 WASM 光栅化、用固定字体文件。

方案依赖跨机一致中文结论
无头 Chrome 截图 本机已有 差（版本/字体都影响） 好 否 只适合人工预览
sharp 渲染 SVG 已是 devDependency 差（走系统字体） 看机器 否 中文要系统装了字体

关键在字体随仓库外置固定、按 SHA 校验，而不是「用系统里有什么就用什么」。 同一份数据 + 同一个模板 + 同一个字体文件 = 同一张图，这条是 M5 验收的全部内容。

仓库现有的 public/fonts/ 只有拉丁字重（Inter / Cormorant / Fira Code）， 没有中文字体。所以 M5.2 必须单独解决字体：下载到 node_modules/.cache/， 记 SHA，不进 git——一个完整的中文字体是几 MB 到十几 MB，不该躺在仓库里。

关键设计

「版式稳定」怎么定义

不是「看起来差不多」，而是三条可以自动判定的性质：

  1. 字节稳定。同一份 report.json + 同一模板 + 同一字体，两次渲染的 PNG 字节完全相同。
  2. 局部性。改一条 claim，只有包含它的那一页图片 hash 变化，其余页不变。
  3. 不溢出。任何一页的文字都在安全区内——靠模板容量上限 + 硬截断保证，不靠肉眼检查。

第 3 条是设计出来的，不是测出来的：每个槽位声明「最多几行、每行最多几字」， 超出就截断并加省略号。绝不用自动缩字号——那会让同一套模板出两种字号， 多页卡片翻起来像两种设计。

可追溯

// manifest.json（和图片放在一起）
{
  "issue": "26102322",
  "report_hash": "sha256:…",         // 渲染时 report.json 的指纹
  "template_version": 3,
  "font_sha": "…",
  "images": [
    { "file": "cover.png", "size": [1200, 630],
      "claims": ["highlights[0]", "highlights[1]"] },
    { "file": "card-01.png", "size": [1080, 1440],
      "claims": ["categories[seiyuu].summary"] }
  ]
}

claims 记录「这一页的每个字是从哪条 claim 来的」，claim 又指向 item key。 所以任何一张图都能反查到推文——这就是「来源可追溯」在图片这一层的意思。

manifest.json 里每个 claims 路径都能在 report.json 里取到值。

任意一页图片的最长一行文字不超过模板声明的容量（用脚本数，不靠肉眼）。

本里程碑不做

  • 不做「自动配图」——不用模型生成插画、不抓账号头像做拼贴。图片只承载文字版式。
  • 不做在线模板编辑器。模板是 SVG 文件，改模板就是改文件。
  • 不把图片塞进 RSS。<enclosure> 会让部分阅读器把条目撑变形，收益不明。

08M6 · 视频稿与后续自动化

M6 视频稿与后续自动化 第 3 期

稿件结构完整，每段内容能关联来源，人工可以独立完成后续制作。

这一步产出的是「稿」，不是「片」

M6 的边界要划得很清楚：输出五份文本，交给人去做视频。 口播稿、分镜、字幕文本、画面提示、素材清单——这五样齐了，一个没参与生成的人 拿着它们就能把片子剪出来。这既是验收标准，也是范围边界。

工作包

关键设计

一段稿子的结构

{
  "index": 3,
  "kind": "highlight",          // open | category | highlight | outro
  "narration": "…",             // 口播稿，口语，可直接念
  "duration_est": 18.5,         // 按字数/语速估算，人工可改
  "subtitle": ["…", "…"],       // 按呼吸点切成 1–2 行
  "visual": {
    "type": "card",             // card | quote | profile | blank
    "ref": "images/daily/26102322/card-02.png"
  },
  "sources": ["x:2113…", "x:2114…"],
  "notes": "…"                  // 给剪辑的人看的提示，不念
}

时间轴怎么来

不做强制对齐（forced alignment），那是另一套工具链。用字数 ÷ 语速估算， 语速默认 5.2 字/秒，写进配置；估算值直接写进 duration_est， 人工改了就以人工的为准（重跑不覆盖已手改的字段）。

这意味着字幕不会自动对上真实音频。这是有意的取舍：自动对齐需要音频， 而 M6 不生成音频。字幕文件的作用是「给剪辑软件一个起点」，不是成品。

出口闸门 · M6

对一期已定稿日报跑 script → script.json 通过 schema 校验，segments 非空。

每段的 sources 非空，且每个 key 都在对应 report 的条目集合里。

subs.srt 能被 VLC / 剪辑软件识别，时间轴单调递增且无重叠。

assets.md 里列出的每个路径，要么存在，要么明确标 missing。

人工 dry-run：只看 script.md + assets.md， 写下「第一镜拍什么、第二镜配哪张图」，过程中不需要问任何问题。

本里程碑明确不做

不做自动配音，不做视频渲染。这不是「以后再排」，是本轮不做。 理由：两者都会把项目从「静态站 + 本地脚本」推成「有渲染管线」，构建时间、机器要求、 失败模式全部换一套；而 M6 的产出（五份文本）已经能让人独立把片子做出来。

什么时候再评估：连续做满 10 期视频，且每期人工制作时间稳定超过 1 小时， 说明瓶颈确实在「配音 + 剪辑」而不是在「稿子」。到那时再谈，也只考虑配音，不考虑成片渲染。

09推进协议：一个里程碑一次

这一节是给「怎么执行」定的规矩，比上面任何一节都重要。 六个里程碑一次性生成出来的东西，大概率是六个都能跑但彼此不兼容的半成品； 一个一个来，每个都能停在可用状态。

每个工作包的完成定义

一个工作包算「做完」，要同时满足四条。少一条就是没做完，不许开下一个。

  1. 代码在仓库里，不是只在对话里。
  2. 有测试覆盖，并且测试能因为「改坏了」而失败——不是只跑通一次。
  3. 整套闸门通过：npm run check、npm run build、npm run links、npm test、npm run test:md。
  4. 写进构建日志：docs/daily-build-log.md 追加一条，记工作包编号、实际命令输出、遗留问题。

每个里程碑的收尾

动作内容
跑验收 逐条执行本节里程碑里「出口闸门」列的判据，把实际输出贴进构建日志，不写「应该通过」
跑全量闸门 上面五条命令，全部贴输出。Python 测试数、Node 测试数、页面数都要记下来
提交 一个里程碑一个 commit，message 里写清「M<n> 完成」+ 验收结论
发布 推上去，等 GitHub Pages 生效，抽查一个真实 URL。M1–M3 站点不变，也要抽查——证明「没变」
回写本文档 把该里程碑的工作包表加一列「状态」，把闸门里的数字改成实测值

四条禁止

不许跨里程碑预写

做 M2 的时候不要顺手把 M3 的校验器写了。可以留 TODO 注释，不要留半成品实现——半成品比没写更危险，因为它看起来是能用的。

不许回改已验收的接口

M1 定下的 Item 字段，M4 想加字段只能加，不能改名。要改名就升 schema_version 并写迁移。

不许让站点进入「等下一步」状态

任何一次提交后 npm run build 都要能出站。M4 的切换是唯一一次「数据源换血」，它必须在一个 commit 里完成，不留中间态。

不许跳过闸门「先往下做」

闸门不过就停下来修。跳过闸门省下的时间，会在下一个里程碑以三倍还回来——因为下游会开始依赖一个错的东西。

如果中途要停

每个里程碑结束时都是干净的停点。停之前把构建日志写完，写清「下一个工作包是哪个、当时在想什么」。 重新开工时先读日志，不要靠回忆。

M1、M2、M3 结束时站点完全不变，M4 结束时站点换了数据源但页面一样。 所以哪怕只做到 M2 就停，得到的也是一个能用的、更可靠的老日报——不是一堆废代码。

11红线与反模式

这些是「一旦做了就要推倒重来」的东西，写在这里当检查表用。

红线为什么违反的典型症状
脚本里不出现模型 API 调用 CI 零 key 零服务器是整套方案的前提 CI 需要配 secret；本地跑不动；构建时间随模型响应抖动
构建期不发起网络请求 断网必须还能出站 构建偶发失败；换网络就挂
模型不许写 URL 链接由 handle 拼，模型没机会写错 页面出现 404 的 x.com 链接；npm run links 报外链
已确认版本不被覆盖 存档的意义就是「发出去的东西不会变」 同一期 URL 前后内容不一致；读者看到的和 feed 里的不一样
中间产物不进 public/ public/ 原样拷进 dist，会直接上线 线上出现 /out/26102322/briefing.txt
now() 不进产物（除 provenance） 否则「同输入同输出」永远不成立 可复现测试永远失败，只好把它关掉
输出顺序不依赖文件系统顺序 不同机器 glob() 返回顺序不同 同一份数据在两台机器上生成不同顺序的日报
不引入数据库 纯静态 + 纯文件是这套方案能被维护的原因 需要备份、需要迁移、需要服务
不在 dist 里手写文件 下次构建会被清掉，且绕过校验 「本地好的，推上去就没了」
M4 验证通过前不删 src/content/daily 它是当前唯一的线上数据源 删早了，站点构建直接失败或日报全空

待定问题（不影响开工，但要有人定）

  1. 分类体系最终几个类？M2 只需要结构，可以先给 2–4 个占位类。 真名单进来之前定不下来，也不该现在定。
  2. 目标规模是 30 人还是 100 人？影响 M3 要不要一次就上 map-reduce。 现在的设计两个都能跑（分类数决定 map 次数），但 100 人时单分类内的条目量要再压一次。
  3. 要不要 /daily/<category>/ 分类页？ scaling plan 把它排在扩容二期，本文档的 M4 没排。 如果确定要，它属于 M4 之后的独立小里程碑，不塞进现有六个里。
  4. 视频稿的时长目标是多少？M6 的 segments 数量和语速都受它影响。 先按「3–5 分钟」写，真做一期再校准。
  5. data/daily/<id>/history/ 要不要设上限？ 一期改三五次是常态，无限累积会让仓库变大。倾向保留最近 5 个版本。

这五个问题都不用现在回答。它们的共同点是：答案会随真实使用变化， 现在猜一个反而会把设计锁死。每个里程碑的闸门里都留了「回写本文档」这一步， 到时候一起改。
