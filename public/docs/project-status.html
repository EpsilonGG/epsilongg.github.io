01一句话结论

站点已经完整可用：五个固定页面、一条文章路由、一套设计系统、一条 CI 流水线、 一套文档和一套脚本，全部跑通且互相对得上。它的定位是一个编辑型个人主页—— 首页是名片，不是博客；文章是名片上的补充说明。

真正缺的不是功能，是规模。当前所有设计都建立在"文章不超过十篇"这个前提上： 没有列表页、没有分页、没有标签页、没有搜索、没有文章内目录。一旦文章过二十篇， /archive/ 会变成一条无限长的列表，读者只能靠浏览器查找。

能用

7 个页面全部 200；构建 0 报错；astro check 36 个文件 0 错 0 警 0 提示；22 个测试全过；两次线上部署已验证。

能改

个人信息、链接、文案都在 src/config/；颜色字号间距在 tokens.css。改内容不碰组件。

能复制

README/fork.md 把"改成你自己的"拆成五步，最小改动只需换 5 个文件。

不能扩

内容规模化那一层（列表／分页／标签／搜索／TOC）完全空白，而且是刻意的——项目书 B-3.0 明确规定了首页顺序和不设 /blog/ 列表页。

03逐项说明

每一项都给出：做了什么、关键文件在哪、以及还剩什么。

3.1 页面与路由 src/pages/

四个固定页面加一条动态路由，全部静态预渲染：

  • / 首页：简介 → 站点导航 → 最近文章 → Footer，顺序固定
  • /me/ 名片：简介、主要平台、关注领域、项目、经历
  • /morelinks/ 链接库：5 组、2 个子栏目
  • /archive/ 归档：按年份分组的全部文章
  • /blog/{slug}/ 文章详情，文件名即 URL
  • /404、/robots.txt（路由生成，不是静态文件）、/rss.xml、/sitemap-index.xml

trailingSlash: 'ignore' 配 build.format: 'directory'， 线上 URL 一律带尾斜杠。所有内链写成根绝对路径 /xxx/， 这意味着站点只能部署在域名根路径。

剩余：没有分页；没有 /blog/ 列表页（项目书规定）。
3.2 设计与排版 src/styles/tokens.css · 91 行

所有颜色、字号、间距、圆角、行宽都只在 tokens.css 定义，组件里不允许写死数值。 视觉规则：黑白灰、无强调色、常规圆角统一 6px（徽章 2px 是唯一例外）、无阴影、中文不用斜体。

三套字体，全部自托管、只含拉丁子集，合计 105 KB： Cormorant Garamond（标题衬线）、Inter（正文无衬线）、Fira Code（等宽）。 中文走系统字体栈，不下载中文字体。

剩余：CJK 字形在 macOS / Windows / Linux 上不一致，标题观感会飘。
3.3 内容与数据配置 src/config/

约定是"JSON 是数据源，同名 .ts 只做类型包装"，这样 Python 同步脚本能直接读 JSON， 不需要解析 TS。目前四个数据源：site.json（站点名、域名、语言、起始年、OG 图）、 profile.json（姓名、简介、头像、社交链接）、navigation.json（导航项）、 links.ts（链接库，因为是带联合类型的结构化数据，直接用 TS 更省事）。

剩余：about.ts 是纯 TS，不符合"JSON 数据源"的约定，Python 脚本读不到它。 当前没有脚本需要读，属于已知不一致。
3.4 链接库 src/config/links.ts · LinkBlock.astro

五组：平台、项目、工具与服务、研究、常用链接。常用链接下再拆两个子栏目—— GitHub（5 位朋友，带头像）和 ACG 资源（12 条，一排五个的按钮墙）。

五种排版：卡片（LinkCards）、图标网格（IconGrid）、列表（LinkList）、按钮墙（BadgeWall）、单行（LinkRow）。 LinkBlock.astro 按 layout + fallbackLayout 做分发和降级， 所以某个组数据不全时会自动退到更简单的排版，不会渲染出空洞。

剩余：34 个图标是手工抓取的 PNG（多数 64×64，工具类 96×96），源站换 favicon 不会自动更新； VNDB 和南+论坛只提供 16×16 图标，用 CSS 字母块代替位图。
3.5 博客与 Markdown src/content.config.ts · astro.config.mjs

Content Collections + Zod。字段：title（必填）、pubDate（必填）、 description、updatedDate、tags（默认空数组）、 draft（默认 false）。另外有一条跨字段校验：updatedDate 不能早于 pubDate。

Astro 7 默认用 Sätteri 处理器，所以 GFM 脚注开箱可用，不需要装 remark-gfm。 代码高亮用 Shiki 双主题（github-light / github-dark）， defaultColor: false 让颜色交给 CSS 变量，跟随站点主题切换。

剩余：tags 字段收集了但没用起来——没有标签页、没有按标签筛选； 草稿只能改成 draft: false 才能预览。
3.6 注释（脚注弹层） 本轮新增 article-notes.ts · 101 行

写法就是标准 GFM 脚注：正文里 文字[^1]，文末写 [^1]: 注释内容。 点击正文里的上标，页面底部滑出一块面板显示该条注释，右上角有 × 可关闭； 文末仍然保留完整的注释列表。

  • 关闭方式三种：× 按钮、Esc、点面板外部
  • 关闭后焦点回到刚才点的标记，aria-expanded 同步复位
  • 点标记不会跳转锚点（location.hash 保持为空），读者不会丢失阅读位置
  • 面板里的「注释 N」序号和文末列表一一对应，克隆自文末节点并去掉回跳箭头
  • JS 失效时退化成原生脚注：上标仍能跳到文末列表

现有一篇访谈里的 8 条「译注」已全部改成脚注，打开 /blog/rurudo-unreal-interview/ 就能直接看效果； 标记的点击热区做过外扩，视觉尺寸不变但更容易点中。

剩余：面板最高 45vh，超长注释要在面板内滚动；窄于 480px 时面板几乎占满屏幕。
3.7 图片图注 本轮新增 src/lib/markdown-figure.mjs · 62 行

最短写法：![alt](图片路径 "图注文字")——Markdown 的 title 就是图注。 构建时一个 hast 插件把"独占一个段落、带 title 的图片"升级成 <figure> + <figcaption>，并把 title 从 <img> 上摘掉，避免和浏览器 hover 提示重复。

需要精确控制尺寸时手写 <figure class="article-figure"> 也可以， 现有那篇访谈的 11 张插图就是这么转的。图片统一放 public/images/blog/<slug>/。

剩余：只处理"独占段落的图片"。行内图片、多图并排、被链接包住的图片都不会生成图注。
3.8 主题与可访问性 theme.ts · BaseLayout.astro

亮/暗双主题：默认跟随系统 prefers-color-scheme，可手动切换，选择记在 localStorage。页面 <head> 里内联了一小段同步脚本， 在首次绘制前就把主题类名写上去，所以不会闪白。

可访问性做了这些：.skip-link「跳到主要内容」、注释面板 role="dialog" + aria-labelledby + 焦点管理 + Esc、 主题按钮带 aria-pressed、图片全部有 alt、 prefers-reduced-motion 下关掉滑入动画。

剩余：没做过屏幕阅读器实测；对比度没用量化工具核过；移动端只验到 500px 宽（Chrome headless 的下限），没上真机。
3.9 性能 dist/ · 1.7 MB

产物 1.7 MB 的构成：图片 1.4 MB、字体 105 KB、HTML 与 CSS 合计约 175 KB。 CSS 打成单文件 24 KB，没有任何外部 JS 文件——脚本量太小，Astro 全部内联了。

文章页一共 4 个 <script>：1 个在 head 里防主题闪烁，3 个 module （主题切换、阅读进度、注释面板）。没有客户端框架、没有 hydration、没有第三方请求， 字体和图标都是自己的。图片带 loading="lazy" 和显式 width/height 防布局抖动。

剩余：图片没转 WebP/AVIF、没做 srcset，这一项能从 1.4 MB 压到 400 KB 量级。
3.10 部署与 CI .github/workflows/

GitHub Actions → GitHub Pages，push 到 main 触发，也可以手动 dispatch。 流水线跑 npm ci → npm run check → npm run build， 类型不过就不发布。权限收到最小（contents: read / pages: write / id-token: write），并用 concurrency 保证同一时间只有一个部署任务。

仓库是用户站 EpsilonGG/epsilongg.github.io，所以不配 base，域名即根路径。

剩余：Actions 列表里偶尔有一条 pages build and deployment 失败，那是 GitHub 内置构建 与自定义流水线打架，不影响发布结果，属于已知无害项。
3.11 脚本与测试 scripts/ · tests/

sync_profile_readme.py（445 行）把 profile.json、 navigation.json 和文章列表同步进主页 README 的三个 marker 块里。 三个 marker 的顺序固定，脚本幂等（重复运行结果不变），写入用"临时文件 + 原子替换"， 所以中途失败不会留下半截文件。--check 是严格只读模式，可以用来做 CI 校验。

tests/test_readme_sync.py（287 行）覆盖 22 个用例，包含 marker 缺失、 顺序错乱、内容为空、日期格式化等边界。全部通过。

剩余：测试只覆盖 README 同步，站点本身没有自动化测试。
3.12 文档 README/ · public/docs/
  • README.md（根）：主页名片 + 文档导航，内容与 GitHub 主页 README 大致一致
  • README/project.md：目录结构、路由、配置项、写文章、部署与排查
  • README/blog-guide.md：frontmatter、图注、注释的写法、发布前清单、给 AI 的提示词
  • README/fork.md：从 fork 到上线，含"必须部署在根路径"的警告
  • public/docs/github-profile-readme-guide.html：主页 README 搭建与维护
  • public/docs/project-status.html：本页
为什么两个指南放 public/docs/：GitHub 不渲染 .html，只会给出源码。 放进 public/ 后由站点托管，链接是可读的网页。

05可优化点

按"什么时候必须做"分三档。成本是粗估的工程量，不是日历时间。 P0 的共同点是：不做，文章一多就会难受。

P0 · 内容变多之前必须做
P0 文章列表页 + 分页 成本 中

新建 /blog/ 列表页，或者给 /archive/ 加分页。 注意这会推翻项目书 B-3.0 里"不设列表页"的约定——真要做得先改约定， 否则以后会反复纠结"到底该不该有"。实现上 Astro 静态分页（paginate()）即可，不需要额外依赖。

P0 文章内目录（TOC） 成本 低

render() 的返回值里已经带 headings，直接渲染成侧栏或可折叠块就行， 零新增依赖。现在那篇访谈两百多行，没有目录只能靠滚动。

P0 补一个 LICENSE 成本 极低

建议代码与文字分开授权：代码用 MIT，文章与图片用 CC BY-NC-SA 4.0。 页脚已经写了"未经同意禁止转载"，但没有 LICENSE 文件，法律上仍然是"保留所有权利"的默认状态，边界模糊。

P1 · 体验明显提升
P1 图片优化：WebP + srcset 成本 中

这是投入产出比最高的一项。构建时把 public/images/blog/ 下的图转成 WebP 并生成多档宽度， 1.4 MB 能压到 400 KB 左右，首屏会明显变快。可以用 sharp 写个构建前脚本，不必上 Astro 的图片组件。

P1 图注插件扩展 成本 低

在 markdown-figure.mjs 里再认两种结构：被 <a> 包住的图片（a > img）， 以及连续多张独占段落的图片（自动合成一个 grid figure）。插件只有 62 行，改起来很轻。

P1 窄屏注释降级 成本 低

窄于 480px 时，把底部面板换成"原地内联展开"或全屏 sheet。 纯 CSS 加一段媒体查询 + 一个类名切换就能做到，不用改交互逻辑。

P1 标签页 成本 中

tags 字段已经在 schema 里了，缺的是 /tags/{tag}/ 路由和标签索引页。 文章少于十篇时收益有限，超过二十篇时几乎是必需品。可以等文章攒够再一次性做。

P1 站内搜索 成本 中

Pagefind 在构建后扫一遍 HTML 生成静态索引，运行时纯前端查询，不需要后端， 不违反"无数据库、无服务端"的约束。索引文件按需加载，不拖首屏。

P2 · 长期维护
P2 解除 Astro 版本锁 成本 低

先把本机 Node 升到 ≥ 22.23.4，再把 astro 从 7.3.8 放开到 ^7.4。 升级后要重跑 astro check 和构建，重点看 Sätteri 处理器的配置项有没有变。

P2 支持子路径部署 成本 中

把所有内链从 /xxx/ 改成 import.meta.env.BASE_URL 前缀， 这样 fork 出来的人可以直接部署到 user.github.io/repo，不必买域名。 改动面广但机械，适合一次性做完再统一验证。

P2 图标自动化 成本 中

写个脚本按 links.ts 里的域名批量抓 favicon、校验尺寸、缺图的自动退到字母块。 顺便把"手工抓 34 张图"这件一次性劳动变成可重复的流程。

P2 CI 加链接检查 成本 低

构建后扫一遍 dist 里的内链和图片引用，死链在流水线阶段就报错。 外链可以单独跑、允许失败，避免被别人的站点波动拖累。

P2 草稿预览 成本 低

dev 环境放行 draft: true，生产构建继续过滤。 posts.ts 里加一个 import.meta.env.DEV 判断即可。

P2 无障碍实测 成本 低

用对比度工具核一遍灰阶文字（尤其是 --text-muted 在小字号下的表现）， 再用 VoiceOver 或 NVDA 走一遍首页到文章页的路径。黑白灰配色风险不大，但没量过就是没量过。

07当模板用的话

如果以后拿这个仓库开新项目，按下面四步走，能省掉重新踩坑的时间。

必须改的五个文件

文件改什么
src/config/site.json站名、域名、描述、语言、起始年
src/config/profile.json姓名、简介、头像、社交链接
src/config/navigation.json导航项与顺序
src/config/about.ts/me/ 页的全部内容
src/config/links.ts链接库；清空数组页面也不会崩

必须删的三样

  • src/content/blog/rurudo-unreal-interview.md 和 public/images/blog/rurudo-unreal/
  • public/docs/ 下的两个 HTML 指南（它们是写给这个项目自己的）
  • public/og-default.png，换成自己的分享图

必须想清楚的一件事

部署路径。现在所有内链都是根绝对路径，站点只能挂在域名根上 （用户站 user.github.io 或自己的域名）。如果新项目要部署成 user.github.io/repo 这种子路径，必须先按 P2 那一条把所有内链改成 import.meta.env.BASE_URL 前缀，否则整站 404。 README/fork.md 的第 0 节专门写了这件事。

最好别动的

src/styles/tokens.css。它只有 91 行，但是整个站点的气质来源—— 改了颜色、字号、圆角，等于换了一套设计语言，所有页面的观感会一起漂移。 想调局部，加组件级样式，别动令牌。

可以整个丢掉的

scripts/、tests/ 和 README/。 这三样服务于"把站点内容同步到 GitHub 主页 README"这个特定需求， 新项目如果不需要主页名片，删掉它们不影响站点运行。
