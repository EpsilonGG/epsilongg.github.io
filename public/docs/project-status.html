01一句话结论

站点已经完整可用：四个固定页面、一条文章路由、一套设计系统、一条 CI 流水线、 三份维护文档和两套脚本，全部跑通且互相对得上。它的定位是一个轻量化的编辑型个人主页—— 首页是名片，不是博客；文章是名片上的补充说明。整站首页传输 9.1 KB、零外部 JS， 这个体量是刻意的，也是它区别于同类站点的地方。

上一轮体检时最大的欠账是"内容规模化"——没有列表页、分页、标签筛选、搜索、文章内目录。 那一层已经补齐。这一轮补的是四件"零成本纯收益"的欠账： 补上 LICENSE（代码 MIT、内容 CC BY-NC-SA）、图片全部转 WebP 并加 srcset 与宽高、图注插件扩展到能认"带链接的图"和"连续多图"、 解除 Astro 版本锁（7.3.8 → ^7.4.2）。 顺手把 4 篇文章里 40 张手写 <figure> 统一成了 Markdown 写法， 否则它们永远享受不到图片管线。

剩下没做的是分类体系、社区性功能（评论、访问统计）和 子路径部署。前两项和"轻量化"这个定位冲突，属于想清楚了才做的取舍； 第三项只在 fork 到 user.github.io/repo 时才需要，方案写在第九节。

能改

03逐项说明

每一项都给出：做了什么、关键文件在哪、以及还剩什么。

3.1 页面与路由 src/pages/

四个固定页面加一条动态路由，全部静态预渲染：

  • / 首页：简介 → 站点导航 → 最近文章 → Footer，顺序固定
  • /me/ 名片：简介、主要平台、关注领域、项目、经历
  • /morelinks/ 链接库：5 组、2 个子栏目
  • /blog/ 笔记：按年份分组的全部文章（搜索 + 标签筛选 + 分页）
  • /blog/{slug}/ 文章详情，文件名即 URL
  • /404、/robots.txt（路由生成，不是静态文件）、/rss.xml、/sitemap-index.xml

trailingSlash: 'ignore' 配 build.format: 'directory'， 线上 URL 一律带尾斜杠。所有内链写成根绝对路径 /xxx/， 这意味着站点只能部署在域名根路径。

剩余：没有分类页（/blog/c/<slug>/）；列表页当初项目书规定"不设"，后来推翻了，见第五节。
3.2 设计与排版 src/styles/tokens.css · 91 行

所有颜色、字号、间距、圆角、行宽都只在 tokens.css 定义，组件里不允许写死数值。 视觉规则：黑白灰、无强调色、常规圆角统一 6px（徽章 2px 是唯一例外）、无阴影、中文不用斜体。

三套字体，全部自托管、只含拉丁子集，合计 105 KB： Cormorant Garamond（标题衬线）、Inter（正文无衬线）、Fira Code（等宽）。 中文走系统字体栈，不下载中文字体。

剩余：CJK 字形在 macOS / Windows / Linux 上不一致，标题观感会飘。
3.3 内容与数据配置 src/config/

约定是"JSON 是数据源，同名 .ts 只做类型包装"，这样 Python 同步脚本能直接读 JSON， 不需要解析 TS。目前四个数据源：site.json（站点名、域名、语言、起始年、OG 图）、 profile.json（姓名、简介、头像、社交链接）、navigation.json（导航项）、 links.ts（链接库，因为是带联合类型的结构化数据，直接用 TS 更省事）。

剩余：about.ts 是纯 TS，不符合"JSON 数据源"的约定，Python 脚本读不到它。 当前没有脚本需要读，属于已知不一致。
3.4 链接库 src/config/links.ts · LinkBlock.astro

五组：平台、项目、工具与服务、研究、常用链接。常用链接下再拆两个子栏目—— GitHub（5 位朋友，带头像）和 ACG 资源（12 条，一排五个的按钮墙）。

五种排版：卡片（LinkCards）、图标网格（IconGrid）、列表（LinkList）、按钮墙（BadgeWall）、单行（LinkRow）。 LinkBlock.astro 按 layout + fallbackLayout 做分发和降级， 所以某个组数据不全时会自动退到更简单的排版，不会渲染出空洞。

剩余：34 个图标是手工抓取的 PNG（多数 64×64，工具类 96×96），源站换 favicon 不会自动更新； VNDB 和南+论坛只提供 16×16 图标，用 CSS 字母块代替位图。
3.5 博客与 Markdown src/content.config.ts · astro.config.mjs

Content Collections + Zod。字段：title（必填）、pubDate（必填）、 description、updatedDate、tags（默认空数组）、 draft（默认 false）。另外有一条跨字段校验：updatedDate 不能早于 pubDate。

Astro 7 默认用 Sätteri 处理器，所以 GFM 脚注开箱可用，不需要装 remark-gfm。 代码高亮用 Shiki 双主题（github-light / github-dark）， defaultColor: false 让颜色交给 CSS 变量，跟随站点主题切换。

剩余：tags 已经用起来了（列表页的 AND 组合筛选），但没有独立的 /tags/<tag>/ 路由，筛选状态也不进 URL，刷新后丢失； 草稿仍然只能改成 draft: false 才能预览。
3.6 注释（脚注弹层） 本轮新增 article-notes.ts · 101 行

写法就是标准 GFM 脚注：正文里 文字[^1]，文末写 [^1]: 注释内容。 点击正文里的上标，页面底部滑出一块面板显示该条注释，右上角有 × 可关闭； 文末仍然保留完整的注释列表。

  • 关闭方式三种：× 按钮、Esc、点面板外部
  • 关闭后焦点回到刚才点的标记，aria-expanded 同步复位
  • 点标记不会跳转锚点（location.hash 保持为空），读者不会丢失阅读位置
  • 面板里的「注释 N」序号和文末列表一一对应，克隆自文末节点并去掉回跳箭头
  • JS 失效时退化成原生脚注：上标仍能跳到文末列表

现有一篇访谈里的 8 条「译注」已全部改成脚注，打开 /blog/rurudo-unreal-interview/ 就能直接看效果； 标记的点击热区做过外扩，视觉尺寸不变但更容易点中。

剩余：面板最高 45vh，超长注释要在面板内滚动；窄于 480px 时面板几乎占满屏幕。
3.7 图片图注 完成 src/lib/markdown-figure.mjs · 228 行

最短写法：![alt](图片路径 "图注文字")——Markdown 的 title 就是图注。 构建时一个 hast 插件把"独占一个段落、带 title 的图片"升级成 <figure> + <figcaption>，并把 title 从 <img> 上摘掉，避免和浏览器 hover 提示重复。

这一轮把认得的结构从 1 种扩到 4 种，另外加了一条并组规则：

  • p > img：普通图片
  • p > picture > img：已经被 WebP 管线包过的图片
  • p > a > img：点击可放大的图片（链接保留在 figure 里）
  • p > a > picture > img：两者叠加
  • 连续两张以上带图注的独占段落图 → 自动并成 <div class="article-figure-grid">， 宽屏并排、窄于 34rem 时回到一行一张

顺手还修掉一个一直没人发现的老问题：<figure> 带着浏览器默认的 左右各 40px 外边距，之前的样式只覆盖了上下，于是每张图注图实际只有 528px 宽（正文栏 608px），并且整体右移 40px。单张时只是"看着有点偏"， 并组之后每格白丢 80px 才暴露出来。

剩余：行内小图标（段落里还有文字）仍然不出图注，这是有意的——把图标包进 figure 会撑乱行距。 另外并组只认"相邻"，中间夹一句正文就断开了。
3.8 主题与可访问性 theme.ts · BaseLayout.astro

亮/暗双主题：默认跟随系统 prefers-color-scheme，可手动切换，选择记在 localStorage。页面 <head> 里内联了一小段同步脚本， 在首次绘制前就把主题类名写上去，所以不会闪白。

可访问性做了这些：.skip-link「跳到主要内容」、注释面板 role="dialog" + aria-labelledby + 焦点管理 + Esc、 主题按钮带 aria-pressed、图片全部有 alt、 prefers-reduced-motion 下关掉滑入动画。

剩余：没做过屏幕阅读器实测；对比度没用量化工具核过；移动端只验到 500px 宽（Chrome headless 的下限），没上真机。
3.9 性能与图片管线 dist/ · 15 MB（原图 7.0 + WebP 6.2）

产物 15 MB 的构成：图片 14 MB（原图 7.0 MB + WebP 变体 6.2 MB + 站点图标）、 HTML 约 500 KB、字体 136 KB、CSS 35 KB。 但首屏和这个数字无关——首页实际传输 9.1 KB（HTML 2.8 + CSS 6.3）， 文章页 21.0 KB。图片只在滚到它时才开始下载。

CSS 打成单文件 35 KB，gzip 后 6.3 KB，没有任何外部 JS 文件—— 脚本量太小，Astro 全部内联进了 HTML。文章页一共 5 个 <script>： 1 个在 head 里防主题闪烁，其余是主题切换、阅读进度、注释面板、侧栏目录与返回顶部。 没有客户端框架、没有 hydration、没有第三方请求，字体和图标都是自己的。

图片管线是本轮新增的：public/ 下的文件是原样拷贝， Astro 的图片管线完全不管，所以之前 7 MB 图片既没压缩也没尺寸。 现在构建前跑 scripts/optimize_images.mjs（sharp）： 每张图生成 600 / 960 / 原宽三档 WebP，把宽高和变体清单写进 src/data/image-manifest.json，再由 hast 插件拼成 <picture> + srcset + width/height。 并排成组的那几张，sizes 会跟着从 38rem 改成 19rem， 否则浏览器按整栏宽挑图，白白多下一倍。

仓库是用户站 EpsilonGG/epsilongg.github.io，所以不配 base，域名即根路径。

剩余：Actions 列表里偶尔有一条 pages build and deployment 失败，那是 GitHub 内置构建 与自定义流水线打架，不影响发布结果，属于已知无害项。
3.11 脚本与测试 scripts/ · tests/

sync_profile_readme.py（445 行）把 profile.json、 navigation.json 和文章列表同步进主页 README 的三个 marker 块里。 三个 marker 的顺序固定，脚本幂等（重复运行结果不变），写入用"临时文件 + 原子替换"， 所以中途失败不会留下半截文件。--check 是严格只读模式，可以用来做 CI 校验。

check_remote_images.py（约 290 行）扫文章里的远程图片，逐张请求， 报状态码、类型和体积，坏链退出码 1。它补的是一个结构性漏洞—— 构建只拼 HTML 不请求图片，所以外站删图在流水线里永远发现不了。 加 --write-dims 时顺便把宽高记进 src/data/remote-images.json， 构建时自动给远程图补尺寸（见 3.15）。

optimize_images.mjs（约 190 行）是图片管线的前半段：扫 public/images/blog/，出 WebP 变体、写尺寸清单。按 mtime 增量， 第二次运行基本是空转。

测试合计 53 个用例：

  • test_readme_sync.py（24 个）：marker 缺失、顺序错乱、内容为空、日期格式化
  • test_remote_images.py（13 个）：两种图片写法、代码块忽略、行号、 体积格式化，以及 PNG/JPEG/GIF/WebP 的宽高解析（纯 Python，不依赖 Pillow）
  • test_image_manifest.py（5 个）：文章引用的每张图都在清单里、 变体文件真实存在、宽度递增且不放大
  • tests/markdown/*.test.mjs（11 个，node --test）： 图注插件的单图 / 并组 / 行内图 / 链接图 / picture 五种情形， 外加并组后 sizes 是否跟着缩半
剩余：测试覆盖的是脚本和插件，站点页面本身仍然没有自动化测试—— HTML 结构、内链、TOC 条数这些还是靠手工抽查。加一个构建后扫死链的脚本成本很低（约 30 行）， 但这一轮没做。

frontmatter 加了一个 source 枚举，只有两个值： original（原创，或人工转载）和 ai（AI 参与整理/生成）。 不另开栏目，全部留在「笔记」一栏里：默认列表叫「原创与转载」，只显示 original； 勾上筛选区的「含 AI 整理」滑块后，ai 的文章才并入，栏目名跟着变成「全部（含 AI 整理）」。

ai 的文章在列表项、单篇页、首页「最近文章」三处都显示「AI 整理」标记—— 披露必须跟着文章走到任何可能出现的地方，只做一处等于没做。

剩余：original 里混着"原创"和"人工转载"两种，目前靠正文里的出处说明区分，没有字段级的细分。
3.15 图片策略：本地化、远程引用与 WebP 完成 markdown-images.mjs · optimize_images.mjs · check_remote_images.py

两种模式并存。B 站专栏的图一律下载、压到 1400px 宽再落地； 其它外站文章可以只写原站地址（![图注](https://原站/xx.jpg "说明")）， 仓库零字节，构建时也不会去请求它。

markdown-images.mjs 干两件事：给所有 Markdown 图片补 loading="lazy" / decoding="async" / referrerpolicy="no-referrer"（最后一条用来绕开外站基于 Referer 的防盗链， 实测 gamespark、4gamer、denfaminicongamer、automaton、famitsu 五家都不拦）， 再把有 WebP 变体的站内图包成 <picture>。

图片尺寸有两个来源，合并在一个查找表里：站内图读 src/data/image-manifest.json（构建时生成）， 远程图读 src/data/remote-images.json（跑一次 check_remote_images.py --write-dims 才有）。两个文件都缺也不会报错， 只是那几张图没有 width / height。

剩余：手写 <figure><img> 属于原始 HTML，不经过插件， 拿不到上面这些属性。这一轮已经把 40 张手写图转成 Markdown 写法， 只剩 1 张因为图注里带链接和引号留在手写状态。
3.16 授权 本轮新增 LICENSE · LICENSE-CONTENT

  • LICENSE（MIT）：src/、scripts/、 tests/、配置文件与工作流。随便拿去改、拿去商用，保留版权声明即可
  • LICENSE-CONTENT（CC BY-NC-SA 4.0）：文章、译文、图片、文档。 署名 + 非商业 + 相同方式共享

04问题清单：原因与严重性

这一节只回答三个问题：是什么、为什么、有多要紧。 "严重性"按"会不会真的咬到人"排，不看实现难度： 严重 影响正确性或可用性 · 中等 影响体验但能忍 · 轻微 基本无感 · 已解决 这一轮修掉了。

图片没有 WebP / AVIF，也没有 srcset 中等 已解决

public/ 是原样拷贝进产物的，Astro 的图片管线只管 src/assets/ 里的图。Markdown 里写 /images/blog/… 走的是 public/，所以从来没被优化过——不是配置漏了，是这条路本来就不通。

修法：构建前用 sharp 出 WebP 三档 + 尺寸清单，构建时读清单拼 <picture>。详见 4.1 第一条。
远程图片拿不到原始宽高 轻微 已解决

构建是离线拼 HTML：远程图只有一个 URL，尺寸要下载完才知道， 浏览器在图片到达前只能按 0 高度排版，于是图片一加载页面就往下顶一下（CLS）。 纯前端也补不了——跨域读 naturalWidth 要等图到，等于没解决。

修法：让体检脚本顺手把宽高写进 src/data/remote-images.json，构建时只读文件。 详见 4.1 第二条。
CJK 依赖系统字体 轻微 不做

中文字体没法像拉丁字母那样只带两百个字形。一个常用字子集约 0.8–1.5 MB，而整站首页只传 9.1 KB——装一个中文字体， 首屏就翻一百倍。拉丁部分（Inter / Cormorant）是自托管的，中文刻意交给系统： macOS 用苹方、Windows 用雅黑或宋体、Android 用思源。字形略有差异，字号和行高是一致的。

如果非要统一：只对标题做子集化（仍要 300–600 KB），或者用第三方 CDN 的思源子集 （引入外部请求，破坏零依赖）。两条都不划算。
astro 锁死 7.3.8 中等 已解决

astro 7.4 起要求 node >= 22.23.4，而本机 PATH 里默认是 22.22.2——只差三个补丁号，但 npm 会按 engines 拒绝安装。 实际上机器上同时装了 Node 24.15.0，只是 PATH 优先给了旧的。 换句话说，锁的是路径，不是机器。

修法：放开到 ^7.4.2、engines 跟上游对齐、CI 钉 Node 24。详见 4.1 第三条。
只能部署在域名根路径 中等 不做

站内链接全是 /blog/、/images/… 这种根绝对路径， astro.config.mjs 也没设 base。放到 user.github.io/repo/ 下，所有链接都会指到域名根，全站 404。

绕开办法：新账号建同名仓库（<name>.github.io）就天然是根路径， 零改动。真要做子路径，改动清单在 9.3 节。
og-default.png 是静态图，且不跟 base 走 轻微 不做

OG 协议要求绝对 URL，构建时用 new URL(ogImage, site.url) 拼出来， 所以它跟 site.url 走、不跟 base 走。 换域名要改 site.json；改成子路径部署时它仍然指向域名根，分享卡片会裂。 图本身是手做的 PNG，改站名要重做一张。

自动化要引入 satori / resvg 之类的渲染引擎，为了一张图不值得。
站内搜索只到标题 / 描述 / 标签 中等 不做

搜索是纯前端读 DOM 上的 data-title / data-description / data-tags。正文根本没进索引——不是"搜得不准"， 是"没被索引"。列表页为了首屏体积不可能把全文塞进 DOM。

增量评估：Pagefind 索引约 15–25 KB/篇（gzip），只在打开搜索时下载。 5 篇约 100 KB，20 篇约 400 KB。判定见第五节。
CI 没有链接检查 中等 不做

死链只在构建产物里才看得见。Astro 不会校验 /blog/xxx/ 是否真的存在， astro check 也只看类型。一次手滑改 slug 就是线上 404，而且没人会发现。

脚本约 30 行：扫 dist 里的 href="/…" 与 src="/…"， 映射到文件系统，缺文件即退出 1。第五节排在第一。
无障碍没有实测 中等 不做

对比度、焦点顺序、读屏朗读只能人工验；axe 之类的自动工具只覆盖三到四成。 黑白灰配色风险不大，但"没量过"就等于"不知道"。

真机与读屏实测由站长自己安排，这一轮不动。
手写 <img> 绕过所有 Markdown 插件 轻微 基本清完

Sätteri 把原始 HTML 当 raw 节点透传，不解析成 hast， 插件在树里根本看不到里面的 <img>。之前 4 篇文章的 40 张图都是这么写的， 等于整条图片管线对它们无效。

这一轮把 40 张全部转成 Markdown 写法，只剩 1 张因为图注里带链接和引号留在手写状态。
图标是手工抓的 轻微 不做

链接库三十多个站点的 favicon 是一次性下载加手工筛的，没有记录来源与时间。 源站换图标不会跟着更新，但图标本来也不会坏。

没有评论、没有访问统计 中等 取舍

两者都需要一个"能写数据的地方"，静态站没有。加任何第三方服务都会引入 外部请求与隐私披露，和"零第三方依赖"直接冲突。 评论区、统计、登录这三件是同一个问题的三种问法。

只做"发到我邮箱的表单"是可行的，复杂度与风险见第七节。
没有分类体系 轻微 取舍

分类要有意义，得每类至少三篇。现有 5 篇全落在「访谈 + 翻译」里，做出来就是四个空格子。 标签筛选已经能顶一阵。

详细判据在 README/reports/category-module-proposal.html。

4.1 三条已经修掉的，修法值得记一下

图片优化：在 public/ 外面补一条管线 scripts/optimize_images.mjs

既然 Astro 不管 public/，那就自己管：构建前用 sharp 扫一遍 public/images/blog/，给每张图出 600 / 960 / 原宽三档 WebP， 同时把宽高写进 src/data/image-manifest.json。 构建时一个 hast 插件读清单，把图包成 <picture><source type="image/webp" srcset><img></picture>， 并补上 width / height。

为什么不换 Astro 的 <Image> 组件：那要求把 52 张图搬进 src/assets/ 并改所有文章的写法。收益只是"少写一个脚本"， 代价是写作体验变差（图片路径不再是稳定的公开 URL）。不划算。

实测：手机端读完整个站点的图片下载量从 7.0 MB 降到 1.8 MB（26%）； 代价是产物从 7.8 MB 涨到 15 MB，因为原图留着当兜底。
远程图尺寸：把"联网"挪到脚本里，别让构建联网 check_remote_images.py --write-dims

构建期联网是禁忌（慢、会挂、CI 里不可复现）。所以换一个思路： 体检脚本本来就要请求每一张远程图，顺手把宽高解析出来写进 src/data/remote-images.json，构建时只读文件。

解析器是纯 Python 的（PNG / JPEG / GIF / WebP 头部，约 50 行）， 不依赖 Pillow——因为写文章的机器上不一定装了 Pillow，而这个脚本要能随时跑。

代价：原站换图（尺寸变了）时得记得重跑一次。忘了也不会坏，只是那几个 width / height 会偏，反而可能比以前更糟——所以这一步写进了维护文档。
Astro 版本锁：先确认"锁"是不是真的 package.json · .github/workflows/deploy.yml

上一轮记的结论是"本机 Node 22.22.2，装不了 astro 7.4"。这一轮查了一下： 机器上同时装了 Node 24.15.0，只是工具环境的 PATH 把 22.22.2 排在前面。 换句话说，锁的是路径，不是机器。

处理：astro 从 7.3.8 放开到 ^7.4.2， engines.node 改成 >=22.23.4（跟着上游要求走，不再假装 22.12 够用）， CI 的 setup-node 钉到 24。 升级后 astro check 0 错、构建通过、53 个测试全过。

顺手记一个坑：Astro 7 把渲染好的 Markdown HTML 缓存在 node_modules/.astro/data-store.json 里。 改了 hast 插件不删这个缓存，构建结果不会变—— 这一轮在这上面浪费了四次构建才反应过来。

05还剩什么值得做

上一轮列了一堆 P1/P2，这一轮砍到只剩三件——其余明确不做， 理由写在下面，免得过几个月又想起来纠结一次。

值得做 · 按性价比排
1 CI 加构建后死链检查 成本 极低 · 约 30 行

扫 dist 里所有 href="/…" 与 src="/…"， 映射到文件系统，缺文件就退出 1。外链单独跑、允许失败，避免被别人的站点波动拖累。 这是全站唯一一处"出错概率不低、发现概率为零"的地方：改 slug、删页面、 换图片目录，都不会有任何提示。

2 站内搜索扩到正文（Pagefind） 成本 中 · 2 小时

必要性判断：5 篇文章时搜标题就够了；到 15 篇，读者会开始记得 "某篇里提过某个作品"而不是标题；到 30 篇，搜不到正文就等于没有搜索。

项目增量：Pagefind 在构建后扫一遍 HTML 生成静态索引， 运行时纯前端查询，不需要后端。索引按篇分片，约 15–25 KB/篇（gzip）： 5 篇约 100 KB，20 篇约 400 KB，50 篇约 1 MB——而且只在打开搜索框时才下载， 不进首屏。代价是多一个构建步骤、多一份产物、多一个 npm 依赖。

3 支持子路径部署 成本 中 · 半天

把所有内链加上 import.meta.env.BASE_URL 前缀。改动面不窄但很机械： 8 处组件里的 href="/…"、navigation.json 里的 href、 Markdown 图片路径（要加一个插件改写）、site.json 的 ogImage、 RSS 与 sitemap 的绝对地址。做之前先确认真的需要——第九节给了一条零改动的替代路径。

明确不做
  • AVIF——比 WebP 只再省 10–20%，编码慢十倍，52 张图省不下多少，还多一套兜底逻辑
  • 自托管中文字体——一个子集 0.8–1.5 MB，是首屏的 100 倍。要么标题单独子集化（仍要 300 KB+），要么放弃
  • 评论后端 / 访问统计——都要能写数据的地方，都要第三方请求。轻量化的核心是"没有这些东西也能读"
  • 分类树（/blog/c/…）——5 篇文章分不出四类。标签筛选已经够用，等 12 篇以上再谈
  • 标签进 URL、独立标签页——收益是"能分享筛选结果"，文章少的时候几乎没人会分享
  • 窄屏注释面板改全屏 sheet——现在的 45vh 面板能用，改它属于打磨，不是修 bug
  • 图标自动抓取——一次性劳动已经干完，自动化只对"以后频繁加链接"有用
  • 草稿 dev 预览开关——把 draft 改成 false 只要两秒，加开关反而多一条代码路径
  • 自动生成 OG 图——要引入 satori/resvg 之类的渲染引擎，为了一张图不值得

6.5 优点与缺点，直说

优点 · 体积

首页 9.1 KB，是三个对照站的 1/8 到 1/55；文章页对文章页是 2.3 倍。没有框架、没有水合、没有第三方请求，这不是优化出来的，是架构决定的。

优点 · 阅读侧最完整

图注、注释弹层、侧栏目录、阅读进度、较新/较旧、返回顶部——四个站里唯一把这些凑齐的。

优点 · 可维护

数据只在 config/，样式只在 tokens.css，31 个测试、3 份文档、一条 CI。改内容不碰组件。

优点 · 有披露意识

AI 整理在列表、单篇、首页三处同步标记，转载注明出处，页脚有版权声明。这一项很多同类站直接没有。

缺点 · 内容撑不起体量

5 篇、3.5 万字。轻量化在数字上是优势，在观感上就是"空"——首页除了一段简介，只剩一屏文章列表。

缺点 · 零互动

没有评论、没有统计。读者无处说话，站长不知道哪篇有人看。这是刻意的取舍，但代价是真实的。

缺点 · 分类缺位

标签只能临时筛选，刷新就丢、不能分享。文章一多，"按主题找"这件事没有落脚点。

缺点 · 工程欠账

图片管线与 LICENSE 已经补齐；剩下无真机与无障碍实测（站长自己安排）、无子路径部署、无死链检查。

最后一句判断。对照下来，本项目的短板不是功能，是内容。 功能已经越过"够用"这条线：目录、筛选、分页、注释、图注、披露，该有的都有， 再加功能只会往 ymgal 那个方向走，而那条路需要后端和运营。 接下来真正该做的是把文章从 5 篇写到 15 篇——那时候分类体系才有意义， 也才谈得上"这个站在讲什么"。

07只开一个邮箱框行不行

结论先说：行，但收益有限，而且它不是"免费"的。 静态站没有服务端，所以"提交"这件事必须落到别人家的服务器上—— 你少写一个后端，就多欠一个第三方。

7.1 三条路线，复杂度差一个数量级

mailto: 链接 复杂度 零

一个 <a href="mailto:…">，页脚现在就是。 点下去会调起本机邮件客户端——很多人根本没配，点了没反应；手机上还行。

第三方表单服务 复杂度 低

Formspree / Web3Forms / Getform，一个 <form action="https://…"> 就完事。 免费额度 50–250 封/月；服务商能看到内容；邮件可能进垃圾箱；免费版可能夹广告页。

这一条才是你说的"发送到我邮箱的框"。
GitHub Issues 当评论区 复杂度 中

giscus / utterances，iframe 里嵌一个讨论串。必须登录 GitHub 才能发言， 门槛比邮箱高；页面里多一个 iframe 和一段第三方脚本。

"发送到我邮箱的框"对应的是第二行。真正要写的代码只有一块表单： 姓名（可选）、邮箱（可选）、内容（必填）、一个 honeypot 隐藏字段、 提交后把按钮换成"已发送"——大约 20 行 HTML，零 JavaScript 依赖， 用浏览器原生校验就够。

7.2 受攻击的难度：低，但打不穿

先把一件事说清：静态站没有可攻破的后端。没有数据库、没有登录、没有文件上传、 没有服务端渲染，所以"网站被黑"这条基本不成立——攻击者最多改自己浏览器里看到的东西。 风险全在表单那条链路上：

绕过页面直接 POST 难度 极低

表单的 action 就写在 HTML 里，curl 一行就能刷。 绕不过去——这是公开接口的固有属性，只能靠服务商限流。

垃圾邮件 难度 低

脚本批量提交广告，收件箱被塞满。 honeypot 隐藏字段能挡掉九成机器人：人看不见那个字段，机器人会填。

当免费邮件枪用 难度 低

反复提交，让你收到几千封、顺便烧掉免费额度。额度被耗尽后正常访客就发不进来了， 服务商也可能因此封号——这一条的后果比垃圾邮件严重。

投毒内容 难度 低

提交超长文本、链接、HTML。因为内容只进你的邮箱、不进网页，所以没有 XSS 风险； 但可能触发邮件客户端的渲染问题。

判断。攻击成本低、收益也低——别人花力气刷你，只能给你添堵， 拿不到任何数据。所以真实风险是"烦"，不是"危险"。 加上 honeypot + 服务商自带限流之后，可以接受。 真正需要警惕的是"额度被烧光导致正常留言丢失"，那属于可用性问题。

7.3 如果真要做，建议这么写

  • 用 Web3Forms 或 Formspree，不自己搭 Serverless—— 后者要账号、要域名、要处理密钥，等于真的开了个后端
  • 表单字段只留"称呼 / 邮箱 / 内容"，邮箱选填（必填会劝退一半人）
  • 加一个 display:none 的 company 字段当 honeypot； 有值就直接在前端拒收（不用发出去）
  • 提交成功不要跳转，原地把按钮文案换成"已发送"，失败给一句"没发出去，可以直接发邮件到 …"
  • 页脚保留 mailto: 兜底——表单挂了，人还能找到你

最后一句实话。页脚和名片页现在已经放了邮箱，"能联系上"这件事已经成立。 加表单的边际收益只是"不用打开邮件客户端"，边际成本是打破"零第三方请求"这个招牌， 以及多一个需要盯着额度和垃圾邮件的账号。想做就做，但别指望它带来多少互动—— 一个没人看的站，多一个输入框还是没人留言。

08站点气质从哪来

这一节写给"没有网页设计经验、但想改观感"的自己。核心只有一句话： 所有"长相"相关的数值都集中在 src/styles/tokens.css 一个文件里， 组件只写"用哪个名字"，不写具体数值。 所以你不需要看懂组件，改一个变量，全站跟着变。

8.1 它到底管什么

tokens.css 是一张 91 行的清单，分四组，对"气质"的影响权重完全不同：

颜色 影响 最大

--color-bg、--color-text、--color-text-secondary、 --color-border、--color-selection、--color-tile-*，一共 10 个。 换一套颜色等于换一个站。现在的黑白灰是"编辑型"气质，靠的正是没有强调色。

字体 影响 很大

--font-sans / --font-serif / --font-mono。 衬线标题 = 杂志感；圆体 = 二次元；等宽正文 = 极客感。换之前先确认字体文件在 fonts.css 里声明过，否则浏览器会静默回退。

字号 / 行高 / 字距 影响 中

--text-xs … --text-3xl、--leading-*、--tracking-*。 字号大一号、行高松一点，立刻从"文档"变成"读物"。

间距 / 形状 / 动效 影响 中

--space-1..8、--radius、--duration、--ease。 圆角 6px 是"克制"，16px 是"柔和"，0 是"硬朗"；间距加大是"呼吸感"。

最容易踩的坑：深色主题只覆盖了颜色。 tokens.css 末尾有一段 :root[data-theme="dark"]， 里面只重新定义了颜色变量。所以换色要改两处（浅色一份、深色一份）， 改字号、圆角、间距则只改一处。忘了改深色那份，深色模式下新颜色会失效， 而且不一定看得出来。

8.2 三个配方，直接抄

把下面任一段追加到 tokens.css 的 :root 里即可。三段互斥，选一个。

配方 A · 二次元一点

关键动作只有三个：底色从纯白换成带色相的浅色（纯白最"办公"）、 加一个强调色（现在没有，这是它显得"冷淡"的根本原因）、 圆角加倍。 

/* 浅色：米白底 + 樱花粉强调 + 大圆角 */
--color-bg: #fffafc;
--color-bg-subtle: #fdf2f6;
--color-text: #2a2226;
--color-text-secondary: #6b5a63;
--color-border: #f0dde5;
--color-accent: #e0708f;      /* 新增：链接、标签、选中态用它 */
--radius: 14px;
--font-sans: "Zen Maru Gothic", "PingFang SC", "Microsoft YaHei", sans-serif;

/* 深色那份也要跟着改 */
--color-bg: #1a1418;
--color-bg-subtle: #221a1f;
--color-text: #f2e9ed;
--color-accent: #f090ad;

注意：--color-accent 是新增的变量，组件里现在没有任何地方用它。 要让它真的生效，得去 components.css 里把链接的 text-decoration-color、标签底色、选中态改成 var(--color-accent)—— 这一步就不是"改 token"了，是改组件。所以先想清楚：要不要破"无强调色"这条线。 这也是当前设计的边界：它靠"没有颜色"保持统一，加了颜色就必须重新决定"哪里该有颜色"。

配方 B · 杂志感一点

不换色，只放大标题、换衬线、拉开行距。改动最小，效果最"贵"。

--text-3xl: 2.75rem;          /* 大标题再大一号 */
--text-2xl: 2.125rem;
--leading-relaxed: 1.9;       /* 正文行距放宽 */
--tracking-wide: 0.08em;
--font-sans: "Source Serif 4", "Songti SC", "Noto Serif SC", Georgia, serif;

配方 C · 带广告 banner

广告位不是"改个颜色"，它会撞上现有的三条约束，得一起处理：

  • 宽度不够：正文容器 --page-max: 46rem（736px）， 而常见 banner 是 728×90 或 970×90。728 勉强能塞，970 塞不下。 要么把容器放宽到 60rem，要么让 banner 独立于容器、自己居中
  • 比例要固定：不给高度的话，图片没加载完页面会跳，和图片 CLS 是同一个问题。 728×90 的比例是 8.09:1，用 aspect-ratio 锁住
  • 会引入第三方：广告要么是图片（自己托管，可控）， 要么是联盟脚本（外链 JS，打破"零外部 JS"）
/* 新增两个 token，不动原有版式 */
--ad-max: 45.5rem;   /* 728px */
--ad-ratio: 728 / 90;

/* 组件里大致这么写（示意，不在 tokens.css 里） */
.ad-slot {
  max-width: var(--ad-max);
  margin: var(--space-5) auto;
  aspect-ratio: var(--ad-ratio);
  border: var(--border-width) solid var(--color-border);
}
.ad-slot img { width: 100%; height: 100%; object-fit: cover; }

广告会把"编辑型站点"的气质一次性变成"门户"。真要做，建议先想清楚 放在哪：文章正文中间（打断阅读，收益最高）、列表页每 5 篇一个（不打断阅读）、 还是页脚上方（几乎没人看）。位置上做选择，比配色重要得多。

8.3 改完怎么自检

  • 对比度：正文对背景至少 7:1，次要文字至少 4.5:1。 现在的 #1a1a1a 对 #ffffff 是 17.4:1，很安全； 换成浅粉底 + 深灰字时要重新量
  • 深色模式：切一次主题，看有没有哪块还是白的
  • 窄屏：缩到 390px 宽，看标题会不会折成三行、表格会不会撑破
  • 别在组件里写死颜色：写了就再也改不动了，而且深色模式必漏

一句话总结。想改气质，先动颜色和字体，别动间距—— 颜色和字体是"一眼看见"的，间距是"感觉舒服"的。前者改对了气质立刻变， 后者改错了会显得排版松散，而且很难说清哪里不对。

9.5 备份时绕不开的三个现实问题

  • 公众号正文基本不能带外链。译文里的原文出处链接会被折叠或要求改写成文字， 建议在正文末尾统一写"原文：xxx（链接见站点）"，站点那份保留可点的链接
  • 图片要重新上传。公众号不接受外链图床，本地图得再传一遍； 本站的 WebP 变体不用带过去，原图（.jpg / .png）才是通用格式
  • 授权跟着仓库走。fork 出去后 LICENSE（MIT）和 LICENSE-CONTENT（CC BY-NC-SA）也一起过去了。备份自己的文章没问题； 如果备份的是别人的译文，出处必须一起保留——那是 CC 署名的要求， 也是原作者的底线

这一节没有改任何代码。路径 A 的四个配置文件、路径 A 的删除清单， 都是纯手工操作，脚本化反而更容易出错（每个备份站的取舍不一样）。 真要动手时照着 9.1 的六步走，比记一套脚本可靠。

11当模板用的话

如果以后拿这个仓库开新项目，按下面四步走，能省掉重新踩坑的时间。

必须改的五个文件

文件改什么
src/config/site.json站名、域名、描述、语言、起始年
src/config/profile.json姓名、简介、头像、社交链接
src/config/navigation.json导航项与顺序
src/config/about.ts/me/ 页的全部内容
src/config/links.ts链接库；清空数组页面也不会崩

必须删的三样

  • src/content/blog/ 下全部文章，以及 public/images/blog/ 下对应的图片目录
  • public/docs/ 下的 HTML 指南（它们是写给这个项目自己的，共 4 个）
  • public/og-default.png，换成自己的分享图

必须想清楚的一件事

部署路径。现在所有内链都是根绝对路径，站点只能挂在域名根上 （user.github.io 这种用户站，或自己的域名）。要部署成 user.github.io/repo 这种子路径，必须先加 base 并改写内链， 否则整站 404——完整改动清单在 9.3 节，README/fork.md 第 0 节也写了这件事。

换气质就改 tokens.css

src/styles/tokens.css 只有 91 行，但它是整个站点的气质来源： 颜色、字体、字号、间距、圆角、动效全在里面，组件只引用变量名、不写具体数值。 它不是"最好别动"，而是"只该在这里动"——想改观感就去改它， 别去组件里写死颜色。三个现成配方（二次元 / 杂志感 / 带广告位）在第八节。

新项目会立刻遇到的两件事

  • npm run dev / build 会先跑 scripts/optimize_images.mjs， 它依赖 sharp（已经在 devDependencies 里，npm ci 会自动装）。 新项目如果没有 public/images/blog/，脚本会直接跳过，不报错
  • 改了 Markdown 插件之后，必须删掉 node_modules/.astro/data-store.json 再构建，否则看到的是缓存的旧 HTML。这个坑一次能省掉半小时

可以整个丢掉的

scripts/sync_profile_readme.py、tests/test_readme_sync.py、 .github/workflows/sync-profile-readme.yml 和 README/。 这一组服务于"把站点内容同步到 GitHub 主页 README"这个特定需求， 新项目如果不需要主页名片，删掉它们不影响站点运行。 scripts/ 里另外两个（图片优化、远程图体检）是站点本身要用的，别删。
